# 계약 청구·입금 장부 및 TV 매출 화면 설계 초안

상태: 사용자 선택과 개발 진행 요청을 반영한 구현 기준. 운영 배포는 별도 결정.

## 목적

정기 계약과 단건 계약을 동일한 월별 장부로 관리한다. CRM에서는 계약별 청구와 여러 차례의 부분입금 및 미수금을 확인하고, 회사 TV에는 확인된 합계만 표시한다. 기존 계약·입금 상태는 삭제하거나 자동으로 확정하지 않는다.

## 확정된 결정

- 정기·단건 모두 공통 장부에 연결한다. 정기는 계약 기간과 월 금액으로 월별 청구 초안을 제안한다. 단건은 작업일·입금 예정일·계약 금액을 이용해 해당 계약의 청구 초안을 제안한다.
- 기존 계약의 `연간`·`기타` 납부 방식은 월 정기나 단건으로 임의 해석하지 않고 `청구 방식 확인 필요`로 둔다. 관리자가 납부 주기와 귀속 월을 확인할 때까지 TV 금액에 넣지 않는다.
- 담당자는 초안과 입금 내역을 입력·수정한다. 대표 또는 관리자만 확정한다. 부분입금과 여러 건의 입금을 허용한다.
- TV는 청구액과 실제 입금액을 분리해 표시한다. 미확정 기록은 금액에 포함하지 않고 `확인 대기` 건수로만 표시한다.
- 기존 `collectionStatus`는 화면 호환을 위해 유지하되 새 장부의 확정된 입금액을 대신하지 않는다. 기존 체크만으로 입금액을 소급 생성하지 않는다. 입금일·금액 근거가 없는 단건은 `근거 확인 필요`로 표시하고, 담당자 입력·관리자 확정 뒤 집계한다.

## 데이터 계약

- 장부 위치는 기존 `crmCompany/data/contracts`와 분리된 `crmCompany/billingLedger`로 한다. 계약 데이터의 전체 저장 경로를 변경하지 않는다.
- 이 장부는 BRING이 고객에게 청구하고 회사 계좌로 받은 금액이다. 기존 건물주·세입자용 `paymentCalendars`와 매출을 혼합하지 않는다. 기존 계약 일정은 계속 계약·캘린더 화면에서 조회할 수 있다.
- `invoice`는 고유 ID, 계약 ID, 계약 유형(정기/단건), 청구 대상 월, 청구 예정일, 청구 금액(정수 원), 상태(`draft`/`approved`/`void`), 버전, 작성·확정 UID/시각을 갖는다. 정기는 `contractId + YYYY-MM`, 단건은 `contractId + occurrenceId`로 중복을 막는다. 금액·월을 바꾸는 재확정에는 버전 충돌 검사가 필요하다.
- `receipt`는 고유 ID, invoice ID, 실제 입금일, 실제 입금액(양의 정수 원), 증빙 참조, 상태(`draft`/`approved`/`void`), 작성·확정 UID/시각을 갖는다. 동일 은행 거래 참조는 동일 청구서에 두 번 확정할 수 없다.
- 취소는 삭제 대신 `void`와 취소자·시각·사유를 남긴다. 승인 후 금액 변경도 원본 이력 보존과 새 승인으로 처리한다.
- 청구서 `approved`와 입금 `approved` 권한은 Firebase 규칙에서도 관리자 역할로 제한한다. 직원의 입력 권한과 관리자 확정 권한은 UI 숨김만으로 대신하지 않는다.

## 계산 규칙

- 청구액 = 대상 월의 `approved` 청구 합계. 청구 예정 초안은 별도 `확인 대기`다.
- 입금액 = 대상 월에 실제 입금일이 속하는 `approved` 입금 합계. 청구 대상 월과 입금 발생 월을 섞지 않는다.
- 계약별 미수금 = 확정 청구 누계 − 연결된 확정 입금 누계. 초과입금은 음수 미수금으로 숨기지 않고 `초과입금 확인`으로 표시한다.
- 상태는 `미확정`, `미입금`, `부분입금`, `입금완료`, `초과입금 확인`으로 계산한다. 사람이 상태 문자열을 임의로 입력하지 않는다.
- 취소·종료·시작 전·종료 후 계약에서는 새 정기 청구 초안을 만들지 않는다. 계약 변경으로 기존 확정 장부를 삭제하지 않고 차액 확인 작업을 만든다.
- 단건 계약의 월간 귀속 기준은 작업일, 없으면 입금 예정일, 없으면 시작일이다. 기존 경영보고의 귀속 기준과 맞추고, 실제 입금액은 항상 실제 입금일 기준으로 별도 표시한다.
- 숫자 집계에는 정수 원과 안전한 합계 검사를 사용한다. `0원`, 금액 미입력, 데이터 미조회는 서로 다르게 표시한다.

## CRM 사용자 흐름

1. 계약 상세의 `청구·입금` 탭에서 기존 계약 정보를 바꾸지 않고 월별 초안을 연다.
2. 담당자가 청구액·대상 월·예정일을 확인하고 증빙을 연결해 관리자에게 확정 요청한다.
3. 실제 입금이 있으면 같은 청구서에 날짜·금액·거래 증빙을 건별로 기록한다. 일부만 입금되면 잔액을 바로 표시한다.
4. 관리자는 원문 계약과 입금 증빙을 확인한 뒤 청구 및 입금을 각각 확정한다. 거절·반려 사유를 남길 수 있다.
5. 월별 경영보고와 TV는 같은 확정 장부 집계 함수를 사용한다. 기존 단건 보고 숫자와 새 장부 숫자는 이행 기간에 나란히 보여 차이를 확인한다.

## TV 공개 경계

- TV 스냅샷에는 월, 확정 청구 합계, 확정 입금 합계, 미수 합계, 확인 대기 건수, 자료 기준 시각만 실린다. 계약명·고객명·건물명·거래일별 내역·계좌·증빙 링크·UID는 실리지 않는다.
- 관리자 승인이 없는 수치는 `집계 대기`로 표시한다. 지난 정상 게시본을 유지할 때에는 게시 시각과 `연결 확인 중`을 보여 주며 새 실적처럼 꾸미지 않는다.
- 회사 전체 실적만 표시한다. 팀원별 개인 매출·평가 지표로 자동 전환하지 않는다.

## 이행과 검증

- 배포 전 기존 계약과 장부의 읽기 전용 스냅샷을 백업하고 샘플 계약별 금액·상태를 대조한다.
- 과거 단건의 `입금 완료` 체크만으로 확정 입금 레코드를 만들지 않는다. 날짜·금액·증빙 확인이 필요한 건으로 분리한다.
- 먼저 순수 집계 함수와 규칙 테스트를 작성하고, 이어서 CRM 입력·확정 화면과 TV 투영을 만든다. 새 장부가 비어 있어도 기존 계약·캘린더·TV 장면이 동작해야 한다.
- 중복 청구·중복 거래·부분입금·여러 입금·환불/취소·계약 수정·권한 거절·연도 경계·서버 연결 실패를 테스트한다.
- 실제 회사 데이터는 자동 소급 확정하지 않는다. 운영 반영은 샘플 대조, 관리자 확인, 두 기기 TV 갱신 확인 후 별도 결정한다.

## 운영 배포 차단 조건 (구현 검토 중 확인)

현재 초안 구현의 Firebase 규칙은 각 청구/입금 레코드의 권한·형식·버전을 검증하지만, 형제 레코드를 가로지르는 자연키 중복과 거래번호 중복, 확정 입금이 달린 청구서의 취소를 원자적으로 증명하지 못한다. CRM 클라이언트의 사전 검사는 일반 사용 흐름을 보호하지만 동시 저장이나 직접 쓰기까지 막는 서버 보장은 아니다. 따라서 이 브랜치는 검토용이며 장부 쓰기 규칙·관리자 확정·TV 매출 게시를 운영에 배포하거나 병합하지 않는다.

운영 전에는 신뢰된 서버의 단일 장부 트랜잭션에서 권한·버전·중복·취소 연관성을 함께 검사하고, Firebase 장부의 클라이언트 직접 쓰기를 닫는다. 기존 장부에 중복·고아 레코드가 없는지 읽기 전용 사전 검사를 하고, 동시 승인·취소 경쟁을 포함한 에뮬레이터/통합 테스트와 실제 두 기기 TV 갱신 확인을 통과해야 배포 판단을 다시 한다.
