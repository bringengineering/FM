# CRM 단건 계약·수익·고객 메모 설계

## 목표

BRING CRM에서 예초·청소·도배·폐기물 처리처럼 한 번 수행하는 작업을 단건 계약으로 등록하고, 고객에게 받을 금액과 업체에 지급할 비용을 분리해 수익과 입금 상태를 관리한다. 고객 정보 수정 화면에는 요청 내용과 별개인 개인 메모를 항상 보이는 기본 항목으로 제공한다.

## 데이터 모델

### 단건 계약

기존 `contracts` 컬렉션을 사용하며 `billingCycle: "건별"`로 구분한다. 단건 계약에는 기존 고객·건물·계약 필드와 함께 다음 값을 저장한다.

- `workDate`: 실제 작업일 또는 예정 작업일
- `paymentDueDate`: 고객 입금 예정일
- `amount`: 고객에게 받을 금액
- `vendorCost`: 업체 지급액 또는 직접 작업비
- `grossProfit`: `amount - vendorCost`로 계산한 수익
- `collectionStatus`: `입금 예정`, `입금 완료`
- `vendorPaymentStatus`: `지급 예정`, `지급 완료`
- `serviceRecordId`: 연결된 작업 기록 ID

저장 시 `grossProfit`은 입력값을 신뢰하지 않고 금액과 비용으로 다시 계산한다. 음수 금액과 숫자가 아닌 값은 거부한다.

### 작업 기록

기존 `serviceRecords`는 현장 작업 사실과 증빙을 보관한다. 연결된 단건 계약 ID와 금액 요약을 추가해 작업관리 화면에서도 매출·비용·수익을 확인할 수 있게 한다. 기존 8월 15일 예초 기록은 보존하고 계약 정보만 연결한다.

### 고객 개인 메모

기존 고객의 `notes` 필드를 그대로 사용한다. 별도 마이그레이션이나 중복 필드는 만들지 않는다. 화면 레이블만 `개인 메모·고객 특징`으로 바꾸고 기본 정보 영역에 항상 노출한다.

## 화면 설계

### 입금 캘린더

기존 정기 납부 일정을 유지하면서 상단에 `정기 납부`와 `단건 계약` 구분을 제공한다. 단건 계약 화면에는 다음 내용을 표시한다.

- 작업일과 입금 예정일
- 고객·건물·작업명
- 받을 금액, 업체 지급액, 예상 수익
- 고객 입금 상태와 업체 지급 상태
- 신규 등록·수정·삭제 동작

단건 계약의 고객 입금 예정일은 월별 캘린더에도 표시한다. 업체 지급은 고객 입금으로 오인되지 않도록 별도 상태로만 표시한다.

### 고객 정보 수정

`현재 어떤 요청이 있나요?` 바로 아래에 `개인 메모·고객 특징` 입력란을 배치한다. 기존 접힌 `고객 추가 정보` 안의 `고객 메모`는 제거해 같은 값을 두 곳에서 수정하는 문제를 막는다.

## 저장과 동기화

단건 계약과 고객 메모는 기존 CRM 공용 저장 경로를 사용한다. 월별 입금 캘린더는 계약에서 단건 입금 일정을 읽어 표시하므로 같은 정보를 별도 컬렉션에 이중 저장하지 않는다. 오프라인 저장 후 재연결될 때도 기존 CRM 동기화 절차를 따른다.

## 오류 처리

- 고객 또는 건물이 삭제되었으면 저장 전 다시 선택하도록 안내한다.
- 입금액·비용이 유효하지 않으면 저장하지 않고 해당 입력란에 오류를 표시한다.
- 서버 저장 실패 시 화면에 성공 상태를 표시하지 않으며 입력값을 유지한다.
- 동일한 계약 ID의 재시도는 새 계약을 중복 생성하지 않고 기존 항목을 갱신한다.

## 검증

- 단건 계약 생성·수정·삭제 및 수익 자동 계산 테스트
- 정기 납부 일정이 기존과 동일하게 표시되는 회귀 테스트
- 단건 입금 예정일의 월별 필터·표시 테스트
- 고객 `notes` 값의 편집·저장·재조회 테스트
- 기존 예초 작업 기록과 단건 계약 연결 테스트
- 전체 데스크톱 CRM 테스트, 스모크 테스트, 자동 업데이트 빌드 검증

## 제외 범위

- 회계 세금계산서 발행
- 업체 송금 자동 실행
- 은행 거래의 비용 자동 매칭
- Functions 또는 Hosting 배포
