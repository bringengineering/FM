# BRING CRM 중심 현장 업무 통합 설계

상태: 대표 검토본

작성일: 2026-08-14

대상 기준: BRING CRM 1.7.0, 현재 BRING FIELD 운영 소스

## 1. 한 문장 결론

BRING CRM을 회사의 단일 운영 본체로 두고, BRING FIELD는 별도 플랫폼이 아니라 CRM 건물·호실·공실에서 실행되는 ‘현장 업무’ 기능으로 재구성한다.

휴대전화에서는 촬영과 업로드에 최적화된 BRING FIELD를 계속 사용하되, 데스크톱 CRM 안에서는 CRM의 메뉴·디자인·건물 ID·담당자·업무 흐름을 그대로 따른다.

## 2. 이 설계가 해결할 문제

현재 FIELD는 CRM 안에 표시되지만 실제로는 별도 웹앱 전체를 끼워 넣은 구조다.

- CRM 사이드바 안에 FIELD 사이드바와 상단바가 다시 나타난다.
- FIELD 홈의 관리 건수와 오늘 할 일은 실제 데이터가 아니라 예시값이다.
- CRM 건물과 FIELD 건물이 서로 다른 ID로 중복 생성된다.
- CRM에서 건물·호실을 보고 FIELD를 열어도 다시 대상을 찾아야 한다.
- 촬영 완료가 곧 광고 승인으로 처리되는 등 실제 업무 통제와 맞지 않는다.
- 주소 중복확인, 좌표, 업로드 권한, 내장 로그인, Drive 연결에 실제 운영을 막을 수 있는 문제가 있다.

이번 개편의 목표는 단순한 외형 변경이 아니다. 대표가 CRM 한 곳에서 사업 구조를 보고, 직원은 배정된 현장 업무를 실행하고, 완료 증거가 다시 CRM 영업·공실 단계로 돌아오게 만드는 것이다.

## 3. 확정 제품 원칙

### 3.1 CRM이 단일 원장이다

다음 정보는 CRM만 원본으로 가진다.

- 고객·건물주
- 건물 기본정보와 주소
- 호실과 공실·퇴실예정 정보
- 임대조건
- 관리계약
- 영업 대상과 영업 단계
- 민원·청소·수리 케이스
- 업체와 견적
- 담당자와 다음 행동
- 보안·출입정보의 관리 위치

FIELD가 같은 정보를 별도 원장으로 다시 만들지 않는다.

### 3.2 FIELD는 현장 실행과 증거를 담당한다

다음 기능은 FIELD의 강점이므로 유지한다.

- 모바일 구역별 촬영 가이드
- 필수 사진·영상 검증
- 촬영 중단 후 이어하기
- 오프라인 보관과 재업로드
- 사진 교체·제외·재시도
- 대표사진 선정과 순서 확정
- 당근·네이버용 사진·문구 묶음 생성
- 현장 방문·촬영·업로드·검수 이력
- CRM 관리 건물의 현장 지도

### 3.3 직원 입력은 한 번만 한다

건물·호실·임대조건은 CRM에서 선택한다. FIELD에서는 현장에서 새로 확인한 내용, 사진, 영상, 체크 결과만 입력한다.

### 3.4 자동 단계 상승은 증거가 있을 때만 한다

촬영 완료, 광고 검수 완료, 광고자료 완성, 실제 광고 게시를 서로 다른 사건으로 기록한다.

- 촬영자가 필수컷을 채웠다고 광고가 자동 승인되지 않는다.
- 광고자료가 완성됐다고 실제 광고가 게시된 것으로 보지 않는다.
- CRM의 광고 게시 단계는 게시 채널과 게시 URL 또는 확인 증거가 있을 때만 올라간다.

### 3.5 기존 데이터는 지우거나 추측해서 합치지 않는다

기존 FIELD 건물은 관리번호와 정규화된 주소로 CRM 후보를 제안하되, 담당자가 확인한 연결만 확정한다. 애매한 항목은 미연결 상태로 남긴다.

## 4. 채택한 제품 형태

검토한 세 방향 중 ‘CRM 적응형 FIELD’를 채택한다.

### 채택안: CRM 적응형 FIELD

- 데스크톱: CRM 셸 안에서 CRM형 현장 업무 화면을 사용한다.
- 모바일: 현재 PWA의 촬영·오프라인 강점을 살린 독립 실행 화면을 사용한다.
- 데이터: CRM ID를 기준으로 FIELD 실행 기록을 연결한다.
- 서버: 현장 상태 요약과 증거만 CRM으로 안전하게 되돌린다.

데스크톱 구현은 기존 Electron WebContentsView를 완전히 버리지 않는다. 대신 CRM이 현장 업무를 정식 currentView로 관리하고, 그 콘텐츠 영역 안에 FIELD React 앱의 content-only 모드를 표시한다. FIELD React 앱이 오늘 작업·지도·촬영·광고 준비를 한 번만 구현하므로 데스크톱과 모바일의 업무 규칙이 갈라지지 않는다. Electron은 CRM 메뉴·상단바·실제 화면 크기·딥링크·안전한 외부 링크·종료 경고만 담당한다.

### 채택하지 않은 안

- 외형만 CRM처럼 변경: 이중 장부와 가짜 현황, 재검색 문제가 남는다.
- FIELD 전체를 Electron CRM 코드로 재작성: 모바일 촬영·오프라인 기능을 훼손하고 변경 위험이 너무 크다.

## 5. 정보구조와 메뉴

### 5.1 CRM 왼쪽 메뉴

기존 BRING FIELD 메뉴를 다음처럼 바꾼다.

- 주 메뉴: 현장 업무
- 보조 브랜드: BRING FIELD

현장 업무는 다른 CRM 메뉴와 같은 선택 상태, 제목, 상단 영역, 권한 규칙을 사용한다. 별도 FIELD 사이드바와 상단바는 CRM 내장 모드에서 표시하지 않는다.

### 5.2 현장 업무 메인 화면

첫 화면은 대표와 팀이 실제로 판단할 수 있는 정보만 표시한다.

상단 핵심 지표:

- 오늘 방문
- 촬영 대기
- 업로드 실패
- 광고 검수 대기
- 미배정
- 기한 초과
- 관리자 조치 필요

모든 지표 카드는 숫자만 보여주지 않고 누르면 해당 업무 목록으로 내려간다.

업무 필터:

- 내 업무 / 팀 전체
- 오늘 / 이번 주 / 전체
- 담당자
- 업무 유형
- 진행상태

콘텐츠 탭:

1. 오늘 작업
2. 현장 지도
3. 촬영·업로드
4. 광고 준비

‘홈’, ‘건물’, ‘패키지’처럼 CRM과 겹치거나 뜻이 모호한 명칭은 사용하지 않는다.

### 5.3 오늘 작업

카드나 표의 각 행에 다음을 표시한다.

- 건물명·주소
- 호실
- 업무 유형: 공실촬영, 퇴실확인, 정기점검, 민원확인, 청소 전후촬영 등
- 예정일·긴급도
- 담당자
- 현재 상태
- 업로드 상태
- 한 개의 다음 행동 버튼

대표 화면은 전체 병목을 보여주고, 직원 모바일 화면은 자신에게 배정된 업무가 기본값이다.

미배정 업무는 admin과 member가 함께 볼 수 있는 ‘미배정 업무함’에 표시한다. 팀원은 ‘내가 맡기’로 업무를 가져갈 수 있으며, 서버 트랜잭션으로 한 사람만 성공하게 한다. 일정 변경·담당 변경·취소는 기본 버튼 옆 더보기 메뉴에 두고 반드시 사유를 남긴다.

### 5.4 현장 지도

CRM에 연결된 건물만 표시한다.

- 공실 있음
- 촬영 필요
- 방문 예정
- 업로드 실패
- 광고 검수 대기

기존 유지보수 업체 지도는 FIELD에서 제거하고 CRM의 업체·협력사 기능을 사용한다.

미연결 현장 후보는 일반 관리지도에 섞지 않는다. admin의 ‘연결 대기’ 보조 레이어에서만 임시 위치와 접수사진을 확인하고, 연결 확정 전에는 관리 건물 수에 포함하지 않는다.

### 5.5 촬영·업로드

건물과 호실 기준으로 방문·촬영 세션과 미디어 상태를 확인한다.

- 촬영 예정
- 촬영 중
- 기기 저장 대기
- 업로드 중
- 업로드 실패
- 업로드 완료
- 검수 반려
- 검수 완료

영구 삭제는 제공하지 않는다. 잘못된 기록은 사유를 남기고 제외 또는 보관한다.

### 5.6 광고 준비

공실 호실별로 다음 흐름을 보여준다.

촬영 완료 → 검수 대기 → 사진 확정 → 문구 확정 → 광고자료 완성 → 게시 확인

당근과 네이버는 실제 게시 전까지 ‘광고자료 준비’로만 표시한다. 실제 게시 시 CRM 영업 화면에서 채널과 URL 또는 증거를 저장하고 광고 게시 단계가 확정된다.

채널별 상태는 각각 관리한다. 예를 들어 당근은 게시 완료이고 네이버는 아직 준비 중일 수 있다. 임대조건이나 확정 사진이 바뀌면 기존 광고자료 버전은 ‘정보 변경·갱신 필요’가 되며, 임대 완료나 광고 철회 시 ‘게시물 내리기’ 업무를 만든다.

## 6. 핵심 사용자 흐름

### 6.1 공실 영업에서 촬영까지

1. 대표나 팀원이 영업 CRM에서 건물과 공실 호실을 확인한다.
2. ‘현장 촬영 요청’을 누른다.
3. 건물·호실·임대조건·요청 목적이 입력된 현장 업무가 생성된다.
4. 같은 건물·같은 방문일의 여러 호실은 한 방문 묶음으로 합치되, 호실별 업무와 상태는 독립적으로 만든다.
5. 담당 직원 모바일의 오늘 작업에 나타난다. 미배정이면 팀원이 미배정 업무함에서 원자적으로 가져간다.
6. 직원은 출발 전 일정·연락 담당·출입 준비·기기 저장공간·카메라 권한을 확인한다.
7. 직원은 대상을 다시 검색하지 않고 촬영을 시작한다.
8. 건물 외관·공용부 사진은 같은 방문의 여러 호실이 공유하고, 실내·임대조건·검수는 호실마다 분리한다.
9. 오프라인이어도 촬영 결과는 기기에 보관된다.
10. 연결이 복구되면 서버를 통해 업로드하고 CRM에 요약 상태가 반영된다.

### 6.2 촬영에서 광고 준비까지

1. 필수컷이 채워지면 촬영 완료가 기록된다.
2. 서버 Storage 확정이 끝난 사진은 검수 대기 상태가 된다. Drive 복제는 별도 진행상태이며 검수를 막지 않는다.
3. 검수 권한자가 제외사진, 대표사진, 순서를 확정한다.
4. 당근·네이버용 자료 묶음을 생성한다.
5. CRM의 해당 공실 호실에 광고자료 링크와 완료시각이 연결된다.
6. 실제 게시 담당자가 게시 채널과 URL을 기록하면 광고 게시 증거가 생성된다.

### 6.3 관리·민원 현장 업무

1. CRM 건물, 업무 또는 민원 케이스에서 현장 방문을 만든다.
2. 업무 유형에 맞는 체크리스트가 열린다.
3. 직원이 확인 결과와 전후 사진을 기록한다.
4. 완료 결과가 원래 CRM 건물 또는 케이스에 연결된다.
5. 추가 수리·청소가 필요하면 기존 CRM의 업체·견적 흐름으로 넘긴다.

### 6.4 현장에서 미등록 건물을 발견한 경우

모바일에서 곧바로 정식 건물 원장을 만들지 않는다.

1. ‘미연결 현장 후보’로 주소, 위치, 외관 사진, 메모를 임시 접수한다.
2. CRM 대표 화면의 연결 대기함에 나타난다.
3. 기존 건물과 연결하거나 CRM에 새 건물을 만든 뒤 확정한다.
4. 확정 전에는 광고 승인이나 관리계약 처리를 할 수 없다.

이 방식은 현장 기동성을 살리면서 중복 건물 생성을 막는다.

### 6.5 배정과 변경

1. 업무 생성 시 담당자를 바로 정하거나 미배정으로 둘 수 있다.
2. 배정된 팀원은 수락하고, 미배정 업무는 admin 또는 member가 ‘내가 맡기’로 가져간다.
3. 같은 업무를 두 명이 동시에 가져가면 서버가 먼저 확정된 한 명만 성공 처리한다.
4. 담당자·일정·우선순위 변경, 회수, 취소에는 사유와 변경자를 남긴다.
5. 신규 배정, 일정 변경, 검수 반려, 기한 초과는 대상 팀원에게 앱 내부 알림과 해당 업무 딥링크를 제공한다.
6. 담당자가 일정 내 수락하지 않거나 부재 처리되면 미배정 업무함으로 회수하고 대표 화면에 표시한다.

### 6.6 출입 준비

현장 카드에는 일반 메모가 아니라 ‘출입 준비’ 영역을 둔다.

- 건물주 또는 현장 연락 담당자에게 전화
- 관리자에게 출입 승인 요청
- 권한 있는 배정자만 시간제 출입정보 열람
- 출발 전 출입 준비 완료 체크

시간제 출입정보는 별도 secureReveal callable이 현재 배정, 활성 작업자, CRM 보안정보 권한, 재배정·취소 여부를 확인한 뒤 60초 메모리 전용 오버레이로 한 번만 보여준다. 열람 작업자표식·시각·대상을 감사로그에 남기고, 화면 닫기·시간 만료·재배정·취소 시 즉시 폐기한다. URL, IPC, FIELD RTDB, 로그, IndexedDB에는 원문 비밀번호를 저장하지 않는다. 오프라인이 예상되면 출발 전에 연락 담당자와 출입 방식을 확인해야 하며, 확인하지 못한 업무는 ‘출입 준비 안 됨’으로 출발 경고를 표시한다.

## 7. 데스크톱과 모바일 화면 규칙

### 7.1 데스크톱 CRM 내장 모드

- CRM 사이드바와 상단바만 보인다.
- FIELD 자체 사이드바·상단바·로그아웃·역할 표시는 숨긴다.
- CRM의 배경, 글꼴, 색상, 카드, 버튼, 표, 상태 배지를 사용한다.
- 현재 메뉴는 ‘현장 업무’로 정확히 선택 표시한다.
- 상단 제목은 ‘현장 업무’, 검색은 건물·호실·업무번호·담당자 범위로 바꾸고, 기본 생성 버튼은 ‘+ 현장 업무’로 바꾼다. viewer에게 생성 버튼을 표시하지 않는다.
- 창 크기를 고정 숫자로 추측하지 않고 CRM 콘텐츠 영역의 실제 위치와 크기를 전달한다.

- FIELD에서 CRM 건물·호실·케이스를 열었다가 돌아오면 원래 탭·필터·선택 업무·스크롤 위치를 복원한다.

## 8. 데이터 소유권과 연결 구조

### 8.1 CRM 원본 데이터

CRM의 기존 고객, 건물, 영업대상, 영업호실, 케이스를 그대로 원본으로 사용한다.

다만 현재 CRM에는 건물 아래에서 오래 유지되는 정식 호실 원장이 없고, salesUnits는 한 번의 공실 영업 사이클에 가깝다. 따라서 다음 두 개를 분리한다.

- buildingUnits: 건물에 실제 존재하는 101호, 102호 같은 안정적인 호실 원장
- salesUnits: 해당 호실에서 발생한 이번 공실·퇴실예정·임대완료 영업 사이클

salesUnits에는 crmBuildingUnitId를 두어 정식 호실을 참조한다. 같은 101호가 나중에 다시 공실이 되면 buildingUnits는 그대로 두고 새 영업 사이클을 만든다. 기존 salesUnits는 확인된 건만 buildingUnits와 연결하고 추측해서 합치지 않는다.

buildingUnits는 기존 CRM 공용 저장소에 들어가므로 오프라인 pending 저장 버전을 올리고 collection-presence 호환 규칙을 적용한다. 구버전 pending 파일에 buildingUnits가 없다는 이유로 서버의 정식 호실을 빈 목록으로 덮어쓰면 안 된다. 같은 buildingId 안에서는 정규화한 호실명이 중복되지 않게 검증하고, 삭제 대신 보관한다.

FIELD에 연결된 buildings, buildingUnits, salesUnits는 일반 shared-store 쓰기만으로 변경하지 않는다.

- Firebase 규칙은 현재 crmCompany/data 상위의 member 전체 쓰기 허용을 제거하고 컬렉션별 규칙으로 내린다. RTDB의 상위 허용은 하위에서 취소할 수 없으므로, 상위 `.write`를 둔 채 linked 레코드만 하위에서 막는 방식은 사용하지 않는다.
- customers, activities 등 기존 컬렉션에는 기존 admin/member 쓰기 의미를 유지하는 하위 규칙을 명시한다.
- 신규 CRM에서 생성·수정하는 buildings, buildingUnits, salesUnits는 모두 commitCanonicalCrmEntity 서버 API만 쓴다.
- 각 레코드에 entityVersion을 둔다.
- 신규 CRM은 expectedVersion을 포함해 commitCanonicalCrmEntity 서버 API로 변경한다.
- 서버는 CRM 접근권한, 부모·자식 관계, FIELD 링크, 보관 상태를 확인하고 한 트랜잭션에서 버전 증가와 감사로그를 남긴다.
- 규칙은 FIELD 링크가 있는 레코드의 직접 삭제와 버전 없는 직접 수정을 거부한다.
- 구 CRM이나 오래된 pending 데이터가 이 레코드를 수정하려 하면 덮어쓰지 않고 ‘최신 CRM 필요’로 실패한다.
- 신규 remote serializer는 서버관리 version·link 필드를 로컬 데이터로 지우지 않는다.

구 CRM 버전의 직접 쓰기를 먼저 종료하고 최소 지원 CRM 버전을 올린 뒤, 세 canonical 컬렉션의 클라이언트 직접 쓰기를 규칙에서 전부 차단한다. 전환 중 구 CRM이 남아 있을 때는 규칙을 성급히 차단하지 않고 새 FIELD 연결과 canonical API를 기능 플래그로 비활성화한다. 즉 ‘FIELD 미연결 레코드만 조건부 직접쓰기’ 같은 영구 예외는 두지 않는다.

commitCanonicalCrmEntity는 Electron용 제한 HTTPS endpoint로 두고 Authorization Bearer의 bring-fm ID token, crmCompany/access, requestId, expectedVersion, 허용 필드와 크기를 검증한다. Electron에서 발급할 수 없는 웹 App Check를 가장하지 않으며, 이 endpoint는 건물·호실의 허용된 변경 외 다른 FIELD 동작을 받지 않는다. 사용자·IP 속도 제한과 서버 감사로그를 적용한다.

기존 건물의 externalRefs에는 확인된 FIELD 관리번호와 FIELD 건물 ID를 추가할 수 있다. 그러나 대용량 촬영기록이나 미디어 목록은 CRM 공용 저장소에 복사하지 않는다.

확장 필드 이름은 externalRefs.fieldBuildingIds와 externalRefs.fieldManagementNumbers로 고정하고, 기존 paymentBuildingIds를 덮어쓰거나 의미를 바꾸지 않는다.

### 8.2 FIELD 운영 데이터

FIELD는 다음 실행 기록을 유지한다.

- 현장 업무
- 방문
- 촬영 세션
- 미디어
- 업로드 작업
- 검수 결과
- 광고자료 묶음
- 감사로그

신규 작업은 fieldPlatform/v2/workItems 아래에서 관리하고, 기존 buildings·units·listings는 호환기간 동안 CRM 원본을 반영하는 서버 관리형 투영으로 사용한다. 즉 FIELD 화면에서 이 사본을 직접 수정해 CRM 원본과 갈라지게 하지 않는다.

한 번의 실제 방문은 fieldPlatform/v2/visits에 두고 여러 workItem을 묶을 수 있게 한다. 방문에는 건물, 일정, 담당자, 출입준비 상태, 공유 외관·공용부 촬영을 두고, 각 호실의 업무·실내 사진·검수·광고 상태는 workItem에 따로 둔다.

초기 업무 유형 jobType은 다음으로 제한한다.

- vacancy_capture: 공실 광고 촬영
- move_out_check: 퇴실 확인
- cleaning_before_after: 입주·퇴실·공용부 청소 전후
- maintenance_inspection: 정기 시설점검
- complaint_check: 민원 현장확인
- repair_before_after: 수리·방수·장판 등 작업 전후

새로 만드는 FIELD 기록에는 가능한 경우 다음 정식 참조를 넣는다.

- crmBuildingId: CRM 건물
- crmBuildingUnitId: CRM 정식 호실
- crmSalesProspectId: CRM 영업 대상 건물
- crmSalesUnitId: CRM 공실 호실
- crmWorkflowCaseId: CRM 민원·수리·청소 케이스
- crmTaskId: CRM 할 일

참조는 서버가 실제 존재와 권한을 확인한 뒤 저장한다. 주소 문자열만으로 자동 확정하지 않는다.

현재 2~5호 건물처럼 아직 관리계약용 CRM building이 없고 영업대상 salesProspect와 salesUnit만 있는 경우도 정식 흐름으로 지원한다. workItem은 crmBuildingId 또는 crmSalesProspectId 중 하나를 필수 부모로 가지며, 영업대상 전용 지도 표시는 ‘임대 영업 현장’으로 구분한다. 나중에 CRM 정식 건물로 전환하면 서버가 링크만 추가하고 기존 jobId, visitId, mediaId, 광고자료 버전은 그대로 유지한다.

visit의 assignedOperatorId·dueDate는 묶인 workItem의 기본 배정과 일정이다. 하나의 미시작 호실만 다른 사람이나 날짜로 바꾸면 서버가 새 visit으로 분리하고 공용부 미디어는 자동 복사하지 않는다. 방문 전체 변경은 모든 미시작 자식 업무를 함께 바꾼다. in_progress 이후에는 방문을 조용히 재배정하지 않고 사유 있는 분리·취소를 사용하며, 이미 촬영한 미디어의 소유 방문은 바꾸지 않는다.

업무 생성 시에는 다음 스냅샷과 버전을 함께 저장한다.

- 건물명·주소
- 호실명
- 보증금·월세·관리비·입주가능일
- CRM 원본 updatedAt과 내용 해시

촬영 원본은 스냅샷 변경과 무관하게 보존한다. 검수 또는 광고자료 생성 전에 서버가 최신 CRM 원본과 비교하고, 값이 달라졌으면 source_stale을 표시한다. 담당자는 ‘최신값으로 갱신’ 또는 ‘현재 스냅샷 유지 사유’를 선택해야 다음 단계로 갈 수 있다.

광고자료는 packageVersion, sourceHash, mediaHash를 가진다. 채널별 게시기록은 channelPublications로 분리하고 not_started, ready, published, update_required, withdrawal_required, withdrawn 상태와 게시 URL·증거·시각을 기록한다.

### 8.3 CRM 현장 요약 데이터

CRM에는 현장 작업을 판단하는 데 필요한 작은 요약만 저장한다.

요약은 crmCompany/fieldSummaries 아래에 두고 서버만 쓴다. 데스크톱 CRM은 이 경로를 조회하되, 기존 crmCompany/data 전체 저장·오프라인 재동기화에 섞지 않는다. 그래야 FIELD 상태가 바뀌는 동안 CRM의 오래된 로컬 저장이 서버 결과를 덮어쓰지 않는다.

- fieldJobId
- 연결된 CRM 건물·호실·케이스
- 업무 유형
- 담당자
- 예정일
- 현재 단계
- 미디어 개수
- 업로드 실패 개수
- 검수 상태
- 광고자료 링크
- 마지막 변경시각

원본 사진과 상세 업로드 상태는 FIELD가 소유한다. CRM은 참조와 업무 상태만 가진다.

### 8.4 연결 인덱스와 서버 쓰기

CRM과 FIELD의 연결은 서버 전용 인덱스로 한 번만 확정한다.

- fieldPlatform/v2/links/crmBuildings/{crmBuildingId}: fieldBuildingId
- fieldPlatform/v2/links/crmBuildingUnits/{crmBuildingUnitId}: fieldUnitId
- fieldPlatform/v2/links/crmSalesUnits/{crmSalesUnitId}: fieldListingId

CRM에서 현장 업무를 만들 때 클라이언트가 FIELD 경로를 직접 수정하지 않는다. createFieldJob 서버 함수가 CRM 접근권한과 건물·호실 관계를 확인하고, FIELD 업무와 CRM 요약을 원자적으로 만든다. FIELD 상태가 바뀌면 서버가 같은 jobId의 CRM 요약을 갱신한다.

### 8.5 버전 2 정식 경로

모든 v2 업무 쓰기는 서버 함수만 수행한다. 일반 클라이언트의 RTDB 직접 쓰기는 거부하고, 사진·영상도 허용된 임시 Storage 경로 업로드 뒤 서버 확정을 거친다.

| projections/map/{entityId} | 서버가 만드는 관리·영업 현장 지도 | markerType·status | 원본에서 재생성 가능 |
| links/{linkType}/{crmId} | 서버 전용 CRM↔FIELD 확정 연결 | CRM ID | 연결 해제도 이력 보존 |
| notifications/{operatorId}/{notificationId} | 서버 전용 앱 내부 알림 | operatorId·readAt | 읽음 후 90일 |
| candidates/{candidateId} | 서버 전용 미연결 현장 후보 | 상태·정규화주소·접수자 | 확정·중복·폐기 결정까지, 이후 보관 |
| requestReceipts/{scope}/{requestId} | 서버 전용 멱등 영수증 | scope·requestId | 완료 후 30일 |
| migrationRuns/{runId} | 서버 전용 dry-run·manifest·체크섬 | migrationVersion·시각 | 릴리스 감사자료로 보존 |

원본 사진 파일은 Firebase Storage의 staging과 finalized 경로, 회사 Drive의 관리 폴더에 두며 RTDB에는 메타데이터와 제한된 접근참조만 저장한다. 최종 개인정보 보존기간은 별도 승인 전까지 자동삭제하지 않고, PoC가 끝나기 전에 대표가 정책을 확정한다.

### 8.6 상태 정의

업무 진행상태 workflowStatus:

- requested
- assigned
- accepted
- in_progress
- evidence_ready
- review_pending
- changes_requested
- approved
- completed
- cancelled

업로드 상태 uploadStatus:

- none
- queued
- uploading
- partial_failure
- failed
- synced

업무 진행과 파일 전송 상태를 한 칸에 섞지 않는다. 예를 들어 현장 증거는 모두 작성됐지만 일부 파일 업로드가 실패한 상태를 workflowStatus=evidence_ready, uploadStatus=partial_failure로 정확히 표현한다. 광고자료 생성과 채널 게시도 별도 packageVersion과 channelPublications 상태로 관리한다.

업무 단계는 서버에서 허용한 순서로만 전환한다. 완료시각과 담당자는 한 번 생성된 뒤 일반 수정으로 덮어쓰지 않는다.

화면에는 내부 코드를 노출하지 않고 각각 ‘요청’, ‘배정’, ‘수락’, ‘진행 중’, ‘증거 작성 완료’, ‘검수 대기’, ‘수정 요청’, ‘승인’, ‘완료’, ‘취소’로 표시한다.

### 8.7 현황 지표 정의

모든 날짜 경계는 Asia/Seoul을 사용하고 보관·취소된 업무는 제외한다.

- 오늘 방문: dueDate가 오늘이고 방문형 업무인 고유 visitId 수
- 촬영 대기: workflowStatus가 requested, assigned, accepted, in_progress인 촬영형 업무 수
- 업로드 실패: uploadStatus가 partial_failure 또는 failed인 업무 수
- 광고 검수 대기: workflowStatus가 review_pending인 공실 광고 업무 수
- 미배정: assignedOperatorId가 없고 완료·취소되지 않은 업무 수
- 기한 초과: dueDate가 오늘보다 이전이고 완료·취소되지 않은 업무 수
- 관리자 조치 필요: Drive 장애, 연결 충돌, source_stale 장기 미확인, 출입 준비 실패 같은 차단상태 수

화면 숫자는 이 정의로 계산된 실제 값만 보여주며, 서버 조회 실패 시 0으로 속이지 않고 ‘집계 확인 필요’로 표시한다.

### 8.8 업무 유형별 정책

모든 업무는 jobPolicyVersion과 checklistId를 저장한다. 과거 업무는 당시 정책으로 판정하고 새 정책 배포가 이미 완료된 업무를 소급 변경하지 않는다.

| vacancy_capture | VACANCY_CAPTURE_V1 · 호실별 내부 필수구역, 하자, 임대조건 스냅샷, 촬영동의 | 수락 → 진행 → 증거완료 → 검수대기 → 승인 → 완료 | 촬영·검수 요약과 광고자료 링크만 연결. 실제 광고 게시 이벤트는 만들지 않음 |

업무 카드의 주 행동은 현재 정책이 계산한다. 예를 들면 미배정은 ‘내가 맡기’, 배정됨은 ‘수락’, 출입 미확인은 ‘출입 준비’, 진행 중은 ‘계속 기록’, 검수대기는 ‘검수’, 반려는 ‘재촬영’으로 한 개만 표시한다.

## 9. 인증과 권한

### 9.1 로그인 경험

- 현재 CRM과 FIELD의 운영 인증 프로젝트는 모두 bring-fm을 사용한다. bring-fm-hj는 이전 CRM 세션 검증과 호환 용도로만 남아 있으므로 신규 구조의 기본 인증 경로로 사용하지 않는다.
- CRM에서 현장 업무를 열 때 추가 로그인 화면을 보여주지 않는다.
- 현재 CRM Firebase 세션을 같은 회사 프로젝트에서 검증한다.
- 현재 운영처럼 회사 공용 CRM 계정 한 개를 유지하고, 별도의 팀원 로그인은 새로 만들지 않는다.
- 각 기기에서 최초 한 번 ‘현재 작업자’를 대표·황우중·김현진 등 활성 팀원 목록에서 선택한다. 이는 비밀번호를 묻는 로그인이 아니라 업무 배정과 표시를 위한 기기 프로필이며 상단에서 언제든 확인할 수 있다.
- 모든 쓰기는 authUid와 operatorId를 함께 저장하고, 서버는 operatorId가 crmCompany/teamProfiles의 활성 팀원인지 확인한다.
- 세션이 없거나 권한이 없으면 CRM 화면 안에서 간단한 연결 오류와 재시도만 표시한다.
- 모바일 독립 접속은 기존 회사 Google 계정을 유지한 뒤 같은 작업자 프로필을 선택한다.

기본 연결은 현재 CRM 로그인 창과 FIELD WebContentsView가 같은 origin과 `persist:bring-field` 파티션을 사용해 Firebase 웹 세션을 공유하는 방식이다. 최초 로그인, 앱 재시작, 사용자 변경, 파티션 유지 여부를 자동 테스트한다.

파티션 세션이 없어졌지만 CRM REST 세션은 유효한 예외상황에서는 일회용 자동 복구를 사용한다.

1. CRM 메인 프로세스가 최신 CRM ID token으로 60초·1회용 코드를 요청한다.
2. 서버는 bring-fm 토큰, crmCompany/access, 활성 회사 계정을 확인한다.
3. FIELD가 코드를 교환해 같은 회사 UID의 세션을 만들고 즉시 URL에서 코드를 지운다.
4. FIELD custom claim이 없으면 서버가 CRM 접근정보를 기준으로 권한을 프로비저닝하고 토큰을 한 번 새로고침한다.
5. 코드 원문·ID token·custom token은 로그나 영구 저장소에 남기지 않는다.

현재 handoff의 bring-fm-hj 전용 검증기는 bring-fm 동일 프로젝트 검증으로 교체하고, 이전 설치본 호환 테스트 뒤 구 검증기를 제거한다. 이 자동 연결은 사용자에게 새 로그인 화면이나 별도 비밀번호를 요구하지 않는다.

공용 인증을 사용하는 동안 operatorId는 암호학적으로 개인을 증명하는 수단이 아니다. 대신 현재 3인 팀의 ‘모두 사용 가능’ 운영을 유지하면서 배정과 이력을 구분하는 표식으로 사용한다. 나중에 개인별 계정이 필요해지면 teamProfile에 Firebase UID를 연결하는 방식으로 데이터 구조를 바꾸지 않고 강화할 수 있다.

crmCompany/teamProfiles/{operatorId}에는 displayName, active, sortOrder만 두고 비밀번호나 개인 토큰을 넣지 않는다. 작업자 추가·비활성화는 CRM 설정에서 서버 API로 처리한다. 선택값은 기기에 비밀이 아닌 환경설정으로 저장하며, 작업자 전환 자체도 감사로그에 남긴다.

직원 인증과 회사 Drive 자격증명은 완전히 분리한다. 모바일이나 CRM 로그인 계정이 Google Drive OAuth 토큰을 제공하지 않으며, Drive는 서버에 설정된 회사 자격증명으로만 처리한다.

### 9.2 권한 매핑

- CRM admin: 전체 현장 업무, 배정, 촬영, 다른 사람 촬영의 검수, 연결 확정, 설정
- CRM member: 현장 업무 생성·수행·배정, 촬영·업로드, 다른 사람 촬영의 검수
- CRM viewer: 조회만 가능

현재 3인 팀은 모두 실제 업무를 수행할 수 있다. 별도의 FIELD 전용 역할을 다시 고르게 하지 않는다. 다만 capturedByOperatorId와 reviewedByOperatorId는 달라야 한다. 대표의 긴급 자기승인이 꼭 필요한 경우에만 admin 접근 세션에서 사유를 적어 예외 승인하며 감사로그에 별도 표시한다.

공용 계정을 유지하는 동안 이 분리는 보안상 개인을 증명하는 통제가 아니라 팀 운영 표식이다. UI와 서버는 같은 operatorId의 일반 검수를 막지만, 공용 계정을 아는 사람이 다른 작업자 표식을 선택할 가능성까지 막을 수는 없다. 따라서 ‘개인별 권한’과 ‘부인할 수 없는 개인 감사기록’은 이번 PoC의 완료기준으로 주장하지 않는다.

이번 버전의 확정 기준은 자동승인이 없고, 모든 검수에 검수 작업자 표식 또는 대표의 사유 있는 예외가 남는 것이다. 추후 강한 책임분리가 필요해지면 teamProfile에 개인 Firebase UID 또는 승인 기기 자격증명을 연결해 같은 데이터 구조를 강화한다.

기존 FIELD의 admin, staff, reviewer 역할은 전환기간에만 읽어 CRM 역할로 매핑한다. 최종 권한 원본은 crmCompany/access이며, 서버가 FIELD용 권한표시와 Firebase custom claim을 동기화한다.

### 9.3 민감정보

- 출입 비밀번호, 키 보관 위치, 도어락 정보는 일반 메모에 저장하지 않는다.
- CRM의 제한형 보안정보 기능에서만 관리한다.
- FIELD 영구 데이터와 오프라인 저장소에는 실제 비밀번호 대신 ‘접근권한 확인됨’ 같은 참조 상태만 둔다. 시간제 열람 때만 서버 응답을 메모리에 표시하고 화면을 닫거나 제한시간이 지나면 즉시 폐기한다.
- 토큰, OAuth 정보, 연결코드, 비밀번호는 URL·로그·감사기록에 남기지 않는다.

## 10. CRM과 FIELD 통신 경계

데스크톱 내장 화면은 필요한 메시지만 주고받는 좁은 통신 규칙을 사용한다. 모든 메시지는 `{ protocolVersion, type, requestId, payload }` 봉투를 사용하며 최대 32KB다.

| 메시지 | 방향 | 응답과 제한 |
|---|---|---|
| field.ready | FIELD→CRM | 지원 protocolVersion, FIELD build, 현재 route를 전달 |
| field.navigate | CRM→FIELD | 허용 route와 CRM entity ID만 전달하고 field.ack 응답 |
| field.command | CRM→FIELD | createJob·assign·review 같은 허용 command, requestId 필수, field.commandResult 응답 |
| field.routeChanged | FIELD→CRM | 허용 route·선택 jobId만 전달, CRM이 복귀 상태 저장 |
| field.pendingUploads | FIELD→CRM | 개수와 위험등급만 전달, 파일명·사진은 전달 금지 |
| field.openCrmEntity | FIELD→CRM | 허용 entityType과 ID를 검증하고 CRM 화면 이동 |
| field.openExternal | FIELD→CRM | https와 호스트 정책을 검사한 뒤 OS 브라우저로 열기 |
| crm.logoutCheck | CRM→FIELD | pending 여부를 field.logoutDecision으로 응답 |

requestId는 요청·응답을 연결하고 같은 command 재전송의 중복 실행을 막는다. 기본 시간제한은 10초이며, 사용자가 취소하거나 다른 화면으로 이동하면 cancel 메시지를 보낸다. main process는 메시지를 보낸 webContents ID, 현재 frame URL의 정확한 origin, protocolVersion을 확인한다. route·command·entityType·ID 형식·문자열 길이는 허용목록으로 검증한다.

외부 링크는 drive.google.com, docs.google.com, map.naver.com, land.naver.com, new.land.naver.com, m.land.naver.com, daangn.com, www.daangn.com, bring-fm.web.app만 바로 연다. 다른 https 호스트는 전체 호스트명을 보여주고 사용자가 확인해야 하며, http·file·javascript 등은 차단한다.

인증 토큰, 연결코드, 원본 사진, 출입 비밀번호는 이 통신으로 보내지 않는다.

Electron CRM은 현재 Firebase REST ID token만 사용하고 FIELD 서버 함수는 App Check를 요구하므로, 데스크톱에서 createFieldJob을 직접 호출하지 않는다. CRM이 ‘현장 업무 생성’ 요청과 CRM 참조 ID를 FIELD WebContentsView에 전달하면, FIELD React 앱이 자신의 Firebase SDK 세션과 App Check로 createFieldJob callable을 호출하고 결과 jobId만 CRM에 돌려준다. 같은 방식으로 배정·상태변경·검수도 서버 함수를 거친다.

FIELD 화면이 준비되지 않았거나 인증·App Check가 실패하면 CRM은 작업이 만들어진 것처럼 표시하지 않는다. 요청 ID로 안전하게 재시도하고 서버 영수증을 받은 뒤에만 성공 처리한다.

운영 배포 전 NEXT_PUBLIC_FIREBASE_APPCHECK_SITE_KEY와 reCAPTCHA Enterprise의 bring-fm.web.app 허용 도메인을 확인한다. 실제 Electron WebContentsView에서 App Check 토큰 발급·갱신과 v2 callable 호출을 시험한다. createDesktopFieldHandoff와 exchangeDesktopFieldHandoff는 최초 세션 연결을 위한 예외로 App Check를 요구하지 않되, CRM 토큰 검증, 60초 TTL, 1회 사용, IP·사용자 속도 제한을 유지한다. commitCanonicalCrmEntity는 8.1의 제한 Electron endpoint 정책을 따른다. 그 밖의 v2 업무 callable은 Auth와 App Check가 모두 없으면 거부한다.

## 11. 반드시 선행해서 고칠 정확성 문제

### 11.1 주소와 중복 확인

현재 고정 원주 좌표를 반환하는 임시 주소확인을 제거한다.

- 실제 주소 검색 또는 검증된 주소 입력을 사용한다.
- 도로명 주소를 정규화한다.
- CRM 건물과 FIELD 연결기록을 함께 조회한다.
- GPS를 사용할 수 있으면 현장 위치와 주소 좌표의 거리 경고를 제공한다.
- 좌표를 확인하지 못하면 ‘좌표 미확인’으로 저장하고 임의 좌표를 넣지 않는다.

### 11.2 서버 중심 업로드

클라이언트가 전체 미디어 경로를 읽거나 Drive OAuth 토큰을 직접 가져야 하는 경로를 운영 기본값에서 제거한다.

- 업로드 확정, Drive 동기화, 광고 후보 조회는 Cloud Function 또는 제한된 서버 API를 사용한다.
- 목록은 담당자·업무·촬영세션 기준으로 제한 조회한다.
- 서버 Drive 연결이 끊기면 직원에게 로그인 요구를 하지 않고, 관리자 조치 필요 상태와 로컬 재시도 대기열을 표시한다.

### 11.3 다중 호실

여러 공실 호실을 선택하면 각 호실마다 독립적인 현장 업무·매물 연결·촬영 상태를 만든다. 첫 번째 호실 하나에만 매물이 생기는 기존 동작을 금지한다.

### 11.4 촬영과 승인 분리

필수컷 완료는 evidence_ready까지만 만든다. 필요한 파일이 서버 Storage의 finalized 경로에 확정되면 review_pending으로 전환한다. Drive 복제는 비차단 outbox로 계속되며 실패 시 관리자 조치가 표시되지만 사진 검수를 막지 않는다. advertisingApproved, reviewedByOperatorId, 최종 승인시각은 별도 검수 행동에서만 생성한다. 공용 로그인에서는 검수자 표식 분리가 운영 통제임을 화면에 명시한다.

### 11.5 배정 범위

직원 모바일의 ‘내 업무’는 실제 배정된 업무만 조회한다. 팀 전체 조회는 권한이 있는 역할에만 제공한다. 클라이언트가 전체 건물·호실·미디어를 내려받아 필터링하지 않는다.

### 11.6 Firebase 프로젝트와 트리거

현재 일부 Drive·지도 데이터베이스 트리거가 이전 bring-fm-hj 데이터베이스 인스턴스를 명시한다. 신규 경로를 만들기 전에 다음을 배포 차단 조건으로 확인한다.

- 운영 원본 데이터가 실제로 어느 프로젝트·리전에 있는지 읽기 전용 집계
- 모든 FIELD 함수와 트리거의 프로젝트·데이터베이스·리전 목록
- bring-fm 신규 경로를 가리키는 트리거의 에뮬레이터 테스트
- 구 트리거와 신 트리거의 중복 실행 방지키
- 운영 한 건의 Drive·지도·요약 갱신 확인

bring-fm-hj는 호환 검증 외 신규 FIELD 쓰기 대상으로 사용하지 않는다. 구 트리거 종료 전에 미처리 작업이 0인지 확인한다.

### 11.7 버전 2 경로와 구버전 종료

기존 앱은 fieldPlatform/buildings, units, listings에 직접 쓰고 전체 목록을 읽으므로 같은 경로를 한 번에 서버 전용으로 바꾸지 않는다.

- 신규 서버 관리 데이터는 8.5의 fieldPlatform/v2 정식 경로에만 둔다.
- 신규 FIELD 앱은 v2만 쓰고, 기존 자료는 연결 어댑터를 통해 읽기 전용으로 보여준다.
- 구버전 앱의 기존 경로 읽기·쓰기는 짧은 호환기간 동안 유지한다.
- 서비스워커 버전을 올리고, 온라인 사용자는 새 버전으로 전환되기 전 신규 업무를 시작하지 못하게 한다.
- 서버는 활성 클라이언트 heartbeat에 buildVersion, 마지막 동기화시각, queueCount, queueAcknowledgedAt을 기록한다.
- 모든 최근 활성 기기가 최소 지원 버전이고 queueCount=0을 확인한 뒤 cutoverAt을 공지하고 구 경로의 신규 등록을 동결한다.
- cutoverAt까지의 1차 backfill 뒤 구 경로의 highWaterMark를 기록하고, 동결 후 delta를 다시 스캔한다.
- 원본·v2의 건수, 키 목록 hash, 관계 오류, Storage·Drive 객체 표본을 비교한 뒤 구 직접 쓰기를 차단한다.
- 이후 구 buildings·units·listings는 보관용 읽기 전용으로 남긴다.

신규 앱과 구 앱이 같은 업무를 양쪽 경로에 동시에 쓰는 dual-write는 사용하지 않는다. 마이그레이션은 migrationVersion, sourceKey, sourceUpdatedAt을 멱등키로 사용하고, runId별 highWaterMark·재개점·성공·실패 영수증을 저장한다. 실패하면 마지막 성공 영수증부터 재실행하며, 검증이 맞지 않으면 동결을 해제하지 않고 구 화면을 읽기 전용 안전모드로 유지한다.

### 11.8 CRM 참조 보존

FIELD 링크, 공실 영업, 케이스, 입금기록이 연결된 CRM 건물과 호실은 영구 삭제할 수 없다. CRM UI에서는 보관만 제공하고, 보관 시 신규 현장 업무 생성을 막되 과거 사진·요약·감사이력은 계속 조회한다.

기존 코드에 물리 삭제 경로가 남아 있으면 링크 존재 여부를 확인해 차단하고 테스트한다. 외부 조작 등으로 참조가 사라진 경우 FIELD 원본과 스냅샷을 보존한 채 crm_reference_missing 관리자 조치 상태를 만든다.

### 11.9 공개 레거시 경로

같은 데이터베이스의 workflow, caseSettings, cases, signage에 익명 읽기·쓰기가 남아 있으므로 신규 FIELD 정보는 절대 이 경로에 저장하지 않는다. v2 운영 전 다음 순서로 정리한다.

1. 운영에서 각 공개 경로를 읽고 쓰는 앱과 자동화를 목록화한다.
2. 필요한 데이터를 인증된 crmCompany 경로로 옮긴다.
3. 운영 리허설과 되돌리기 자료를 만든다.
4. 익명 읽기·쓰기를 차단한다.
5. 비로그인 접근 거부와 기존 인증 업무의 정상 동작을 규칙 에뮬레이터와 운영 표본으로 확인한다.

공개 경로 차단이 다른 레거시 운영을 깨는 경우 FIELD v2 출시는 인증 전용 경로로 먼저 진행할 수 있지만, 실제 고객·건물주 연락처나 출입정보를 공개 경로에 복사하는 일은 허용하지 않는다.

## 12. 오류·오프라인 처리

### 12.1 촬영 중 네트워크 단절

- 촬영 시작 전에 카메라·사진첩 권한, 예상 저장공간, 현재 오프라인 준비상태를 확인한다.
- 원본을 IndexedDB에 먼저 보관하되, 브라우저 저장공간 부족·사용자 데이터 삭제·iOS 백그라운드 중단 가능성을 명확히 안내한다.
- 파일별 상태를 queued, uploading, objectStored, finalizing, synced, failed로 기록한다.
- 같은 요청을 다시 보내도 중복 미디어가 생기지 않도록 requestId를 사용한다.
- 앱을 닫거나 로그아웃하려 할 때 미완료 개수와 위험을 알린다.
- 첫 접속부터 오프라인이면 이미 기기에 내려받아 검증된 배정 업무만 열고, 새 업무 생성·출입정보 열람·CRM 최신값 확정은 막는다.
- 모바일 운영체제가 백그라운드 전송을 멈출 수 있으므로 ‘앱을 다시 열면 업로드가 계속됩니다’라는 실제 동작에 맞는 문구를 사용한다.

### 12.2 업로드 실패

- 실패 파일 수, 마지막 오류, 재시도 가능 여부를 표시한다.
- 자동 재시도는 제한된 횟수와 지수형 대기시간을 사용한다.
- 파일 크기·형식 오류는 자동 재시도하지 않고 사용자가 교체하도록 한다.
- 서버·Drive 일시 오류는 로컬 원본을 보존한다.

오류 카드에는 기술 코드 대신 원본 보존 여부, 해결 담당자, 다음 행동을 표시한다. 예를 들어 파일 손상은 촬영 담당자의 ‘파일 교체’, Drive 연결 끊김은 대표의 ‘관리자 설정 확인’, CRM 링크 충돌은 관리자의 ‘연결 검토’로 구분하고 해당 사람에게만 알림을 보낸다.

### 12.3 연결되지 않은 CRM 참조

- 삭제되거나 보관된 건물·호실에 새 현장 업무를 만들지 않는다.
- 작업 중 CRM 대상이 보관되면 업로드는 보존하되 완료 연결을 관리자 확인 대기로 둔다.
- 다른 건물의 호실이나 케이스를 교차 연결하는 요청은 서버가 거부한다.

### 12.4 버전 불일치

CRM과 FIELD가 지원하는 통신 버전을 교환한다. 호환되지 않으면 빈 화면 대신 ‘업데이트 필요’와 안전한 재시도 안내를 표시한다.

### 12.5 사진 개인정보와 공개 범위

미디어는 내부 증거용과 광고 사용 가능을 구분한다. 검수자는 얼굴, 차량번호, 우편물, 기존 세입자 물품, 계약서, 도어락·열쇠 정보가 보이는지 확인하고 광고 사용 제외, 재촬영 또는 가림 필요로 표시한다.

광고자료에는 advertisingEligible=true로 승인된 미디어만 들어간다. 원본 Storage와 Drive 링크는 공개 URL로 만들지 않고 인증된 일시 접근 링크만 사용한다. 광고 게시용 내보내기 파일도 생성자·시각·대상 호실·자료 버전을 기록한다.

## 13. 기존 데이터 연결 계획

마이그레이션은 복사·삭제가 아니라 연결 작업이다.

### 13.1 사전 조사

- 기존 FIELD 건물·호실·매물·방문·촬영세션·미디어뿐 아니라 ownerNotes, managementContractRequests, assignments, secureAccess, adPackages, checklistSubmissions, auditLogs, driveSyncJobs, 초안·영수증을 읽기 전용으로 집계한다.
- CRM 건물·영업호실과 후보 관계를 만든다.
- 각 루트를 CRM 이관, 연결 보존, 읽기전용 보관, 자격증명 회전 후 폐기로 분류한다.
- 파일과 Drive 링크가 실제 존재하는지 표본 검증한다.
- runId, migrationVersion, 시작·완료시각, 원본 건수, key 목록 hash, 관계 오류, Drive 존재 결과를 manifest로 남기고 dry-run 산출물을 릴리스 감사자료와 함께 보존한다.

### 13.2 연결 후보 생성

우선순위는 다음과 같다.

1. 이미 사람이 확인해 저장한 외부 참조
2. 동일 관리번호
3. 완전히 일치하는 정규화 주소와 건물명
4. 주소는 같고 이름이 다른 후보

1만 검증 후 자동 승계할 수 있다. 2~4는 모두 연결 제안일 뿐이며 사람이 확정한다. 어떤 단계든 한 CRM 항목 또는 FIELD 항목에 복수 후보가 생기면 자동 처리를 중단한다.

### 13.3 검토 화면

대표 또는 관리자가 다음 중 하나를 선택한다.

- 기존 CRM 건물에 연결
- CRM에 새 건물 생성 후 연결
- 중복 FIELD 기록으로 보관
- 판단 보류

확정 작업은 감사로그와 이전 참조값을 남기며 되돌릴 수 있어야 한다.

### 13.4 전환 이후

- 신규 정식 건물은 CRM에서만 생성한다.
- FIELD의 기존 건물 등록 화면은 미연결 현장 후보 접수로 전환한다.
- 연결되지 않은 기존 데이터는 읽기 전용으로 유지한다.
- 데이터 삭제는 별도 승인 작업으로 분리한다.

## 14. 구현 단계

### 단계 1: 안전 기반과 버전 2 서버

- 운영 프로젝트·트리거·공개경로·기존 데이터 읽기 전용 감사
- canonical CRM API를 쓰는 CRM 버전을 먼저 배포하고 최소 지원 버전 상향
- 구 CRM 직접 쓰기 종료 후 crmCompany/data 컬렉션별 규칙과 canonical 직접 쓰기 차단
- fieldPlatform/v2와 서버 함수·규칙·멱등 영수증 구축
- 일회용 자동 세션 연결과 작업자 프로필
- Drive·미디어 권한 차단 문제 수정
- 주소 고정좌표 제거

### 단계 2: CRM 셸과 단일 원장 연결

- 현장 업무를 진짜 CRM 메뉴 상태로 편입
- 내장 FIELD의 중복 사이드바·상단바 제거
- 실제 크기 기반 배치와 딥링크
- 고정 예시 홈을 실제 현황으로 교체
- buildingUnits와 관련 참조 모델 추가
- crmBuildingId와 관련 참조 모델 추가
- CRM에서 현장 업무 생성
- 모바일 내 업무 조회
- FIELD 상태 요약을 CRM에 반영
- 다중 호실과 실제 배정 처리

## 16. 배포와 되돌리기

### 16.1 배포 순서

서버 전용 fieldPlatform/v2/config/release에는 enabled, enabledOperatorIds, protocolVersion, minFieldBuild, minDesktopVersion, maxDesktopVersion, safeMode를 둔다. FIELD와 CRM은 매번 v2 쓰기 전에 이 설정을 평가하고, 플래그가 꺼졌거나 버전 범위를 벗어나면 신규 쓰기를 하지 않는다.

1. 새 서버 API와 규칙을 기존 앱과 호환되게 먼저 배포한다.
2. v2를 읽을 수 있고 진행 중 업로드를 재개할 수 있는 안전모드를 FIELD에 먼저 배포한다.
3. 새 FIELD를 v2 기능 플래그가 꺼진 상태로 배포한다.
4. 운영 계정으로 자동 세션, App Check, 촬영, Storage 확정, Drive outbox, 검수를 확인한다.
5. CRM 새 버전을 배포한다.
6. 공용 UID 아래 3개 활성 teamProfile에만 기능 플래그를 켠다.
7. 실제 PoC 건물 1개와 공실 1개로 전 과정을 검증한다.
8. 안정 확인 후 cutover 절차로 기존 FIELD 중복 메뉴와 직접 쓰기를 종료한다.

### 16.2 되돌리기와 안전모드

- v2 쓰기 전에는 플래그를 끄고 이전 내장 화면으로 돌아갈 수 있다.
- 첫 v2 업무가 만들어진 뒤에는 구 legacy 화면으로 되돌리지 않는다. 구 화면은 v2 업무를 모르기 때문에 신규 기록을 숨길 수 있다.
- 장애 시 safeMode를 켜 신규 업무·검수·연결 변경을 막고, v2-aware 안전화면에서 기존 업무 조회, 로컬 업로드 재개, 원본 내보내기만 제공한다.
- 서버는 이미 발급된 v2 requestId와 진행 중 uploadJob을 계속 처리한다. 새 기능은 forward-fix로 복구한다.
- 서버 함수 이전 버전은 protocolVersion 호환 범위 동안 유지하며, 그 기간을 지나면 명시적 업데이트 화면을 보여준다.
- 새 데이터는 기존 필드를 덮어쓰지 않고 추가 참조로 저장한다.
- 배포 전 플래그 off, safeMode, 서버 이전버전, FIELD 현재버전, CRM 이전·현재버전 조합을 호환표로 시험한다.
- 롤백 훈련에서는 이미 생성된 v2 업무가 안전화면에 보이고 업로드가 계속되며 구 화면에 고아로 남지 않는지 확인한다.
- 배포 산출물은 하나의 확정 커밋에서 새 디렉터리로 다시 만든다.
- 자동 업데이트 실설치 검증은 사용자의 명시적 허가 없이 실행하지 않는다.

## 17. 완료 기준

다음 조건이 모두 충족돼야 개편 완료로 본다.

1. CRM에서 현장 업무를 열었을 때 사이드바와 상단바가 각각 하나만 보인다.
2. 이전 메뉴가 선택된 채로 남지 않고 현장 업무가 현재 메뉴로 표시된다.
3. 가짜 숫자 대신 실제 오늘 방문·촬영·실패·검수 건수가 보인다.
4. CRM 건물·호실에서 다시 검색하지 않고 촬영 업무를 시작할 수 있다.
5. 모바일에서는 배정된 오늘 작업과 오프라인 촬영이 정상 작동한다.
6. 주소 확인이 임의의 고정 좌표를 저장하지 않는다.
7. 여러 공실 호실이 각각 독립적으로 촬영·광고 상태를 가진다.
8. 촬영 완료가 광고 승인으로 자동 처리되지 않고, 모든 검수에 다른 작업자 표식 또는 대표의 사유 있는 예외가 남는다. 공용 로그인에서는 이 표식이 개인인증은 아니다.
9. 업로드와 광고 조회가 전체 미디어 부모 경로 권한에 의존하지 않는다.
10. 회사 Drive가 끊겨도 원본이 보존되고 관리자 조치 상태가 표시된다.
11. 실제 광고 게시 증거가 있어야 CRM 단계가 올라간다.
12. 기존 FIELD 데이터는 확인된 항목만 CRM과 연결되고 원본은 보존된다.
13. 미배정 업무를 팀원이 가져가고 배정·변경·반려 알림으로 바로 이동할 수 있다.
14. 업무 유형별 체크리스트와 완료조건이 실제 다음 행동을 결정한다.
15. 출입 준비와 시간제 보안정보 열람이 감사되며 원문 비밀번호가 FIELD에 남지 않는다.
16. 광고 이미지의 개인정보 검수와 채널별 게시·철회 상태가 작동한다.
17. 기존 전체 테스트와 신규 CRM·FIELD·서버 테스트가 0 실패다.
18. 보안 규칙, 모바일 실기기, 데스크톱 화면, 배포 버전 호환 검증이 완료된다.

## 18. 이번 개편에서 하지 않는 것

- 건물·고객·계약을 FIELD에 다시 만드는 것
- FIELD 홈에 전체 회사 매출이나 영업 KPI를 복제하는 것
- 당근·네이버 계정에 자동 로그인해 무인 게시하는 것
- 주소만 비슷하다는 이유로 기존 건물을 자동 합치는 것
- 일반 메모에 출입 비밀번호를 저장하는 것
- 기존 사진·방문 기록을 삭제하는 것
- 모바일 촬영 PWA 전체를 Electron 코드로 재작성하는 것

## 19. 대표 관점의 최종 화면

대표가 보는 구조는 다음처럼 단순해진다.

영업 CRM에서 공실을 확보한다. 현장 업무에서 누가 언제 촬영하는지 본다. 촬영이 끝나면 광고 준비와 막힌 업로드를 확인한다. 실제 광고 게시와 임대 결과는 다시 영업 CRM에 증거로 쌓인다. 청소·수리 필요가 발견되면 기존 케이스와 업체 연결 흐름으로 넘어간다.

즉 BRING FIELD는 별도 사업 화면이 아니라, 브링케어의 영업·임대·관리 사업을 현장에서 실행하고 증명하는 CRM 기능이 된다.
