# BRING 영업 CRM 통합 설계

- 작성일: 2026-08-13
- 상태: 사용자 승인 설계
- 대상 저장소: `bringengineering/FM`
- 사용자: 현재 BRING CRM을 사용하는 팀원 전원

## 1. 목적

기존 BRING CRM에 건물 단위 영업관리 화면을 추가한다. 팀원은 현재 CRM에 로그인한 상태 그대로 건물 발굴부터 공실 매물접수, 광고게시, 임대차계약, 유료관리 전환과 추가서비스 기회까지 기록한다.

이 기능은 별도의 CRM이나 로그인 시스템을 만드는 프로젝트가 아니다. 기존 FM 상단에서 바로 열리는 영업 전용 화면을 같은 저장소, 같은 Firebase 프로젝트와 같은 Google 로그인 세션에 연결한다.

## 2. 확정 원칙

1. 새 로그인 화면, 회원가입, 팀원 승인 화면을 만들지 않는다.
2. 현재 CRM의 Google 로그인 상태를 그대로 재사용한다.
3. 현재 CRM 사용자에게 별도의 대표·직원 권한 차이를 두지 않는다.
4. 기존 민원·공사 케이스 17단계와 영업 퍼널을 분리한다.
5. 영업의 기준 카드는 고객이 아니라 건물이다.
6. 한 건물 아래 여러 연락처, 호실, 영업활동과 추가서비스 기회를 연결한다.
7. 매물접수와 광고게시는 서로 다른 실적으로 기록한다.
8. 견적요청과 견적승인은 매출로 계산하지 않는다.
9. 기존 민원 CRM, 입금확인 캘린더, 건물지도와 사용자가 수정 중인 `wonju-map.html`의 동작을 변경하지 않는다.

## 3. 구현 방식

### 3.1 저장소와 진입점

- 기존 `index.html` 상단 도구모음에 `📈 영업 CRM` 링크를 추가한다.
- 영업 CRM은 `sales-crm.html`에서 연다.
- 화면 스타일과 로직은 전용 CSS와 JavaScript 모듈로 분리한다.
- 기존 6,000줄 이상의 `index.html`에는 링크 외에 영업 CRM 로직을 넣지 않는다.
- GitHub Pages 배포 방식은 기존과 동일하게 유지한다.

### 3.2 로그인 재사용

- `sales-crm.html`은 기존 Firebase 프로젝트 `bring-fm-hj`를 사용한다.
- Firebase Auth에 이미 로그인한 사용자는 추가 동작 없이 영업 CRM이 열린다.
- 로그인 세션이 없을 때만 기존 `index.html`로 돌아가 Google 로그인을 안내한다.
- 새 이메일 허용목록, 팀원 초대, 역할 관리와 별도 비밀번호는 만들지 않는다.

### 3.3 기존 기능과의 경계

- `/cases`는 민원·수리·견적·승인·작업·정산 케이스로 유지한다.
- 영업데이터를 `/cases`에 넣거나 `c1~c17` 상태를 재사용하지 않는다.
- `caseSettings/paymentBuildings`는 Drive 동기화 때 전체 교체되므로 영업 필드를 저장하지 않는다.
- `paymentCalendars/{uid}`에는 영업정보를 저장하지 않는다.
- 작업 전환 시 영업기회에 기존 민원 케이스 ID를 연결할 수만 있게 한다.

## 4. 화면 구성

### 4.1 영업 대시보드

다음 값을 같은 기준일로 보여준다.

- 전체 대상 건물
- 이번 주 신규 접촉
- 응답 건물과 유효관심 건물
- 미팅과 현장진단
- 매물접수 호실
- 광고게시 호실
- 임대차계약 호실
- 유료관리 전환 건물
- 추가서비스 기회와 작업완료 건수
- 오늘 할 후속연락과 기한이 지난 후속연락
- 담당자별 진행 건수

집계는 현재 단계 문자열이 아니라 완료증거가 저장된 이벤트를 기준으로 한다.

### 4.2 건물 파이프라인

건물 카드를 다음 단계별 열에 표시한다.

1. 건물후보
2. 유효 연락처 확보
3. 최초접촉
4. 응답
5. 유효관심
6. 미팅 확정
7. 현장진단 완료
8. 매물접수
9. 광고게시
10. 임차문의·방문
11. 임대차계약
12. 유료관리 전환
13. 보류·종료

건물 카드에는 건물명·주소, 공실·퇴실예정 호실 수, 담당자, 현재단계, 마지막 활동, 다음 행동과 기한을 표시한다.

### 4.3 건물 상세

건물 상세는 다음 영역으로 나눈다.

- 기본정보: 건물명, 주소, 지역, 유형, 수요거점, 조사일
- 건물주·연락처: 이름, 역할, 전화번호, 출처, 확인일, 수신거부 여부
- 호실: 호실명, 공실·퇴실예정 상태, 보증금·월세·관리비, 사진·자료 링크
- 활동이력: 문자, 전화, 방문, 미팅, 응답 원문, 사용 대본 버전
- 현장진단: 촬영동의, 확인사항, 문제목록, 긴급도, 증거 링크
- 중개 인계: 매물접수, 광고게시, 임차문의, 방문, 계약의 완료시각과 증거
- 관리 전환: 유료관리 시작일, 서비스 범위, 연결된 기존 케이스
- 추가서비스: 청소, 입·퇴실청소, 장판·도배, 방수, 설비·수리, 사이니지, 기타

### 4.4 영업 표준자료

CRM 안에서 다음 기준을 바로 열람한다.

- 승인된 S1~S12 문자·전화·방문 대본
- CL01~CL08 단계별 체크리스트
- 금지문구와 법률·공인중개사 인계기준
- 마스터 매뉴얼 PDF
- 현장 플레이북 PDF
- 교육자료 PPTX
- 실무평가표 XLSX

CRM 기록에는 긴 문서 전문을 복사하지 않는다. 활동에는 사용한 대본 ID와 버전, 체크리스트 통과 여부와 증거만 저장한다.

## 5. 데이터 모델

영업데이터는 기존 경로와 분리해 `salesCrm` 아래에 저장한다.

```text
salesCrm/
  buildings/{buildingId}
  contacts/{contactId}
  units/{unitId}
  leads/{leadId}
  activities/{activityId}
  events/{eventId}
  opportunities/{opportunityId}
  auditLogs/{auditId}
  settings/codes
```

### 5.1 건물

- 안정적인 건물 ID
- 건물명·별칭, 주소, 지역, 건물유형과 수요거점
- 담당자, 우선순위, 현재단계
- 공실·퇴실예정 호실 수
- 마지막 활동일, 다음 행동, 다음 행동 기한
- 기존 온보딩 건물의 `driveFileId` 또는 기존 케이스 참조
- 생성·수정 시각과 사용자 이메일

### 5.2 연락처

- 건물 또는 건물주 계정 참조
- 이름·역할·전화번호
- 연락처 출처와 출처 증거
- 확인일, 접촉 근거상태, 수신거부 여부와 시각

수신거부가 설정된 연락처에는 새 문자·전화 활동을 등록할 수 없다.

### 5.3 호실

- 건물 참조와 호실명
- 상태: 공실, 퇴실예정, 임대중, 확인필요
- 퇴실예정일
- 임대조건과 옵션
- 촬영·광고 자료 링크

### 5.4 활동과 이벤트

활동은 시도와 대화를 기록하고, 이벤트는 완료증거가 확인된 영업성과를 기록한다.

- 활동: 문자, 전화, 방문, 미팅, 내부메모, 후속일정
- 이벤트: 건물조사, 유효연락처, 접촉시도, 응답, 유효관심, 미팅확정, 현장진단, 매물접수, 광고게시, 임차문의, 방문, 임대차계약, 유료관리
- 공통필드: 대상, 담당자, 시각, 결과, 증거, 생성 사용자

대시보드는 이벤트만 집계한다. 활동을 여러 번 기록해도 완료증거가 없으면 다음 단계 성과로 계산하지 않는다.

### 5.5 추가서비스 기회

추가서비스는 임대 퍼널과 별도 상태를 사용한다.

`기회발견 → 견적요청 → 견적승인 → 작업완료 → 매출기록`

- 서비스 유형
- 발견일과 요구사항
- 담당자와 기한
- 견적·승인·완료 증거
- 연결된 민원 케이스 ID
- 완료일

내부 원가, 마진, 중개수익 배분은 이 CRM의 1차 범위에 넣지 않는다.

## 6. 초기 데이터와 중복 방지

- 현재 영업 매뉴얼의 5개 건물·7개 호실 PoC 정보는 초기 참조 스냅샷으로 사용한다.
- `1호 건물` 같은 익명 별칭을 실제 주소로 추측하지 않는다.
- 기존 `caseSettings/paymentBuildings`에서 건물을 가져올 때 사용자가 일치하는 건물을 선택한다.
- 확인된 기존 건물은 `driveFileId`로 연결하고 복제하지 않는다.
- 일치하지 않는 PoC 항목은 `확인 필요` 임시카드로 두고 실제정보 확인 후 연결한다.

## 7. 접근과 변경이력

- 현재 CRM에서 Google 로그인을 완료한 사용자는 영업 CRM의 모든 기능을 동일하게 사용할 수 있다.
- 별도 역할과 사용자별 기능 제한은 두지 않는다.
- 모든 생성·수정·단계변경·보관·복원에는 사용자 이메일과 시각을 남긴다.
- 일반 화면에는 영구삭제를 제공하지 않고 보관·복원만 제공한다.
- Firebase 규칙은 `salesCrm` 경로를 최소한 로그인 사용자에게만 허용한다.
- 기존 `/cases`, `/workflow`, `/caseSettings` 규칙은 기존 자동화 영향을 피하기 위해 이번 범위에서 바꾸지 않는다.

## 8. 입력 검증과 예외

- 주소 또는 건물 별칭 중 하나가 없으면 건물후보를 저장하지 않는다.
- 유효 연락처 근거 없이 `유효 연락처 확보` 이벤트를 만들지 않는다.
- 최초접촉에는 채널, 담당자, 일시와 결과가 필요하다.
- 매물접수에는 호실과 중개사 인계 증거가 필요하다.
- 광고게시에는 게시 채널, 게시시각과 확인 증거가 필요하다.
- 임대차계약에는 협력 공인중개사 완료확인만 저장하고 계약서 작성 기능은 만들지 않는다.
- 견적요청·견적승인을 매출로 집계하지 않는다.
- 다음 행동 기한이 지나면 지연 상태로 표시한다.
- 동일 주소 후보가 있으면 새 건물 생성 전 중복 경고를 표시한다.
- Firebase 저장 실패 시 화면 값을 성공으로 표시하지 않고 재시도 또는 임시 입력 복구 안내를 보여준다.

## 9. 테스트와 배포

### 9.1 자동검증

- 기존 CRM 상단에 영업 CRM 링크가 존재한다.
- 기존 Firebase 로그인 세션을 재사용한다.
- 비로그인 상태에서 영업데이터를 불러오지 않는다.
- 건물·연락처·호실·활동·이벤트·기회 입력 검증이 동작한다.
- 매물접수와 광고게시가 별도 이벤트로 집계된다.
- 완료증거 없는 단계가 KPI에 포함되지 않는다.
- 수신거부 연락처의 새 접촉 등록이 차단된다.
- 견적요청과 견적승인이 매출에서 제외된다.
- 보관·복원과 감사기록이 보존된다.
- 기존 `index.html`, 민원 케이스와 입금캘린더가 계속 열린다.

### 9.2 수동검증

- 현재 로그인 후 추가 로그인 없이 영업 CRM 진입
- PC와 모바일에서 파이프라인·상세·활동 입력
- 세 명이 같은 데이터를 실시간으로 확인
- 기존 건물 가져오기와 중복 경고
- 민원 케이스 연결
- GitHub Pages 배포본 새로고침과 이전 화면 복귀

### 9.3 작업 안전

- 현재 사용자 수정 `wonju-map.html`은 수정·스테이징·커밋하지 않는다.
- 별도 작업 브랜치와 worktree에서 구현한다.
- 현재 브랜치와 원격의 차이를 확인한 뒤 기준 브랜치를 정한다.
- DB 규칙 배포는 GitHub Pages 배포와 분리해 검증한다.
- 운영 데이터에 테스트 레코드를 만들기 전에 로컬·에뮬레이터 검증을 완료한다.

## 10. 완료 기준

1. 기존 CRM 상단에서 영업 CRM을 한 번에 열 수 있다.
2. 기존 로그인 사용자는 추가 로그인 없이 화면을 사용한다.
3. 건물을 기준으로 여러 연락처·호실·활동·기회를 관리한다.
4. 승인된 영업 퍼널과 추가서비스 흐름을 기록한다.
5. 매물접수와 광고게시, 견적과 매출이 구분된다.
6. 현재 PoC 건물을 기존 건물 레지스트리와 확인 후 연결할 수 있다.
7. 세 사용자에게 동일한 기능을 제공한다.
8. 기존 민원 CRM·입금캘린더·건물지도가 회귀 없이 동작한다.
9. 주요 입력·집계·보관·감사 동작의 자동검증이 통과한다.
10. GitHub Pages에서 실제 사용 가능한 상태로 배포된다.
