# 청구·입금 초안 반려 이력 설계

상태: 사용자 승인 설계. 원자적 장부 쓰기 PR #134의 후속 개발 범위이며 운영 배포 승인은 아니다.

## 목적과 경계

관리자가 청구서 또는 입금 초안의 근거가 부족할 때 사유를 남겨 담당자에게 돌려보낸다. 반려는 매출 확정이나 취소가 아니므로 기존 `draft`/`approved`/`void` 상태를 변경하지 않는다. 기존 장부·계약·입금 기록은 삭제하거나 소급 수정하지 않는다.

## 저장 모델

- 각 초안에 서버 소유의 `returnHistory` 맵을 선택적으로 둔다. 키는 요청 ID, 값은 `{ reason, returnedBy, returnedAt, revision }`이다. 사유는 앞뒤 공백을 제거한 5~500자 텍스트다. 클라이언트가 작성자·시각·버전을 지정할 수 없다.
- `returnPending: true`는 마지막 반려 뒤 담당자의 실질적인 수정이 없다는 뜻이다. 초안을 실제로 수정하면 서버가 `false`로 바꾸되 `returnHistory`는 보존한다. 이전 데이터에 두 필드가 없어도 정상 기록이다.
- 전체 장부의 기존 1MiB 제한은 그대로 적용한다. 한계에 닿으면 이력을 삭제하지 않고 명시적으로 저장을 거절한다. TV·월별 합계에는 두 필드를 전달하지 않는다.

## 서버 명령과 권한

- 기존 HTTPS Function에 `action: "return"`, `kind`, 레코드 ID, 기대 버전, 요청 ID, 반려 사유를 받는 명령을 추가한다. 기존 생성·수정·확정·취소 요청 형식과 응답은 유지한다.
- 서버는 Firebase 로그인·회사 접근·관리자 역할을 검증한다. 대상이 현재 `draft`이고 기대 버전이 일치할 때만 단일 장부 트랜잭션에서 이력을 추가하고 버전을 1 올린다. 청구·입금 금액이나 날짜는 변경하지 않는다.
- 같은 요청 ID의 재시도는 동일 결과를 돌려주고 이력을 중복 추가하지 않는다. 다른 사유를 같은 요청 ID로 보내면 충돌로 거절한다. 경합한 수정·확정·반려 중 하나만 성공하고 나머지는 버전 충돌을 받는다.
- `returnPending`인 초안은 관리자가 즉시 확정할 수 없다. 담당자 또는 관리자가 내용의 적어도 한 사업 필드를 실제로 바꿔 저장해야 보류 표시가 해제된다. 내용이 동일한 저장은 반려 해제로 취급하지 않는다.
- 관리자도 초안의 내용 변경과 반려를 한 요청에서 동시에 할 수 없다. 반려 사유만 기록하고, 담당자가 별도 수정·재제출한다.

## CRM 화면

- 초안 행에 `반려 중` 배지와 최근 사유·시각을 표시한다. 펼쳐 보기에서는 해당 기록의 이전 반려 이력을 읽을 수 있다. 이 내용은 장부 접근 권한이 있는 사내 사용자에게만 보인다.
- 관리자에게 초안별 `반려` 버튼을 제공한다. 사유 5~500자를 입력하고 확인하면 저장한다. 진행 중에는 중복 제출을 막고, 충돌 시 최신 장부를 다시 읽어 기존 입력 사유를 보여 준다.
- 담당자가 초안을 수정한 뒤에는 `수정됨 · 관리자 재확인 대기`로 표시한다. 관리자 확정 버튼은 `returnPending`이 해제된 뒤에만 보인다. 화면 숨김 외에 서버에서도 동일 조건을 검사한다.
- 입금 초안이 청구 초안에 연결된 경우 기존처럼 청구 확정 전에는 입금 확정을 허용하지 않는다.

## 호환성·검증

- 기존 기록의 `returnHistory`/`returnPending` 부재를 허용하고 읽기 화면·로컬 백업 점검 도구가 새 필드를 검증하도록 한다. 구버전 CRM의 직접 장부 쓰기 금지 정책은 유지한다.
- 순수 리듀서와 Firebase 에뮬레이터에서 관리자만 반려, 사유 길이, 재시도 중복 방지, 수정·반려 경합, 실질적 수정 전 확정 차단, 이력 보존을 검사한다. CRM 원격 호출·화면과 TV 투영에도 회귀 테스트를 추가한다.
- 구현과 테스트가 완료되어도 PR은 초안으로 유지한다. 회사 장부 읽기 전용 백업·대조, 배포 정책 확인, 실제 기기/TV 검증과 별도 배포 승인 전에는 병합하거나 운영 배포하지 않는다.
