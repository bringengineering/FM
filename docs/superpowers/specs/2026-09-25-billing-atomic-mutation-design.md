# 청구·입금 장부 원자적 저장 설계

상태: 대표 승인 요청. 기존 [계약 청구·입금 장부 및 TV 매출 설계](2026-09-25-contract-billing-ledger-tv-design.md)의 운영 배포 차단 조건을 해결하기 위한 추가 설계다. 운영 배포는 포함하지 않는다.

## 결정

기존 Firebase Realtime Database의 `crmCompany/billingLedger` 구조와 CRM 화면·IPC 인터페이스를 유지한다. 새 HTTPS Firebase Function 하나가 장부 변경의 유일한 쓰기 경로가 된다. 클라이언트가 장부를 직접 수정하는 권한은 Firebase 규칙에서 닫는다. 따라서 다른 사용자가 동시에 저장하거나 구버전 클라이언트가 쓰더라도 서버에서 권한·중복·상태 전이를 검증한다.

## 요청과 응답

CRM은 기존 로그인 토큰으로 서버에 `invoice` 또는 `receipt` 변경을 보낸다. 요청에는 작업 종류(초안 생성·수정, 확정, 취소), 레코드 ID, 기대 버전, 요청 ID, 필요한 필드만 담는다. 서버는 토큰과 회사 접근 권한을 다시 검증한다. 담당자는 초안 생성·수정만, 관리자만 확정·취소할 수 있다. 서버가 작성자·승인자·취소자와 시각을 기록하며, 클라이언트의 UID·상태·시각 주장은 신뢰하지 않는다. 성공 응답은 저장된 레코드와 새 버전을 돌려준다. 충돌 또는 검증 실패는 구별 가능한 오류 코드로 응답하고 CRM은 새 장부를 읽어 차이를 보여준다.

## 원자적 검증

서버는 `crmCompany/billingLedger` 노드에서 한 번의 Realtime Database 트랜잭션으로 아래를 함께 검사하고 변경한다. 트랜잭션 재실행 중 외부 전송이나 로그 쓰기 같은 부작용을 하지 않는다.

- 기대 버전이 현재 버전과 일치하는지 검사한다. 같은 요청 ID와 이미 반영된 변경은 재시도로 취급해 중복 저장하지 않는다.
- 취소되지 않은 정기 청구는 계약 ID·청구 월, 단건 청구는 계약 ID·발생 ID가 중복되지 않게 한다.
- 입금은 존재하는 확정 청구에만 확정할 수 있다. 같은 청구에 동일 거래 참조의 확정 입금을 둘 수 없다.
- 확정 입금이 연결된 청구는 취소할 수 없다. 확정 레코드는 금액·귀속 월·거래 내용을 직접 수정하지 않는다.
- 날짜·월·양의 정수 금액·문자열 길이·안전한 합계 범위를 검사한다. 알 수 없는 상태나 손상된 장부는 자동 수선하지 않고 오류로 중단한다.

트랜잭션이 커지는 문제를 감지하도록 장부 크기 상한과 명시적 오류를 둔다. 상한에 도달하면 임의로 기존 기록을 지우지 않고, 별도의 분할 설계를 승인받는다.

## 읽기·보고·TV

장부 읽기와 기존 계산·TV 공개 범위는 유지한다. TV에는 관리자 확정 청구액과 확정 입금액의 회사 합계만 간다. 저장 실패, 승인 전 초안, 근거 없는 과거 `입금 완료` 표시는 매출 실적으로 집계하지 않는다. 네트워크 응답이 끊긴 경우 동일 요청 ID로 재확인하며, 결과를 확인할 수 없으면 성공으로 표시하지 않는다.

## 배포 전 확인

순수 검증 함수 테스트와 Firebase 에뮬레이터에서 동시 생성·동시 확정·중복 거래·연결 입금 상태의 청구 취소·직접 쓰기 거부를 검증한다. 기존 장부를 읽기 전용으로 점검해 중복·고아 레코드를 보고하고, 기존 데이터는 자동 삭제·수정하지 않는다. 함수 배포, 새 CRM 배포, 직접 쓰기 차단 규칙의 적용 순서와 구버전 CRM의 오류 안내를 운영 체크리스트로 점검한다. 실제 회사 데이터 반영과 두 기기 TV 갱신 확인을 마친 뒤에만 운영 배포·병합 여부를 별도로 결정한다.
