# TV 서버 매출 자동 갱신 설계

상태: 사용자 승인 방향의 상세 설계. 구현 및 운영 배포는 구분한다.

## 목표와 범위

CRM PC가 실행 중이지 않아도 기존 5분 간격 Cloudflare Worker 갱신 경로가 회사 Firebase의 청구·입금 장부를 읽고 TV의 `매출 현황` 장면을 갱신한다. TV에는 확인된 월별 합계만 게시한다. 계약·고객·은행 거래·증빙·반려 사유는 게시하지 않는다. 기존 CRM의 장부 입력·관리자 확정, TV의 다른 장면과 로컬 미리보기는 유지한다.

이번 변경은 Worker 코드와 로컬 테스트까지다. `WALLBOARD_SCHEDULED_REFRESH_ENABLED`는 계속 `false`로 두고 운영 배포나 Firebase Functions 배포는 하지 않는다.

## 접근 방식

기존 TV 읽기 계정의 ID 토큰으로 Worker가 `crmCompany/billingLedger`를 읽는다. 대안인 새 Firebase 집계 Function은 데이터 접근 범위를 더 좁힐 수 있으나 현재 회사 Functions 배포 정책상 운영 연결을 보장할 수 없다. 기존 CRM PC 게시 방식만 유지하면 PC 독립성이 생기지 않는다. 따라서 읽기 전용 Worker 내부 집계를 선택한다.

Firebase 규칙에서는 기존 7개 TV 자료 경로와 동일하게, 이메일 인증이 완료되고 `wallboardReaders/{uid}`에 활성 상태·일치하는 이메일로 등록된 계정에만 장부 읽기를 추가한다. 장부 쓰기 권한은 늘리지 않는다. 이 계정은 원문을 읽을 수 있으므로 전용 계정의 비밀키·권한 관리를 운영 출시 게이트로 취급한다.

Worker의 읽기 대상은 현재 업무·프로젝트 자료에 장부 한 경로를 추가한다. 읽기에는 기존 HTTPS 전용 URL 검증, 토큰 사용, 응답 크기 제한, 타임아웃, 리디렉션 차단을 그대로 적용한다. 토큰이나 장부 원문을 로그·예외·TV 게시물에 넣지 않는다.

## 검증과 계산

서버가 받은 장부는 `invoices`·`receipts` 맵 또는 빈 장부여야 한다. 장부 전체가 `null`이거나 하위 맵이 생략되면 빈 장부로 다루지만, 하위 맵이 명시적으로 `null`이면 손상된 응답으로 거절한다. 각 항목의 ID·상태·버전·금액·날짜·참조 관계와 승인 메타데이터를 검증한다. 잘못된 형식, 고아 입금, 중복 청구 자연키, 동일 청구서의 중복 은행 거래 참조, 안전 정수 초과가 있으면 합계를 게시하지 않는다. `returnHistory`·`returnPending`은 저장 형식을 검증하되 금액 계산에는 사용하지 않는다.

검증한 맵을 배열로 변환한 뒤 기존 `BringBillingLedgerCore.summarizeMonth`와 `BringCompanyWallboard.project`를 사용한다. 청구액은 해당 월 확정 청구, 입금액은 해당 월 실제 입금된 확정 기록, 미수금은 누적 확정 장부를 기준으로 한다. 초안은 금액 대신 확인 대기 건수에만 포함한다. 모든 수치는 안전한 정수 원이다. 새 장부가 비어 있으면 `0원`으로 단정하지 않고 기존의 `집계 대기` 상태를 유지한다.

## TV 게시와 실패 처리

서버 기본 화면 편성에 `companyRevenue`를 추가한다. 기존 관리자가 저장한 편성이 있으면 다른 화면의 순서·노출 시간은 보존하고, 매출 장면이 빠져 있을 때에만 기본 30초 장면을 덧붙인다. TV 공개 스키마는 기존 합계 필드만 허용한다. 게시 직전 원문 고객명·계약 ID·거래 참조·증빙 링크·UID·반려 사유가 스냅샷에 없는지 테스트한다.

장부 조회 권한 오류·타임아웃·손상 등 검증 실패 시 이번 주기에는 **어떤 새 스냅샷도 게시하지 않는다**. 마지막 정상 게시본과 게시 시각은 TV에 남는다. 기존 다른 장면도 유지하며 장애를 신규 매출로 위장하지 않는다. 정상 장부가 다시 읽히면 다음 갱신 주기에서 회복한다.

## 검증과 출시 게이트

- 단위 테스트: 승인/초안/반려/부분입금/월 경계/고아·중복·손상 기록/안전 정수/개인정보 비노출.
- Worker 통합 테스트: 회사 읽기 토큰으로 장부 경로 1회 조회, 다른 경로 유지, 공개 스냅샷 구조, 실패 시 게시 명령 없음, 기존 편성 보존.
- 전체 Worker·CRM 회귀 테스트와 읽기 전용 규칙 에뮬레이터 검증.
- 운영 전에는 회사 장부 백업·대조, TV 읽기 계정의 장부 접근 확인, Worker 비밀키·배포 권한 확인, 두 기기와 실제 TV 전파 시간 측정, 배포 정책과 순서에 대한 별도 승인이 필요하다. 이 조건이 충족되기 전에는 스케줄 플래그를 켜거나 배포하지 않는다.
