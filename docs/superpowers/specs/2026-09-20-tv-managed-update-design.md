# BRING TV 관리자 승인 업데이트 설계

## 목적과 확정 사항

회사 TV에 표시되는 실적·공지·일정은 기존 운영보드 서버로 계속 갱신한다. TV 프로그램 자체의 새 버전은 CRM 관리자가 특정 TV에 명시적으로 승인했을 때만 설치한다. 기존 BRING CRM 업데이트 채널, 태그, 설치본, 사용자 데이터 폴더를 재사용하지 않는다.

## 선택한 방식

CRM 관리자 승인형 업데이트를 사용한다.

- TV는 새 버전을 확인하고 검증할 수 있지만 승인 전에는 설치하지 않는다.
- CRM의 `TV 기기 승인·관리` 목록에서 현재 버전, 최신 버전, 상태를 확인한다.
- 관리자가 대상 기기와 버전을 확인한 뒤 `업데이트 예약`을 누르면 서버에 1회 명령이 저장된다.
- TV는 다음 정상 조회에서 자기 기기의 명령만 수신한다. 설치본을 내려받아 검증한 뒤 프로그램을 재시작하여 설치한다.
- 성공 후 새 버전과 마지막 접속시각이 서버에 기록된다. 실패하면 현재 버전을 유지하고 오류 상태만 보고한다.

이 방식은 무승인 강제 설치보다 업무 중 화면 중단을 줄이고, TV마다 설치 결과를 추적할 수 있다. TV 앞에서 별도의 직원 계정으로 로그인할 필요도 없다.

## 별도 배포 채널

TV 릴리스는 GitHub 저장소 안에서 다음 이름 공간을 사용한다.

- 태그: `tv-v<버전>`
- 설치본: `BRING.TV.Setup.<버전>.exe`
- 블록맵: `BRING.TV.Setup.<버전>.exe.blockmap`
- 매니페스트: `latest-tv.yml`
- 채널 포인터: `tv-update-channel/latest.json`

CRM의 `crm-v<버전>`, `latest.yml`, `crm-update-channel`은 읽거나 변경하지 않는다. 기존 태그를 이동하거나 재사용하지 않는다. 각 릴리스는 소스 SHA, 파일 크기, SHA-512 및 게시시각에 묶인 불변 자산으로 발행한다.

## 구성 요소와 데이터 흐름

1. TV 전용 릴리스 작업이 설치본·블록맵·매니페스트를 빌드하고 검증한다.
2. Windows 게시자 서명과 자산 검증이 모두 성공한 경우에만 TV 채널 포인터를 최신 버전으로 전진시킨다.
3. TV 클라이언트는 고정된 회사 저장소와 TV 채널만 조회한다. 리디렉션·크기·파일명·버전·해시가 다르면 업데이트를 거부한다.
4. TV는 `현재 버전`, `확인한 최신 버전`, `다운로드/준비/설치 실패 상태`만 서버에 보고한다. 기기 토큰은 계속 Windows 보호 저장소 밖으로 내보내지 않는다.
5. CRM 관리자는 기기 목록에서 상태를 보고 특정 기기에 목표 버전을 예약한다. 서버는 관리자 Firebase 신원과 허용 목록을 다시 확인한다.
6. TV는 자기 기기의 미소비 예약만 받아 다운로드한다. 설치 준비가 끝나면 예약 버전과 내려받은 버전이 같은지 다시 검사하고 재시작 설치한다.
7. 새 프로그램이 서버에 버전을 보고하면 예약을 완료 처리한다. 일정 시간 안에 새 버전이 확인되지 않으면 `확인 필요`로 표시한다.

## 서버 저장 항목

기기별로 아래 값만 추가한다.

- 현재 클라이언트 버전
- 마지막 업데이트 상태와 시각
- 관리자가 승인한 목표 버전과 승인자·승인시각
- 명령 소비시각
- 새 버전 최초 확인시각 또는 실패 코드

다운로드 URL, 직원 토큰, 기기 토큰 원문, 고객정보는 저장하지 않는다. 목표 버전은 현재 공개된 TV 채널 버전과 정확히 일치할 때만 승인할 수 있다. 해제된 기기는 명령을 받거나 상태를 갱신할 수 없다.

## 관리자 화면

각 TV 행에 다음을 표시한다.

- 승인/해제 상태
- 마지막 서버 접속
- 현재 TV 버전
- 최신 TV 버전
- 최신/업데이트 대기/다운로드 중/재시작 대기/확인 필요
- `업데이트 예약` 버튼

버튼을 누르면 대상 기기, 현재·목표 버전, TV가 재시작된다는 내용을 확인창에 보여준다. 여러 기기 일괄 업데이트는 첫 운영 검증 이후로 미룬다. 실제 화면 출력 여부는 접속시각만으로 성공 처리하지 않는다.

## 실패와 복구

- 네트워크 오류: 현재 화면과 현재 프로그램을 유지하고 다음 확인에서 재시도한다.
- 채널·해시·서명 불일치: 다운로드·설치를 중단하고 관리자에게 검증 실패로 표시한다.
- 프로그램 종료 또는 전원 차단: 설치 준비 전이면 현재 버전을 유지한다. 설치 도중 실패는 설치 관리자의 원복 결과를 보고한다.
- 서버 명령 중복: 기기·목표 버전 기준으로 멱등 처리한다.
- 해제: 즉시 데이터 조회와 업데이트 명령을 모두 거부한다.
- 잘못된 릴리스: 채널 포인터 전진을 중단한다. 이미 발행한 태그·자산은 수정하지 않고 더 높은 새 버전으로 고친다.

## 서명과 활성화 기준

현재 저장소에서 회사 Windows 코드서명 인증서 구성을 확인하지 못했다. 따라서 코드와 테스트, 별도 릴리스 작업은 구현할 수 있지만 원격 자동 설치 채널은 아래 조건 전에는 활성화하지 않는다.

- 회사 명의 Windows 코드서명 인증서와 GitHub Actions용 보호된 서명 방식 준비
- 서명 주체와 인증서 지문 검증
- 설치본의 Authenticode 유효성 확인
- 새 설치본과 업데이트 설치본 모두 같은 게시자인지 확인

인증서 원문·비밀번호는 저장소나 TV에 넣지 않는다. 준비 전 빌드는 `Preview`로만 취급하고 운영 채널 포인터를 전진시키지 않는다.

## 검증 기준

- 단위 검사: 채널 포인터, 버전 비교, 자산 크기·해시, 관리자 승인, 중복 명령, 해제, 실패 상태.
- 서버 런타임: 기기별 명령 격리, 재시작 후 상태 보존, 권한 없는 예약 거부.
- 패키지 검사: TV 전용 ID·파일·피드만 포함하고 CRM 세션 파일이 없는지 확인.
- 실제 Windows TV: 기존 버전 설치 → 관리자 예약 → 다운로드 → 재시작 → 새 버전 보고 → 5개 장면 정상 표시.
- 장애 검사: 오프라인, 잘못된 해시, 잘못된 서명, 전원 재시작, 기기 해제.
- 기존 CRM 회귀: 로그인·저장·기존 자동 업데이트·AI·카카오·운영보드 게시가 그대로 동작하는지 확인.

## 구현·배포 경계

- Firebase Functions와 Hosting은 배포하지 않는다.
- TV 업데이트 명령을 위해 기존 회사 운영보드 Worker와 전용 Durable Object만 확장한다.
- 서버 변경은 TV 클라이언트보다 먼저 배포하고 구버전의 빈 업데이트 상태 요청을 허용한다.
- CRM 운영 브랜치 병합과 CRM 자동 릴리스는 별도 승인·검증 단계다.
- 실제 TV 설치·시작프로그램 등록·화면 배율 조정은 TV 컴퓨터에서 사용자가 실행하거나 이미 승인된 원격 접속으로 수행한다.

## 완료 기준

코드가 빌드되는 것만으로 완료하지 않는다. 서명된 TV 릴리스가 별도 채널에 게시되고, CRM 관리자 한 명이 실제 TV 한 대에 업데이트를 예약하여 설치·재시작·새 버전 보고·화면 표시까지 확인해야 1차 완료다. 이후 해제된 기기가 더 이상 데이터와 업데이트 명령을 받지 못하는 것까지 확인한다.
