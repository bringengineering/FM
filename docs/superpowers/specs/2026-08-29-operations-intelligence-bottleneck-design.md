# BRING Care 운영 인텔리전스 병목 분석 2단계 설계

## 목표

운영 기록을 단순히 쌓는 데서 끝내지 않고, 어떤 업무가 반복되고 사람의 시간·현장 방문·재작업을 많이 요구하는지 근거로 확인한다. 데이터가 충분하지 않은 상태에서 R&D 분야나 자동화 기술을 미리 결정하지 않는다.

## 선행 안정화

현재 PR #44의 데스크톱 검사는 통과했지만 `backend-and-rules` 검사는 기존 Firebase 테스트 헬퍼의 TypeScript 타입 추론 오류로 실패했다. 기능 확장 전에 해당 헬퍼의 `sign_in_provider`를 Firebase가 허용하는 타입으로 좁히고, 회사 사이트 타입 검사와 전체 CI를 통과시킨다. 운영 규칙 자체의 런타임 실패로 오인하지 않는다.

## 범위

별도 운영 인텔리전스 창을 다음 세 탭으로 확장한다.

1. **운영 현황**: 현재 V1의 KPI, 운영 목록, 등록·상태변경·빠른 완료를 유지한다.
2. **병목 분석**: 시간, 방문, 재작업, 예외, 최초 해결률을 업무 유형별로 비교한다.
3. **개선 후보**: 충분한 표본이 쌓인 업무 유형만 데이터 기반 검토 후보로 보여준다.

기존 CRM의 작업관리, 고객, 건물, 계약 화면과 저장 구조는 변경하지 않는다.

## 수집 데이터 보강

Operation에 다음 필드를 추가한다.

- `repeatability`: low, medium, high
- `managerIntervened`: 대표 또는 관리자 개입 여부
- `managerMinutes`: 대표 또는 관리자 직접 투입시간
- `assignmentChangeCount`: 담당자 변경 횟수(시스템 계산)
- `scheduleChangeCount`: 일정 변경 횟수(시스템 계산)
- `reopenCount`: 완료 후 다시 연 횟수(향후 reopen 동작에서 계산)
- `commentCount`: 연결된 메모·댓글 수(초기에는 0, 시스템 소유)
- `attachments`: 증빙 메타데이터 목록

증빙 메타데이터는 다음만 저장한다.

- 유형: before_photo, after_photo, video, audio, estimate, receipt, invoice, document, other
- 기존 자료의 안전한 참조 ID 또는 HTTPS URL
- 파일명, 등록시간, 등록자, buildingId, unitId

이번 단계에서는 원본 파일 업로드나 대용량 Base64 저장을 도입하지 않는다.

## 자동 계산 원칙

- 담당자가 실제로 달라질 때만 `assignmentChangeCount`를 1 증가시킨다.
- 기존 일정이 다른 일정으로 바뀔 때만 `scheduleChangeCount`를 1 증가시킨다.
- 사용자가 자동 계산 필드를 직접 수정할 수 없도록 메인 프로세스가 서버 기존값을 기준으로 계산한다.
- 저장 시 기존 고객·건물 데이터는 읽기 전용으로 재검증하고 변경하지 않는다.
- 모든 집계는 원본 Operation으로부터 화면에서 계산하며 별도 집계 데이터 복사본을 만들지 않는다.

## 병목 분석

업무 `category + subcategory`를 하나의 유형으로 묶어 다음을 표시한다.

- 발생 건수
- 총 직접 투입시간과 건당 평균
- 현장 방문 건수와 비율
- 재방문·재작업 건수와 비율
- 예외 발생 건수와 비율
- 대표·관리자 개입 건수와 시간
- 최초 해결 건수와 비율
- 일정·담당자 변경 횟수

표본 3건 미만은 수치를 보여주되 `표본 부족`으로 표시하고 비교 순위에서 제외한다. 기간 필터는 이번 달, 최근 90일, 전체를 제공하고 기본값은 최근 90일로 한다.

## 개선 후보

초기에는 0~100점의 Bottleneck Score나 R&D Opportunity Score를 만들지 않는다. 대신 다음 기준 중 2개 이상을 만족하고 표본이 5건 이상인 업무 유형을 `관찰 후보`로 표시한다.

- 건당 직접 투입시간이 전체 중앙값보다 높음
- 현장 방문률 60% 이상
- 재방문 또는 재작업률 20% 이상
- 예외 발생률 25% 이상
- 대표·관리자 개입률 20% 이상
- 최초 해결률 70% 미만
- 반복 가능성 high 비율 50% 이상

후보에는 원인이 아니라 관측 사실만 적는다. 예: `현장 방문 73% · 재작업 27% · 표본 11건`. AI Scheduling, Computer Vision 같은 기술명은 자동으로 붙이지 않는다.

## 화면 구성

상단 공통 영역에 기간 선택과 새 운영 등록 버튼을 둔다. 탭을 바꿔도 필터 기간을 유지한다.

- 운영 현황: 기존 KPI·사람 업무 분석·운영 목록
- 병목 분석: 유형별 비교 카드와 정렬 가능한 표
- 개선 후보: 후보 카드, 관찰 근거, 표본 수, `계속 관찰` 상태

빈 데이터, 표본 부족, 서버 오류를 서로 다른 안내 상태로 표시한다. 조회 전용 사용자는 모든 분석을 볼 수 있지만 기록 수정 버튼은 제공하지 않는다.

## 오류와 동시 수정 처리

- 서버의 최신 version과 화면에서 연 version이 다르면 저장을 거부하고 새로고침을 안내한다.
- 잘못된 상태 전이, 존재하지 않는 고객·건물 연결, 허용되지 않은 증빙 참조를 거부한다.
- 서버 저장 실패 시 화면 데이터만 성공한 것처럼 바꾸지 않는다.
- 병목 계산 중 일부 레거시 값이 잘못돼도 해당 값을 안전한 기본값으로 정규화하고 다른 기록은 계속 분석한다.

## 테스트 기준

- TypeScript 타입 검사와 기존 전체 CI가 통과한다.
- 자동 계산 필드를 렌더러가 조작해도 서버 저장값에 반영되지 않는다.
- 동일 업무를 동시에 수정하면 한쪽이 덮어쓰지 않고 충돌로 종료된다.
- 3건 미만 표본은 순위에서 제외되고, 5건 미만은 개선 후보가 되지 않는다.
- 후보 선정은 원본 배열 순서와 무관하며 같은 입력에 항상 같은 결과를 낸다.
- viewer는 읽기만 가능하고 member/admin만 저장 가능하다.
- 기존 `serviceRecords`, `workManagement`, 고객·건물 저장 결과는 확장 전후 동일하다.

## 이번 단계에서 하지 않는 것

- Bottleneck Score 및 R&D Opportunity Score
- AI 추천, 자동 담당자 배정, 자동 일정 계획
- 원본 파일 업로드와 Google Drive 업로드 자동화
- 기존 작업관리와의 양방향 동기화
- R&D 기술 또는 제품 방향 자동 결정
