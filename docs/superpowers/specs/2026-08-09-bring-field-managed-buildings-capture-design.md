# BRING 관리계약 지도·건물주 메모·현장 촬영 개선 설계

- 작성일: 2026-08-09
- 상태: 사용자 승인 완료, 구현 전 설계 고정
- 대상 저장소: `bringengineering/FM`
- 대상 화면: 내부 현장 플랫폼 `/field`
- 관련 기준 설계: `2026-08-09-bring-field-listing-platform-design.md`

이 문서는 지도 레이어, 건물주 메모, 고정 작업 도크, 촬영·업로드 부분에서 기존 구현 계획보다 우선한다. 기존 계획의 `독립 레이어 체크박스` 테스트와 작업 설명은 구현 전에 이 문서의 `배타적인 두 탭` 기준으로 교체한다.

## 1. 목적

현재 1차 플랫폼에 다음 현장 사용성 개선을 한 묶음으로 추가한다.

1. 기존 원주 유지보수 업체 지도와 BRING이 실제 관리계약을 맺은 건물 지도를 명확히 분리한다.
2. 건물 주소로 자동 계산되는 위도·경도는 내부 데이터로만 유지하고 직원 입력 화면에서는 숨긴다.
3. 건물주 요청사항을 날짜·작성자별로 누적하는 메모장을 모든 등록 단계 상단에 유지한다.
4. 이전·다음 버튼을 화면 하단의 고정된 위치에 배치해 단계마다 이동하지 않게 한다.
5. 휴대전화 카메라로 사진·영상을 촬영하고, 오프라인에서도 보존한 뒤 Firebase에 안전하게 업로드한다.

이 변경은 단순한 화면 시제품이 아니라 대표와 내부 직원이 현장에서 실제 사용할 수 있는 저장 흐름을 목표로 한다.

## 2. 검토한 대안과 결정

### 대안 A: 화면만 빠르게 변경

- 지도 체크박스를 탭처럼 꾸민다.
- 메모와 촬영정보를 현재 `localStorage` 초안에만 둔다.
- 사진은 미리보기만 제공한다.

장점은 구현이 빠르다는 것이다. 그러나 휴대전화 교체, 브라우저 저장소 정리, 직원 간 인계 때 내용이 사라지고 촬영 결과를 공유할 수 없으므로 채택하지 않는다.

### 대안 B: Firebase와 오프라인 대기열을 연결한 실사용형

- 관리계약 상태를 정식 건물 데이터로 저장한다.
- 지도는 두 개의 배타적인 업무 탭으로 전환한다.
- 메모는 append-only에 가까운 기록으로 중앙 저장한다.
- 사진·영상 원본은 IndexedDB 대기열과 Firebase Storage를 거쳐 저장한다.
- 서버가 업로드 결과를 검증하고 미디어 레코드와 감사기록을 확정한다.

직원 간 공유, 재접속 복구, 권한 통제에 필요한 최소한의 신뢰성을 제공하므로 이 방식을 채택한다.

### 대안 C: 앱 내부 실시간 카메라 스튜디오

`getUserMedia`, `MediaRecorder`, 실시간 구도 가이드, 영상 편집을 모두 앱 내부에 구현한다. 장기적으로 유용할 수 있지만 iPhone Safari/PWA 호환성과 권한 오류 처리 범위가 크게 늘어난다. 1차 촬영 기능에는 채택하지 않는다.

## 3. 핵심 제품 결정

- `BRING 관리계약 건물`은 플랫폼에 등록된 모든 건물이 아니라 관리계약 상태가 `active`인 건물만 의미한다.
- 지도에서는 유지보수 업체와 관리계약 건물을 동시에 겹쳐 표시하지 않는다. 직원은 한 번에 한 업무 맥락만 선택한다.
- 위도·경도는 주소 검증 결과로 계속 저장하고 지도/GPS 검증에 사용하지만 수동 입력 필드는 제거한다.
- 건물주 메모는 하나의 장문을 계속 덮어쓰지 않고 날짜·작성자별 항목으로 누적한다.
- 촬영은 모바일 운영체제의 기본 카메라를 여는 방식을 우선한다. 데스크톱에서는 파일 선택으로 자연스럽게 대체된다.
- 사진·영상 바이너리는 `localStorage`에 넣지 않는다. `localStorage`에는 버전이 있는 직렬화 가능한 초안 메타데이터만, 바이너리는 IndexedDB에 저장한다.
- 건물주 메모와 내부 관리계약 정보는 광고 패키지 및 일반 지도 팝업에 포함하지 않는다.
- 촬영 컴포넌트는 등록 마법사의 5단계와 하단 `촬영` 메뉴에서 함께 사용한다. 두 화면에 서로 다른 촬영 로직을 만들지 않는다.

## 4. 관리계약 데이터 모델

건물에 단순 불리언 대신 상태가 있는 관리계약 정보를 추가한다.

```ts
type ManagementContractStatus = "none" | "pending" | "active" | "paused" | "ended";

interface ManagementContractInfo {
  status: ManagementContractStatus;
  startedOn?: string;
  endedOn?: string;
  updatedAt: ISODateTime;
  updatedBy: EntityId;
}
```

운영 규칙은 다음과 같다.

- 신규 건물 기본값은 `none`이다.
- `active`만 관리계약 지도에 노출한다.
- 일반 직원은 `none`에서 `pending`으로 확인을 요청할 수 있다. 관리자만 `active`, `paused`, `ended`로 변경할 수 있다.
- 관리자가 직접 등록하는 경우에는 확인된 계약에 한해 즉시 `active`로 저장할 수 있다.
- `paused`, `ended`, `archivedAt`이 있는 건물은 지도에서 제외하지만 이력은 보존한다.
- 시작일은 `active` 전환 시 입력하도록 안내한다. 데이터 이관 때문에 1차 마이그레이션에서는 선택값으로 허용한다.
- 종료일은 `ended`일 때만 의미가 있다.
- 관리계약 상태 변경은 감사 로그 대상이다.
- 기존 건물은 명시적인 관리자 확인 전까지 `none`으로 간주해 잘못된 관리건물 노출을 방지한다.

등록 첫 단계에는 다음 항목을 제공한다.

- `BRING 관리계약 건물` 토글
- 토글이 켜지면 관리 시작일
- 기존 관리계약 수정 화면에서는 상태와 종료일

직원 화면에서 토글을 켜면 `관리계약 확인 요청`으로 저장되고, 관리자 화면에서는 계약 확인 후 `관리 중`으로 승인한다. 화면 문구가 실제 권한과 다른 인상을 주지 않게 한다.

## 5. 지도 정보구조

### 5.1 두 개의 배타적인 탭

기존 `wonju-map.html`의 독립 체크박스 두 개를 다음 탭형 라디오 선택으로 교체한다.

1. `유지보수 업체 지도`
2. `BRING 관리계약 건물`

항상 정확히 하나만 선택되며 네 가지 혼합 상태를 만들지 않는다.

### 5.2 탭별 화면

`유지보수 업체 지도`에서는 다음만 보인다.

- 기존 업체 통계
- 업체 검색, 업종, 출처, 위치 필터
- 업체 목록과 업체 핀
- 업체 범례와 표시 개수

`BRING 관리계약 건물`에서는 다음만 보인다.

- 관리계약 건물 수와 공실 수
- 건물명·주소 검색
- 공실 있음/없음, 촬영 상태 필터
- 관리계약 건물 목록과 건물 핀
- 관리건물 전용 범례와 Firebase 동기화 상태

기존 23개 업체 업종은 유지보수 업체 탭 내부의 하위 필터로 유지한다.

### 5.3 초기 탭과 임베드 동작

- 독립 실행되는 기존 지도는 회귀 위험을 줄이기 위해 `유지보수 업체 지도`를 기본값으로 한다.
- `/field` 내부 iframe에서 `embedded=field`가 있으면 `BRING 관리계약 건물`을 기본값으로 한다.
- 사용자가 바꾼 탭은 기기 로컬 설정으로 기억하되 URL의 명시적 선택이 있으면 URL을 우선한다.
- `embedded=field`는 실제로 사용해 독립 지도의 중복 헤더를 줄이고 내부 플랫폼에 맞는 높이를 제공한다.
- 루트의 `wonju-map.html`과 `data/field-map-model.js`를 정본으로 유지하고 빌드 전 동기화 스크립트로 `company-site/public` 사본을 갱신한다. 생성된 public 사본을 직접 수정하지 않는다.
- 플랫폼 iframe은 개발과 운영 모두 현재 플랫폼과 같은 출처의 `/wonju-map.html`만 사용한다. localhost에서 GitHub Pages 운영 지도로 자동 전환하는 현재 동작은 제거한다.
- 같은 출처의 iframe은 같은 Firebase 프로젝트의 인증 지속상태를 읽고 ID token의 `fieldPlatform` claim을 직접 확인한다. 지도 코드의 이메일 하드코딩 허용목록은 제거한다.
- ID token, refresh token 또는 로그인정보를 URL query, fragment, `postMessage`로 전달하지 않는다.
- 로컬 개발에서 네이버 타일 인증이 되지 않아도 탭, 목록, 필터와 빈/오류 상태는 로컬 정본으로 검증할 수 있어야 한다.
- 운영 배포 전 Firebase Hosting 도메인과 실제 사용자 도메인이 네이버 지도 Web 서비스 URL에 등록되고, 직원 계정 claim 프로비저닝이 완료됐는지를 출시 체크리스트에서 확인한다.

### 5.4 보안과 표시값

관리건물 핀에는 다음 광고 가능 정보만 표시한다.

- 건물명
- 주소
- 현재 공실 수
- 승인된 임대조건 요약
- 주차 요약
- 촬영 완료 상태

건물주 이름·연락처, 메모, 출입방법, 열쇠 위치는 지도 데이터 투영 단계에서 허용목록에 없으므로 절대 포함하지 않는다.

지도 iframe은 원본 `buildings`, `listings`, `media` 경로를 직접 결합하지 않는다. 서버가 다음 읽기 전용 투영을 유지한다.

```text
fieldPlatform/mapProjections/{buildingId}
```

이 경로에는 위 허용목록과 지도 상태, 좌표, 갱신시각만 저장한다. `saveFieldRegistration`, 매물 상태 변경, 미디어 확정, 관리계약 변경 때 서버가 투영을 다시 계산하고, 클라이언트 쓰기는 항상 거부한다. 관리계약이 `active`가 아니게 되면 투영 레코드를 제거하거나 비활성화해 지도 쿼리에서 제외한다.

## 6. 위도·경도 화면 제거

- 건물 등록 화면의 위도 및 경도 `<input>`은 제거한다.
- 주소 중복 확인 성공 시 검색 결과의 좌표를 기존과 동일하게 초안에 기록한다.
- 좌표가 없는 주소는 다음 단계로 진행시키지 않고 `주소 확인으로 지도 위치를 설정해 주세요`라고 안내한다.
- 오류 메시지는 `위도/경도`라는 내부 용어 대신 `지도 위치`라는 사용자 용어를 사용한다.
- 입지 단계의 현재 GPS 거리 경고와 지도 마커 생성은 내부 좌표를 그대로 사용한다.
- 향후 수동 핀 보정은 별도의 지도 조작 UI로 제공하고 숫자 직접 입력은 다시 노출하지 않는다.

## 7. 건물주 메모장

### 7.1 화면 동작

등록 화면 헤더와 진행률 사이에 `건물주 전달사항` 패널을 둔다.

- 모든 7단계에서 같은 컴포넌트가 유지된다.
- 모바일에서는 최근 메모 한 줄과 `메모 추가` 버튼이 보이는 접힌 상태를 기본으로 한다.
- 펼치면 빠른 입력창, 저장 버튼, 최근 메모 목록을 표시한다.
- 화면을 스크롤하면 상단 앱 헤더 아래에 붙어 있어 단계 이동과 긴 양식에서도 다시 찾을 필요가 없다.
- 메모 저장 성공/대기/오류 상태를 명시한다.
- 최신 항목부터 표시하며 전체 이력 화면으로 이동할 수 있다.

### 7.2 데이터 모델

```ts
interface OwnerNote {
  id: EntityId;
  buildingId: EntityId;
  body: string;
  recordedAt: ISODateTime;
  createdAt: ISODateTime;
  createdBy: EntityId;
  createdByName: string;
  archivedAt?: ISODateTime;
  archivedBy?: EntityId;
}

interface OwnerNoteDraft {
  localId: EntityId;
  draftId: EntityId;
  body: string;
  recordedAt: ISODateTime;
}
```

경로는 `fieldPlatform/ownerNotes/{buildingId}/{noteId}`를 사용한다. 아직 저장 전인 신규 건물 메모는 UID로 구분된 로컬 초안에 `draftId`와 함께만 보관한다. 건물 생성 callable이 성공할 때 초안 메모 배열을 함께 보내고 서버가 정식 `buildingId`와 작성자·작성시각을 결합한다. 미저장 메모를 공용 Database 임시 경로에 먼저 쓰지 않는다.

운영 규칙은 다음과 같다.

- 빈 메모와 공백만 있는 메모는 저장하지 않는다.
- 작성 시각과 작성자는 서버가 확정한다.
- 일반 직원은 기존 항목을 덮어쓰거나 삭제하지 않는다.
- 잘못 쓴 항목은 새 정정 메모를 남긴다.
- 관리자는 물리 삭제 대신 보관 처리할 수 있다.
- 메모 본문은 지도, 광고 투영, Drive 광고 설명에서 제외한다.
- `createdByName`은 클라이언트 입력을 신뢰하지 않고 서버의 사용자 프로필에서 결정한다.
- `recordedAt`은 직원이 현장에서 메모한 사건 시각이고 `createdAt`은 서버 수신 시각이다. 오프라인 지연이 있어도 두 값을 모두 보존한다.
- `localId`를 정식 note ID의 멱등 키로 재사용해 저장 재시도 때 같은 메모가 중복 생성되지 않게 한다.
- 본문은 앞뒤 공백 제거 후 1~2,000자로 제한한다. 본문·작성자·서버 생성시각은 생성 뒤 불변이고 관리자의 보관 메타데이터만 별도 갱신할 수 있다.
- 목록의 정식 정렬 기준은 서버 `createdAt`이다. `recordedAt`이 크게 다르면 `오프라인에서 기록됨`과 현장 기록시각을 함께 보여준다.

### 7.3 권한

- 관리자: 모든 건물 메모 읽기 및 보관 처리
- 담당 직원: 배정된 건물 메모 읽기와 추가
- 검토자: 기본적으로 접근 불가
- 미저장 초안: 같은 UID와 같은 초안 ID에서만 접근

## 8. 고정 이전·다음 동작

현재 내용 카드 아래의 `position: sticky` 푸터는 단계별 카드 높이에 따라 화면 안에서 출발 위치가 달라진다. 이를 뷰포트 기준 고정 작업 도크로 교체한다.

### 모바일

- 앱 하단 5개 내비게이션 바로 위에 고정한다.
- iPhone safe-area를 포함한 하단 여백을 적용한다.
- `이전`과 기본 동작 버튼은 언제나 같은 열과 크기를 차지한다.
- 첫 단계의 `이전`은 숨기지 않고 비활성화해 버튼 위치를 유지한다.
- 내용 컨테이너에 작업 도크 높이만큼 하단 패딩을 줘 마지막 입력칸을 가리지 않는다.

### 데스크톱

- 왼쪽 사이드바를 제외한 작업영역 하단 중앙에 고정한다.
- 양식 최대 너비와 동일한 너비 제약을 사용한다.
- 브라우저 확대 및 좁은 데스크톱에서도 가로 스크롤을 만들지 않는다.

주소 확인처럼 단계 내부에 속한 보조 동작은 고정 도크에 넣지 않는다. 도크의 기본 동작은 `다음 단계` 또는 마지막 단계의 `등록 내용 저장` 하나로 유지한다.

## 9. 현장 촬영 경험

### 9.1 입력 방식

사진과 영상은 각각 다음 네이티브 입력을 사용한다.

```html
<input type="file" accept="image/*" capture="environment">
<input type="file" accept="video/*" capture="environment">
```

모바일에서는 후면 카메라 실행을 유도하고, 지원하지 않는 브라우저와 PC에서는 파일 선택기로 동작한다.

동일한 `CaptureGuide`를 두 진입점에서 사용한다.

- 등록 마법사: 아직 정식 저장 전인 현재 건물·호실 초안의 촬영 세션을 사용한다.
- 하단 `촬영` 메뉴: 기존 건물·호실을 먼저 선택하고 새 방문 세션을 생성하거나 진행 중 세션을 재개한다.

하단 촬영 메뉴는 관리계약 건물뿐 아니라 직원에게 배정된 광고 매물도 선택할 수 있다. 지도에 표시되는 관리계약 기준과 촬영 가능한 업무 배정 기준을 혼동하지 않는다.

### 9.2 촬영 구역

초기 구역은 기존 승인 설계를 따른다.

- 건물 공통: 외관, 도로·진입부, 주차, 공동현관, 복도·계단, 분리수거장
- 호실: 전체구조, 창문·채광, 주방, 욕실, 옵션·수납, 보일러·설비
- 증거: 수리 필요부위
- 영상: 10~20초 세로영상

각 구역 카드에는 촬영 예시 문구, 필수 여부, 현재 개수, 촬영 버튼, 미리보기, 재촬영/제외 동작을 제공한다. 건물 공통사진은 같은 건물의 여러 호실에서 재사용 가능하게 표시한다.

### 9.3 미리보기와 재촬영

- 사진은 축소 미리보기로 표시한다.
- 영상은 `controls`, `playsInline`, `preload="metadata"`로 재생한다.
- 세로영상은 메타데이터에서 재생시간과 `videoWidth`/`videoHeight`를 확인한다. 10~20초 또는 세로 방향 기준을 벗어나면 촬영 자체를 버리지 않고 명확히 경고하되, 필수 촬영 완료 판정에는 포함하지 않는다.
- 미리보기 URL은 `URL.createObjectURL`로 만들고 교체, 제거, 컴포넌트 해제 때 반드시 해제한다.
- HEIC처럼 브라우저 미리보기가 어려운 형식은 파일명·용량·촬영완료 상태 카드로 대체한다.
- 같은 파일을 다시 선택할 수 있도록 처리 후 input 값을 초기화한다.
- 업로드 완료 원본은 클라이언트에서 물리 삭제하지 않는다. 재촬영은 새 미디어 ID를 만들고 이전 원본은 광고 제외 또는 대체 상태로 남긴다.

### 9.4 오프라인 대기열

IndexedDB에 다음 저장소를 둔다.

- `drafts`: UID별 버전 있는 양식 초안
- `mediaQueue`: Blob, 미디어 ID, 세션 ID, 구역, 상태, 재시도 횟수
- `syncState`: 마지막 동기화와 오류 상태

`localStorage`에는 `File`, Blob, base64, `blob:` URL을 저장하지 않는다. 초안에는 `captureSessionId`와 직렬화 가능한 첨부파일 설명자만 둔다.

파일 업로드·서버 확정과 Drive 동기화는 서로 다른 상태값으로 유지한다.

```text
uploadState: queued -> uploading -> objectStored -> finalizing -> finalized
                        \-> failed -> queued(retry)

driveSyncState: notRequested -> queued -> syncing -> complete
                                      \-> failed -> queued(retry)
```

브라우저 백그라운드 동기화만 믿지 않는다. 앱이 열려 있고 온라인이 되면 대기열 처리를 자동 재개하며, 사용자가 남은 파일과 재시도 상태를 직접 볼 수 있게 한다.

`uploadBytesResumable`의 바이트 단위 재개는 같은 페이지 세션 안에서만 보장한다. 브라우저나 앱이 다시 시작된 뒤에는 IndexedDB의 원본 Blob으로 업로드를 처음부터 다시 시작할 수 있다. 재시작 전에 안정적인 Storage 경로를 `getMetadata` 또는 서버 대조로 확인한다.

- 같은 크기·MIME·서버 체크섬의 객체가 이미 완성돼 있으면 재업로드하지 않고 서버 확정 단계로 이동한다.
- 경로는 존재하지만 메타데이터가 다르면 덮어쓰지 않고 새 미디어 ID를 발급하거나 관리자 정리 대상으로 둔다.
- 객체는 완성됐지만 클라이언트 상태 갱신이 끊긴 경우도 위 대조로 복구한다.

저장 전에 `navigator.storage.estimate()`로 여유 공간을 확인한다. 특히 대용량 영상은 브라우저 저장공간이 부족할 수 있으므로 필요한 용량을 확보하지 못하면 촬영 완료처럼 표시하지 않고 즉시 안내한다. 영구 저장 권한을 지원하는 브라우저에서는 사용자 동작 뒤 `navigator.storage.persist()`를 요청한다.

브라우저 저장소는 운영체제 정책으로 제거될 수 있으므로 영구 보존을 보장한다고 표현하지 않는다. IndexedDB 트랜잭션 커밋이 성공한 뒤에만 `기기에 저장됨`으로 표시한다. Storage 업로드와 `finalizeFieldMedia` 검증이 끝나면 로컬 Blob은 즉시 제거하고 직렬화 가능한 메타데이터만 Drive 완료까지 남긴다. `QuotaExceededError`가 발생하면 해당 파일을 대기열에 넣지 않고 기기 공간 확보 또는 즉시 온라인 업로드를 안내한다. 오프라인 상태는 `기기 저장·서버 등록 대기`이지 `등록 완료`가 아니다.

### 9.5 Storage 경로

안정적인 UUID와 MIME 허용목록에서 파생한 확장자를 사용한다.

```text
field-media/{uid}/{captureSessionId}/photos/{mediaId}.{ext}
field-media/{uid}/{captureSessionId}/videos/{mediaId}.{ext}
```

사용자 파일명을 경로 결정에 사용하지 않는다. 사진은 25MiB, 영상은 500MiB 제한을 유지한다.

허용 MIME 초기값은 다음으로 제한한다.

- 사진: JPEG, PNG, WebP, HEIC, HEIF
- 영상: MP4, QuickTime, WebM

SVG와 임의의 `image/*`, `video/*`는 허용하지 않는다.

대용량 영상을 통째로 메모리에 올리는 방식의 사전 SHA-256 계산은 금지한다. 업로드 전 중복 후보키는 세션·슬롯·크기·수정시각을 사용하고, 최종 무결성은 Storage 객체의 서버 측 체크섬과 메타데이터로 검증한다. 브라우저에서 증분 해시를 안전하게 계산할 수 있는 파일만 추가 해시를 기록한다.

### 9.6 정식 레코드 확정

촬영 단계에서는 정식 ID가 없는 신규 건물도 파일을 대기열에 보관하거나 세션 경로에 업로드할 수 있다. 마지막 저장 흐름은 다음 순서로 진행한다.

1. `saveFieldRegistration(requestId, draftId, ...)` callable이 건물, 호실, 매물, 최초방문 레코드, 새 건물의 담당 배정, 초안 메모, 계약상태 감사기록을 하나의 Realtime Database 다중경로 갱신으로 생성 또는 갱신한다.
2. 반환된 정식 ID를 대기 중 미디어에 결합한다.
3. 아직 업로드되지 않은 파일을 Storage에 이어서 업로드한다.
4. `finalizeFieldMedia(mediaId, objectGeneration, requestId, ...)` callable이 Storage 객체의 경로, 소유자, generation, 크기, 서버 MIME 판정, GCS 체크섬과 건물 배정을 검증한다.
5. 서버가 미디어 레코드, 감사 로그, Drive outbox 작업을 하나의 Realtime Database 다중경로 갱신으로 확정한다.

정식 미디어와 감사 로그를 클라이언트가 임의로 완료 상태로 쓰지 못하게 한다.

현재 Database 규칙상 일반 직원은 배정이 생기기 전 새 건물을 직접 생성할 수 없으므로 클라이언트의 직접 다중 쓰기로 이 순서를 우회하지 않는다. 두 callable은 요청 ID와 안정적인 entity ID를 멱등 키로 사용하고 동시 호출, ACK 유실, 부분 성공 뒤 재호출에도 건물, 메모, 미디어, 작업이 중복되지 않아야 한다. Drive API 작업은 Database 트랜잭션에 포함될 수 없으므로 outbox worker가 비동기로 수행한다.

## 10. 인증 세션 전달

현재 인증 게이트가 자식 화면에 UID를 전달하지 않는 구조를 개선한다.

- `AuthGate`가 검증된 `FieldSession`을 context 또는 render prop으로 제공한다.
- 초안 키와 IndexedDB 레코드는 UID로 네임스페이스한다.
- 업로드 경로의 UID는 인증 세션에서만 가져온다.
- Firebase 사용자에게 `fieldPlatform` claim이 실제로 없으면 레거시 이메일 예외만으로 촬영 업로드를 허용하지 않는다.
- 권한 프로비저닝 실패와 네트워크 오류를 구분해 안내한다.
- 인증된 앱 셸을 안전하게 캐시하는 `/field` 전용 service worker를 등록하되 Firebase 응답, 미디어 응답, 보안정보, POST 요청은 캐시하지 않는다.
- custom claim뿐 아니라 `fieldPlatform/users/{uid}/enabled === true`를 rules와 callable에서 매 요청 확인한다. 관리자가 계정을 비활성화하면 refresh token을 폐기하고 다음 요청부터 차단한다.
- 로그아웃 또는 계정 전환 전에 미업로드 초안과 미디어 개수를 보여주고 확인을 받는다. 다른 UID로 로그인하면 이전 UID의 IndexedDB 레코드는 목록·미리보기·업로드에서 완전히 숨긴다.

공용 휴대전화에서 다른 직원이 로그인했을 때 이전 직원의 초안이나 미디어가 노출되지 않아야 한다.

## 11. 보안 규칙 변경

### Realtime Database

- 관리계약 상태 enum과 날짜 형식을 검증한다.
- 건물주 메모는 담당 배정 기반 읽기/추가만 허용한다.
- 기존 메모 덮어쓰기와 직원 삭제를 차단한다.
- 미디어 전체 스키마, enum, 진행률 범위, 경로/UID/세션 일치를 검증한다.
- 미디어 확정, 감사 로그, Drive 작업은 서버만 쓴다.
- `mapProjections`는 인증된 내부 사용자만 읽고 서버만 쓴다.

### Storage

- 엄격한 MIME 허용목록과 기존 용량 제한을 동일하게 적용한다.
- 경로 세그먼트와 UUID 형식을 검증한다.
- 완성 경로는 create-only로 만들어 덮어쓰기를 막는다.
- 삭제는 관리자 정리 또는 수명주기 정책으로만 수행한다.
- 정식 레코드와 결합되지 않은 세션 객체에는 생성시각 메타데이터를 두고, 서버 정리 작업이 보존기간이 지난 고아 업로드만 제거한다.
- staging 객체는 업로더와 서버만 읽을 수 있다. 현재처럼 reviewer/admin이 모든 사용자의 미확정 경로를 직접 읽는 규칙은 제거한다.
- 확정된 미디어 열람은 서버가 현재 건물 배정 또는 검토자 권한을 다시 확인한 뒤 발급하는 짧은 수명의 접근권한으로 처리한다.
- 공개 장기 `getDownloadURL`을 일반 공유 수단으로 사용하지 않는다.
- Functions callable은 App Check를 검증하고 사용자·세션별 호출량 제한을 적용한다. 로컬 에뮬레이터와 승인된 운영 앱에 대한 App Check 설정을 배포 체크리스트에 포함한다.

## 12. 기존 데이터 마이그레이션

- 기존 건물에 `managementContract`가 없으면 `none`으로 해석한다.
- 기존 지도 레코드는 자동으로 관리계약 건물이 되지 않는다.
- 기존 로컬 초안은 `draftVersion` 마이그레이션 함수로 새 필드를 채운다.
- 좌표 값은 보존하고 화면 필드만 제거한다.
- 기존 미디어가 없으므로 촬영 배열은 빈 값으로 시작한다.
- 기존 유지보수 업체 데이터와 필터 결과는 그대로 유지한다.

## 13. 오류 처리

- 주소 확인 실패: 좌표 숫자를 요구하지 않고 주소 재확인 동작을 제시한다.
- 메모 저장 실패: 입력 내용을 지우지 않고 로컬 대기 상태로 둔다.
- 카메라 취소: 오류로 표시하지 않고 이전 화면을 유지한다.
- MIME/용량 초과: 업로드 전에 허용 형식과 크기를 구체적으로 안내한다.
- 오프라인: 촬영 완료와 서버 업로드 완료를 서로 다른 상태로 표시한다.
- 업로드 중단: 같은 페이지에서는 바이트 전송을 재개하고, 앱 재실행 뒤에는 같은 미디어 ID의 완성 객체를 대조한 후 필요할 때만 원본 Blob으로 처음부터 다시 전송한다.
- Firebase 권한 실패: 빈 지도 또는 업로드 완료처럼 보이지 않게 `권한 등록 필요`를 명시한다.
- 일부 파일 실패: 성공한 파일을 다시 올리지 않고 실패한 파일만 재시도한다.

## 14. 테스트 전략

테스트 주도 방식으로 각 기능의 실패 테스트를 먼저 작성한다.

### 컴포넌트

- 위도·경도 라벨/입력이 화면에 없고 주소 확인 뒤 내부 좌표는 유지된다.
- 건물주 메모 패널이 모든 단계에서 유지된다.
- 메모가 날짜·작성자별로 누적되고 공백은 거부된다.
- 이전·다음 도크가 단계별로 동일한 DOM 위치와 버튼 슬롯을 유지한다.
- 사진/영상 input의 `accept`와 `capture` 속성이 정확하다.
- 미리보기, 재촬영, 제외, object URL 정리가 동작한다.
- 저장된 JSON에 File, base64, blob URL이 없다.

### 데이터와 지도

- `active` 관리계약 건물만 관리건물 마커가 된다.
- `none`, `paused`, `ended`, archived 건물은 제외된다.
- 두 지도 모드가 동시에 활성화되거나 모두 비활성화되지 않는다.
- 독립 지도와 `/field` 임베드의 기본 탭이 각각 기대값과 같다.
- 보안 필드와 건물주 메모가 팝업 모델에 나타나지 않는다.

### 오프라인과 업로드

- IndexedDB 재생성 후 Blob과 대기 상태가 복원된다.
- 저장공간 부족과 영구 저장 권한 거절 시 데이터가 저장됐다고 거짓 표시하지 않는다.
- UID 전환, 로그아웃 확인, IndexedDB 스키마 업그레이드에서도 다른 계정의 파일이 노출되거나 사라지지 않는다.
- 안정적인 경로, MIME/용량 검증, 해시와 중복방지가 동작한다.
- 업로드 진행률, 취소, 실패, 온라인 복귀 재시도가 동작한다.
- 같은 페이지에서는 중단 지점부터 이어지고, 앱 재실행 뒤에는 Blob 재업로드 또는 완성 객체 대조로 복구된다.
- Storage 완료 전에는 서버 확정이나 Drive 작업이 생성되지 않는다.
- callable 재호출은 미디어·감사·Drive 작업을 중복 생성하지 않는다.
- `saveFieldRegistration` 재호출은 새 건물, 담당 배정, 초안 메모를 중복 생성하지 않는다.
- 객체 저장 직후 앱 종료, finalizer 동시 호출, ACK 유실, 기존 객체 불일치 상황을 각각 복구하거나 안전하게 중단한다.

### 규칙과 권한

- 관리자, 담당 직원, 미배정 직원, 검토자, 익명 사용자의 읽기/쓰기를 각각 검증한다.
- 메모 수정·삭제, Storage 덮어쓰기·삭제, 잘못된 MIME/경로를 거부한다.
- `mapProjections`에 대한 모든 클라이언트 쓰기를 거부하고 비관리 건물을 투영하지 않는다.
- 레거시 이메일 예외만 있고 claim이 없는 사용자의 업로드를 거부한다.
- 비활성화된 사용자와 폐기 전 오래된 token의 callable/Database/Storage 접근을 검증한다.

### 브라우저와 실기기

- 320×568 및 일반 모바일 너비에서 7단계 각각의 처음·중간·끝 스크롤 위치를 검사한다.
- 작업 도크 하단이 모바일 내비게이션과 safe area 위에 일정 오차 이내로 정렬되고 마지막 입력칸이 도크 위까지 스크롤되는지 확인한다.
- 펼친 고정 메모가 양식을 덮지 않고 가로 overflow를 만들지 않는지 확인한다.
- 입력 중 가상 키보드가 열렸을 때 포커스된 입력과 다음 버튼을 사용할 수 있는지 확인한다.
- `capture` 속성 자동테스트 외에 실제 iPhone Safari/PWA와 Android Chrome/PWA에서 후면 카메라, 사진, 영상, 취소, 재촬영을 수동 검증한다.

## 15. 승인 기준

다음 조건을 모두 만족하면 이번 변경을 완료로 본다.

1. 지도에서 두 탭이 명확히 분리되고 관리계약 `active` 건물만 두 번째 탭에 보인다.
2. 주소 확인 후 지도 핀은 정상 생성되지만 등록 화면에 위도·경도 입력은 없다.
3. 어느 단계에서든 건물주 메모를 추가할 수 있고 작성자와 시각이 보존된다.
4. 모바일에서 이전·다음 버튼 위치가 단계와 스크롤에 따라 움직이지 않고 마지막 입력칸을 가리지 않는다.
5. iPhone Safari/PWA와 Android Chrome/PWA에서 사진 및 영상을 촬영할 수 있다.
6. 저장공간이 허용되는 범위에서 오프라인 촬영물이 IndexedDB에 보존되고, 앱 재접속과 네트워크 복구 뒤 재업로드 또는 완성 객체 대조가 수행된다.
7. 업로드된 미디어가 정식 건물·호실·방문과 연결되고 권한 없는 계정은 읽을 수 없다.
8. 건물주 메모와 보안정보가 지도 팝업 및 광고 투영에 포함되지 않는다.
9. 기존 유지보수 업체 지도 검색, 필터, 링크와 기존 FM 기능의 회귀 테스트가 통과한다.

## 16. 이번 구현 범위 밖
