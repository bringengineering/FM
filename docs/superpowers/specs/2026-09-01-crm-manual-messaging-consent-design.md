# BRING CRM 수동 메시지·마케팅 동의 관리 설계

## 1. 목적

직원이 고객 상세 또는 전용 메시지 화면에서 필요한 안내를 즉시 발송하고, 청소만 이용하는 고객에게도 적법한 범위에서 추가 서비스를 안내할 수 있게 한다. 정보성 안내와 광고성 영업은 같은 화면에서 작성하되 서로 다른 발송 정책을 적용한다.

## 2. 핵심 원칙

- 발송 목적은 `정보성` 또는 `광고성` 중 하나를 반드시 선택한다.
- 정보성 메시지는 연결된 업무 근거와 승인된 알림톡 템플릿이 있어야 한다.
- 광고성 메시지는 선택한 채널의 유효한 마케팅 수신 동의가 없으면 UI와 서버에서 모두 차단한다.
- 과거 거래, 카카오 채널 친구 여부, 고객 등록 사실만으로 동의를 추정하지 않는다.
- AI는 문구 초안만 만들 수 있으며 승인 템플릿과 정책 검사를 우회할 수 없다.
- 외부 전송 직전에 수신자, 목적, 문구, 비용 가능성을 직원이 다시 확인한다.
- API 키와 공급자 비밀값은 EXE, Firebase 데이터, GitHub 저장소에 저장하지 않는다.

## 3. 사용자 화면

### 3.1 고객 상세

고객 상세에 다음 두 영역을 추가한다.

1. `메시지 보내기`: 선택한 고객을 수신자로 하여 작성 화면을 연다.
2. `수신 동의`: 카카오·SMS별 상태, 동의일, 철회일, 수집 경로, 동의 문구 버전, 증빙을 보여준다.

관리자와 일반 작성 가능 사용자는 증빙을 포함해 동의를 등록할 수 있다. 기존 동의를 정정하거나 철회 기록을 되돌리는 작업은 관리자만 가능하다. 조회 전용 사용자는 전화번호가 마스킹된 이력만 본다.

### 3.2 고객 메시지 화면

운영 폴더에 `고객 메시지` 메뉴를 추가한다. 화면은 세 부분으로 구성한다.

- 작성함: 고객, 발송 목적, 세부 유형, 연결 업무, 템플릿, 변수, 채널을 선택하고 미리 본다.
- 발송 가능 여부: 허용·차단과 그 이유를 즉시 표시한다.
- 발송 이력: 요청, 접수, 전달 성공, 실패, 차단 상태를 검색하고 새로 확인한다.

V1은 실수 위험을 줄이기 위해 1명씩 수동 발송한다. 대량 발송과 예약 발송은 포함하지 않는다. 기존 입금 안내 자동화는 변경하지 않는다.

## 4. 분류와 템플릿

### 정보성 유형

- 청소 예정일 안내
- 입주청소 일정 확인
- 고객이 요청한 견적·상담 후속 안내
- 작업 완료 안내
- 입금·미납 안내

정보성 발송은 고객이 먼저 요청했거나 CRM에 존재하는 계약, 작업 일정, 상담 또는 입금 기록을 `sourceType`과 `sourceId`로 연결해야 한다.

### 광고성 유형

- 청소 서비스 재이용 안내
- 건물관리 추가 서비스 제안
- 프로모션·혜택 안내

광고성 발송은 채널별 수신 동의가 `granted`이고 철회되지 않았으며 증빙이 있어야 한다. 광고성 알림톡을 정보성 템플릿으로 보내거나, 카카오 실패를 별도 SMS 동의 없이 문자로 대체하지 않는다.

템플릿은 클라이언트 자유 입력값이 아니라 서버의 허용 목록에서 선택한다. 각 항목은 코드, 버전, 목적, 채널, 필수 변수와 활성 여부를 가진다.

## 5. 데이터 구조

### 고객 동의 `customers/{customerId}/messageConsents/{channel}`

- `status`: `not_collected | granted | withdrawn`
- `consentedAt`, `withdrawnAt`
- `source`: `contract | form | qr | phone | manual`
- `consentTextVersion`
- `evidenceRef`, `evidenceUrl`
- `recordedBy`, `recordedAt`, `updatedAt`

철회는 기존 동의를 덮어 지우지 않고 최신 상태와 감사 로그를 함께 남긴다.

### 발송 기록 `crmShared/messageDeliveries/{requestId}`

- `customerId`, `channel`, `purpose`, `category`
- `sourceType`, `sourceId`
- `templateCode`, `templateVersion`, `variables`
- `provider`, `providerMessageId`
- `status`: `blocked | queued | accepted | delivered | failed`
- `policyCode`, `errorCode`
- `requestedBy`, `requestedAt`, `sentAt`, `deliveredAt`
- `estimatedCost`, `updatedAt`

전화번호 원문과 완성 메시지 본문은 이력에 중복 저장하지 않는다. 화면에는 고객 원본과 템플릿 변수로 미리보기를 재구성하며, 공급자 응답 본문도 저장하지 않는다.

## 6. 서버 처리

Apps Script 자동화 엔드포인트에 닫힌 액션 두 개를 추가한다.

- `sendCustomerMessage`
- `getCustomerMessageDeliveryStatus`

발송 순서는 다음과 같다.

1. 로그인 세션과 `admin | member` 역할을 재검증한다.
2. 요청 ID 중복 여부를 확인해 같은 요청의 재전송을 막는다.
3. 고객과 연락처, 템플릿, 연결 업무를 서버에서 다시 읽는다.
4. 목적별 정책과 채널별 동의를 서버에서 판정한다.
5. 허용된 알림톡 공급자 어댑터를 호출한다.
6. 민감한 공급자 응답을 제거한 상태만 공용 이력에 기록한다.
7. 상태 조회 역시 요청자 권한과 해당 이력을 확인한 후 실행한다.

설정 또는 승인 템플릿이 없으면 실패 닫힘 방식으로 중단한다. 정보성 메시지의 기존 SENS 대체 발송은 해당 템플릿 설정이 명시적으로 허용한 경우만 유지한다. 광고성 메시지는 채널별 동의를 각각 확인한다.

## 7. 권한

- `admin`: 템플릿 설정, 동의 정정·철회, 모든 적격 메시지 발송과 이력 조회
- `member`: 증빙이 있는 신규 동의 등록, 적격 메시지 발송, 업무상 필요한 이력 조회
- `viewer`: 마스킹된 상태와 이력 조회만 가능
- 마케팅 전용 제한 계정: 기존 CRM 권한 모델에 따라 고객 원본을 수정하지 않고, 동의된 광고성 발송만 가능

## 8. 오류와 안전장치

- 연락처 없음, 근거 업무 없음, 동의 없음, 철회됨, 템플릿 비활성, 역할 부족을 서로 다른 코드로 표시한다.
- 발송 버튼은 차단 사유가 해소될 때까지 비활성화한다.
- 네트워크 재시도는 동일한 `requestId`를 사용한다.
- 공급자 장애가 발생해도 성공으로 표시하지 않는다.
- 기존 입금 안내와 민원 알림톡 경로는 회귀 테스트로 보호한다.
- 실제 외부 발송은 사용자가 CRM 확인창에서 누른 경우에만 실행된다.

## 9. 검증 기준

- 동의 없는 건물관리 영업 메시지는 UI와 서버에서 모두 차단된다.
- 청소 일정에 연결된 정보성 안내는 승인 템플릿으로 발송 요청할 수 있다.
- 철회 직후 열려 있던 작성 화면에서도 서버가 재검사하여 차단한다.
- 같은 요청 ID로 두 번 호출해도 공급자 전송은 한 번만 일어난다.
- 조회 전용 계정은 발송하거나 동의를 변경할 수 없다.
- 발송 이력에는 API 키, 전체 공급자 응답, 불필요한 전화번호·본문이 없다.
- 기존 입금 안내, 민원 안내, 자동 업데이트 테스트가 그대로 통과한다.

## 10. 배포 범위

데스크톱 CRM, Firebase 공유 데이터 규칙, Apps Script 메시지 액션을 함께 변경한다. Functions와 Hosting은 배포하지 않는다. 실제 운영 활성화에는 승인된 카카오 템플릿 코드와 현재 Apps Script 배포본 갱신이 필요하며, 템플릿이 준비되지 않은 광고성 기능은 비활성 상태로 공개한다.
