# CRM 3D 건물·설비지도 통합 설계

상태: 통합 방향 승인 후 작성한 구체 설계. 구현·운영 배포 전 검토용.

## 1. 기준과 보존 범위

- 원본: bringengineering1008-pixel/FM, codex/building-atlas-company, f5f43f7971bd7043435ad149dea9b1eab341a188의 building-operations. PR #2는 열린 상태이며 병합하지 않는다.
- 적용 대상: bringengineering/FM의 데스크톱 CRM. 운영 기준은 1889ef252c10e2bdf6b5de46329aae2cf240b482(CRM 1.42.0 소스).
- 이번 작업은 두 저장소 전체를 합치는 작업이 아니다. 3D 모듈과 라이선스만 출처를 기록하여 가져오고, 기존 CRM 코드에는 필요한 진입·수명주기·저장 연결만 추가한다.
- 원본 경로와 루트의 미커밋 파일·사진·마케팅 자료는 수정하거나 포함하지 않는다.
- 설계 브랜치: codex/crm-building-atlas-integration. 운영 반영 전 원격 소스가 달라지면 차이를 재검토한다.

## 2. 목표 화면

CRM의 건물관리에서 ‘3D 설비지도’를 열며, 같은 화면은 CRM 메뉴에서도 접근한다. 별도 창·외부 사이트·중첩 iframe 없이 기존 CRM의 본문 영역에 표시한다.

- 상단: CRM 건물 선택, 현장 확인/임시 모형 안내, 서버 저장 상태, 수동 새로고침
- 왼쪽: 설비 검색, 데이터 영역, 레이어
- 중앙: Three.js 3D, 층 선택, 외벽 투명, 층 분리, 회전·확대, 평면 배치
- 오른쪽: 선택 설비의 정보·사진·연결·점검 이력과 수정 동선
- 좁은 화면: 3D 위/설비 상세 아래, 필터 접기. 기존 CRM 메뉴를 두 벌로 표시하지 않는다.

빈 CRM 건물은 ‘모형 만들기’를 확인한 뒤 빈 모형을 생성한다. 층·치수 기본값은 반드시 임시라고 표시한다. 예시 다가구/상가는 연습 공간으로 유지하고 운영 건물에 자동 복사하지 않는다.

## 3. 유지할 기능과 변경점

3D 회전·층/레이어·설비 선택, 10개 영역, 설비 카탈로그, 설비/층 복제, 평면도 배치, 사진·근거·배관 경로, 점검 일정/이력, 둘러보기, 예시 건물, 보고서 및 JSON 백업 기능을 유지한다.

현재 app.mjs의 document 전역 ID 접근과 localStorage 직접 저장은 CRM 통합 경계에서 제거한다. 컴포넌트는 전달받은 루트 안에서만 요소를 찾으며 mount/unmount 계약을 갖는다. 화면 이탈 시 이벤트, ResizeObserver, 애니메이션, WebGL 자원을 정리한다. 기존 기능은 새 UI에 맞춰 연결하되 무관한 CRM 리팩터링은 하지 않는다.

저장은 비동기 어댑터로 교체한다. 성공 응답 전에 ‘서버 저장 완료’를 표시하지 않는다. 예시/연습 모드의 저장은 회사 데이터와 분리하며 명확히 표기한다.

## 4. 건물 연결

정식 지도는 CRM buildingId 하나에 귀속된다. 건물명·주소는 표시값이며 이름 변경으로 새 지도를 만들지 않는다. 기존 모형의 이름과 주소가 같더라도 자동 병합하지 않는다.

기존 JSON은 검증 → 건물 목록/내용 미리보기 → 대상 CRM 건물 선택 → 사용자 확인 순서로 가져온다. 이미 지도가 있는 대상은 기본 동작을 취소로 두며 교체 전에 백업과 명시적 확인을 요구한다. 다른 건물은 건드리지 않는다. 원본 브라우저 저장소를 자동 탐색하거나 삭제하지 않는다.

CRM 건물의 연락처·계약·가격·개인 메모는 3D 지도에 자동 복사하지 않는다. 설비지도에서 입력하는 운영 기록은 기존 CRM 고객/계약 원장을 수정하지 않는다.

## 5. 공동 저장과 권한

정식 데이터는 기존 bring-fm 인증을 사용해 건물별 별도 지도 경로로 저장한다. crmShared/data 전체 저장에 섞지 않는다. 제안 경로는 기존 회사 데이터 루트 아래 buildingAtlas/{buildingId}이며 기존 database.rules.json의 루트와 직원 허용 목록에 맞춰 구현한다.

전달 인터페이스는 건물 하나 읽기, 검증된 건물 하나 저장으로 한정한다. renderer에는 토큰이나 임의 DB 경로 요청 기능을 주지 않는다. Electron main/preload에서 기존 세션 검증과 요청 경로 제한을 적용한다.

- 활성화·인증된 회사 직원만 읽기. admin/member만 쓰기, viewer는 조회 전용.
- marketing-only 등 기존 업무 접근 제한도 유지한다. 직원 권한이 없으면 저장 대신 오류 안내, 권한 완화 금지.
- 건물 존재 여부, 요청 buildingId와 저장 대상 일치, schemaVersion, revision, updatedBy, 모델 필드/개수/좌표/파일 유형을 검증한다.
- 기존의 ETag 조건부 저장 방식을 사용한다. 두 직원이 동시에 수정하면 먼저 저장된 버전을 덮어쓰지 않고 충돌 안내와 작성 내용 보존을 제공한다.
- 오프라인이면 작성 중/저장 실패를 구분하고 재시도한다. 자동 무조건 재전송이나 충돌 덮어쓰기는 하지 않는다.
- 사진·평면도는 기존 모델의 지원 형식을 유지하되 크기/형식을 검증한다. 업로드 한도 초과는 기존 데이터와 초안을 보존한 채 거절한다. 한도는 새 경로의 규칙 테스트와 가져오기 테스트에서 검증한다.
- 계정/권한 변경과 로그아웃 시 메모리 지도 및 보류 응답을 폐기한다. 이전 계정의 지도를 다음 계정에 보여주지 않는다.
- 정식 회사 서버 저장을 localStorage 성공 메시지로 대체하지 않는다.

공동 저장을 위해 새 지도 경로의 DB 규칙이 필요하다. 기존 경로의 규칙을 완화하지 않는다. 규칙은 로컬 에뮬레이터에서 개발·검증하고 운영 반영 승인은 따로 받는다. Functions/Hosting 배포나 요금제 변경을 이 작업의 전제로 삼지 않는다.

## 6. 실패·안전 안내

조회 중, 빈 지도, 접근 불가, 오프라인, 읽기 실패, 저장 중, 서버 저장 완료, 충돌, 크기 초과를 별도로 표시한다. 조회 실패를 빈 지도로 간주해 새 데이터를 덮어쓰지 않는다.

WebGL 실패 시 목록과 상세 정보는 사용할 수 있도록 한다. 임시 모형·추정 위치·예시 배관은 시공, 차단, 화재 대응 또는 구조 안전 판단의 근거가 아니라고 표시한다. 위치 이동 시 현장 확인 표시와 연관 경로 확인을 해제하는 원본 동작을 유지한다. 실제 센서, AI 진단, 실측 도면 자동 생성은 이번 범위에 없다.

## 7. 구현 단위

1. 원본 3D 모듈 보존 및 CRM 루트에 한정된 화면 수명주기·비동기 저장 인터페이스 분리
2. 건물 ID 연결·미리보기 가져오기·정식/연습 모드 분리
3. 세션 검증·건물별 읽기/조건부 저장·에뮬레이터 규칙 검증
4. 기존 CRM 메뉴/건물관리 연결과 통합 화면 테스트
5. 사용자 확인용 가상 데이터 실행본·검증 보고서 제출, 이후 별도 배포 승인

부분 구현을 최종 완료라고 보고하지 않는다. 특히 공동 저장이 미연결이면 ‘여러 직원 사용 가능’이라고 하지 않는다.

## 8. 합격 기준과 현재 근거

- 원본 단위 테스트 29개를 이번 검토에서 직접 실행: 모두 통과. 브라우저 테스트 12개 통과는 원본 PR의 보고이며 이 통합본의 증거로 대신하지 않는다.
- 통합 후 원본 기능 12개 흐름을 실제 CRM 호스트에서 확인. desktop 1280px와 390px, WebGL 실패, 메뉴 왕복 반복을 포함한다.
- 3D 열기/닫기, 층/필터/카메라 조작만으로 서버 쓰기 0회.
- 같은 건물 ID의 이름 변경은 기존 지도 유지. 같은 이름의 다른 건물은 분리.
- 독립된 두 테스트 클라이언트에서 저장 후 다시 읽어 동일 revision/내용 확인. 동시 수정은 충돌로 처리.
- viewer/비회원/비활성/다른 세션/marketing-only 쓰기 거절을 서버 규칙 및 IPC 테스트로 확인.
- 잘못된 백업, 과대 파일, 용량 초과, 네트워크 실패에도 원본 데이터 보존.
- 기존 CRM 전체 테스트와 새 지도 테스트, DB 규칙 에뮬레이터 테스트 통과.
- 실제 고객 데이터 없이 가상 사례로 검증하고 변경 파일·테스트 결과·남은 제한을 제출.
- 배포 완료 주장은 승인된 운영 반영 및 실제 배포 확인 후에만 한다.

## 검토 결론

단순 링크 연결은 공동 관리 목표를 충족하지 못하고, 전체 재개발은 기존 기능을 불필요하게 잃는다. 원본 렌더링/모델을 보존하면서 CRM 호스트와 저장 어댑터를 교체하는 통합안을 채택한다. 구체 설계 검토 후 구현 계획과 개발로 넘어간다.
