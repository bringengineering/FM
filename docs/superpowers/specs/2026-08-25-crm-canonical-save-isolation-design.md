# CRM 일반 저장의 정식 건물 데이터 격리 설계

## 문제

CRM 1.10.0에서 상담 기록처럼 건물과 무관한 자료를 저장할 때도 렌더러의 전체 저장본을 서버와 비교한다. 로컬에 남은 `buildings` 또는 `salesUnits`가 서버의 정식 원본과 조금이라도 다르면 일반 저장 패치에 정식 컬렉션 변경이 포함되고, 보호장치가 `CANONICAL_COMMIT_REQUIRED`로 전체 저장을 거부한다. 그 결과 상담 기록은 화면에는 보이지만 서버에 저장되지 않는다.

## 목표

- 상담·고객·일정 등 일반 저장이 정식 건물 데이터 차이 때문에 실패하지 않는다.
- `buildings`와 `salesUnits`는 기존 정식 저장 API로만 변경한다.
- 일반 저장이 로컬의 오래된 정식 데이터를 서버에 덮어쓰지 않는다.
- 서버 저장이 실패한 상담 기록을 성공으로 표시하지 않는다.

## 저장 경계

`pushStore`와 대기 저장 재전송은 서버의 현재 정식 컬렉션을 권위 원본으로 사용한다. 일반 저장용 목표 상태를 만들 때 `buildings`와 `salesUnits`는 렌더러 입력이 아니라 현재 서버 값으로 치환한 뒤 차이를 계산한다. 따라서 일반 컬렉션 변경만 PATCH되고 정식 컬렉션은 패치에 나타나지 않는다.

정식 건물·영업호실 변경은 기존 `commitCanonicalCrmEntity` 경로를 유지한다. 이 경로는 현재 작업자, 버전 충돌, 감사 기록을 검증하므로 보호 수준을 낮추지 않는다.

## 오프라인·대기 저장

오프라인 대기 자료에도 상담·고객 변경은 보존한다. 재연결 시점의 최신 서버 정식 컬렉션을 기준으로 다시 합성하여 일반 변경만 반영한다. 오래된 대기 저장이 최신 건물·영업호실을 되돌릴 수 없게 한다.

## 오류 처리와 화면

일반 변경까지 서버 저장에 실패하면 기존처럼 오류·대기 상태를 표시한다. 정식 컬렉션 차이를 단순히 무시하는 대신 서버 원본으로 명시적으로 재기준화하고, 저장 성공 후 로컬 캐시와 렌더러도 서버 정식 원본으로 수렴시킨다.

## 검증

자동 테스트는 다음을 고정한다.

1. 로컬 건물이 서버보다 오래된 상태에서도 새 상담 기록과 고객 수정은 저장된다.
2. 같은 요청에서 `buildings`와 `salesUnits` 패치는 전송되지 않는다.
3. 저장 후 반환값은 서버의 정식 건물·영업호실을 유지한다.
4. 오프라인 대기 저장 재전송도 같은 원칙을 따른다.
5. 정식 저장 API와 기존 전체 데스크톱 회귀 테스트가 모두 통과한다.

## 배포와 현재 자료 복구

수정은 다음 미사용 CRM 패치 버전으로 자동 배포한다. 현재 실행 중인 1.10.0 화면의 미저장 상담 기록은 앱을 닫지 않은 상태로 유지한다. 새 버전 적용 전에는 화면의 두 기록 내용을 별도 보존하고, 업데이트 후 서버 저장 및 다른 세션 조회까지 확인한다.
