# 현장앱(FIELD) 복구 결정안 — 소유자 결정 필요

*2026-09-04 조사 · 아래 근거는 모두 저장소 코드에서 직접 확인한 것입니다.*

## 요약

**배포 중인 현장앱은 프로덕션에서 업무 목록조차 불러올 수 없습니다.**
"촬영·검수 버튼이 안 보인다"는 증상의 실제 원인은 버튼이 아니라,
앱 전체가 배포되지 않는 백엔드에 의존하고 있다는 점입니다.

## 확인된 사실 (근거)

| # | 사실 | 근거 |
| --- | --- | --- |
| 1 | 배포되는 현장앱은 v2 하나뿐 | `company-site/app/field/page.tsx` → `<FieldV2App />` 만 렌더 |
| 2 | v2 는 업무 목록을 **Cloud Function** 으로 받는다 | `app/field/lib/v2/field-v2-api.client.ts:155` `httpsCallable("listFieldOperationsWorkspace")` |
| 3 | 그 Cloud Function 은 **배포되지 않는다** | `release/firebase-targets.json` `functionsDeploymentAllowed: false` + 전 함수 `archivedFunctionNames` 등재 / 릴리스는 `deploy --only database` 만 실행 (`.github/workflows/crm-release.yml:360`) / `docs/crm-automatic-release.md:15` "Cloud Functions를 배포하지 않습니다… 배포 대상이 아닙니다" |
| 4 | v2 데이터 트리는 클라이언트가 읽을 수도 없다 | `database.rules.json` 의 `fieldPlatform/v2` → `.read: false`, `.write: false` |

→ **데이터 경로가 두 방향 모두 막혀 있습니다.** 함수는 배포되지 않고, 직접 접근은 규칙이 막습니다.

### 왜 배포되지 않는가 — 확인됨

**Firebase 프로젝트 `bring-fm` 이 Spark(무료) 요금제이기 때문입니다. Spark 에서는 Cloud Functions 자체를 구동할 수 없습니다.**

- `docs/crm-automatic-release.md:3` — "이 자동 릴리스는 Firebase Spark 요금제에서 동작하도록 Realtime Database Rules와 Windows 설치 파일만 다룹니다. Cloud Functions와 Hosting은 자동 배포하지 않습니다."
- `docs/field-platform-managed-map-release.md:39` — "The CRM release workflow is Spark-compatible and deploys Realtime Database Rules only."
- `.github/workflows/crm-release.yml:111` — "Validate the Spark-only automatic Database Rules target"
- PR #37 본문 — "The CRM-to-FIELD Cloud Functions remain undeployed because the `bring-fm` Firebase project is on Spark."

즉 배포 차단은 누군가의 취향이 아니라 **요금제 제약을 코드로 고정해 둔 것**입니다.
따라서 Functions 에 의존하는 어떤 복구안(A·B·D)도 **Blaze 유료 전환 없이는 성립하지 않습니다.**

## 반면 v1 은 살아 있습니다

이전 버전 현장앱(`app/field/FieldApp.tsx` 외)은 **Cloud Function 없이 동작하도록 이미 전환 완료**돼 있고,
촬영·검수·오프라인 업로드가 구현돼 있으며 테스트도 통과합니다.

- RTDB 직접 접근: `app/field/lib/direct-field-api.client.ts`
- Google Drive 브라우저 직접 업로드: `app/field/lib/direct-drive-media-upload.ts`
- 촬영 화면: `app/field/components/CaptureWorkspace.tsx`, `CaptureGuide.tsx`
- 테스트: `tests/field/capture-workspace.test.tsx`, `capture-components.test.tsx`, `direct-*.test.ts` 등 다수 통과 중

문제는 품질이 아니라 **이 코드가 화면에 연결돼 있지 않다**는 것입니다.

## 선택지

| 안 | 내용 | 공수 | 위험 |
| --- | --- | --- | --- |
| **A** | v2 에 촬영·검수 화면을 새로 만든다 | 2~4주+ | 완성해도 함수 미배포로 **여전히 동작 안 함** |
| **B** | v1 촬영 화면을 v2 로 포팅 | 3~5주 | A 의 문제 전부 + 테스트 1,600줄 재작성 |
| **C** | **진입점 분기** — 현장 직원 폰은 v1, CRM 임베드는 v2 유지 | 약 1일 | 의도적 아키텍처 가드를 되돌림(아래) |
| **D** | Blaze 전환 + Functions 배포 복원 + v2 촬영 백엔드 신규 구현 | 4~8주 | **유료 전환 필요.** 저장소의 모든 정책 문서·테스트가 반대 방향을 강제 |

## 권고: C안 (진입점 분기)

```
?embedded=crm · desktop_handoff  → FieldV2App  (CRM 데스크톱 임베드, 현 상태 유지)
그 외 (현장 직원 폰 PWA)          → FieldApp    (v1, 촬영·검수 동작)
```

**왜 C인가**
1. 현장 직원이 잃어버린 기능이 v1 에 완성·테스트 통과 상태로 이미 있습니다.
2. Google Drive 업로드 토큰은 v1 로그인 경로에서만 발급됩니다 — 어떤 안이든 결국 v1 인증을 거쳐야 합니다.
3. CRM 임베드는 v2 그대로 두어 새 회귀를 만들지 않습니다.
4. A·B 는 "배포되지 않는 백엔드 위에 새 UI 를 얹는" 작업이라 완료해도 현장이 복구되지 않습니다.

## ⚠️ 승인 전에 확인이 필요한 것

C안은 **의도적으로 잠가둔 결정을 되돌립니다.** (다만 위에서 확인했듯 그 결정의 뿌리는
아키텍처 취향이 아니라 Spark 요금제 제약입니다.)
`tests/field/field-v2-entry.test.ts` 가 "`page.tsx` 는 `./FieldApp` 을 참조하지 않는다"를
테스트로 고정해 두었습니다. 즉 누군가 "현장앱은 v2 단일 아키텍처로 간다"고 결정한 흔적입니다.
**그 결정을 왜 했는지 아는 사람의 승인 없이 뒤집으면 안 됩니다.**

또한 아래는 코드만으로 확인할 수 없어 **운영 확인이 필요**합니다.

| 항목 | 내용 |
| --- | --- |
| 커스텀 클레임 | v1 은 `fieldPlatform`/`fieldRole` 클레임을 요구. 발급 함수(`provisionFieldUser`)가 미배포라 **기존 계정에 클레임이 남아 있어야** 동작. 실제 계정 토큰으로 확인 필요 |
| App Check | `NEXT_PUBLIC_FIREBASE_APPCHECK_SITE_KEY` 미설정 시 v1·v2 모두 차단 |
| Drive OAuth | 동의화면 게시 상태와 승인 도메인(`bring-fm.web.app`) 등록 확인 |
| 호스팅 배포 | CI 에 hosting 배포 단계가 없음. 수동 `firebase deploy --only hosting` 으로 운영 중인지 확인 |
| CRM 임베드 | C안은 CRM 데스크톱의 현장 탭을 복구하지 **않습니다**(현재도 동작하지 않는 상태 유지). 별도 과제 |
