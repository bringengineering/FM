# 브링FM 제품화 로드맵

*작성 2026-09-04 · 코드베이스 실측 기반*

이 문서는 브링FM을 **와꾸(아키텍처) · 흐름(업무 플로우) · 판매가능성** 세 축으로
점검한 결과와, 그에 따른 단계별 계획을 담는다.

---

## 1. 한 줄 결론

**내부 운영 도구로는 소규모 회사치고 잘 지었다. 다른 회사에 파는 소프트웨어 제품으로는 아직 제품이 아니다.**
두 목표는 완전히 다른 공사이므로, 어느 쪽을 향하는지 먼저 정해야 한다.

---

## 2. 결정적 사실 — 제품급 백엔드가 이미 있고, 꺼져 있다

`functions/src/` 에 약 22,500줄 규모의 백엔드가 이미 구현·테스트되어 있으나
`release/firebase-targets.json` 의 `functionsDeploymentAllowed: false` 로 **배포되지 않는다.**

| 모듈 | 내용 |
| --- | --- |
| `field-v2/` | `access` · `canonical-crm` · `policies` · `projections` · `contracts` · `release-gate` · `work-items` |
| `drive/` | 재개형 업로드 · 폴더 리스 · 복구키 · 미디어 동기화 |
| `security/` | 속도제한 · 광고 프로젝션 |
| `auth/` | 커스텀 클레임 발급 (`fieldPlatform` / `fieldRole`) |

또한 **"건물별 데이터 격리"의 해답도 이미 코드에 있다.**

```
fieldPlatform/buildingAssignments/{buildingId}/{uid} = true
  + 커스텀 클레임(fieldRole) + users/{uid}/enabled
  → staff 는 배정된 건물만 읽는다 (database.rules.json 에 이미 구현)
```

즉 이 일은 밑바닥부터의 개발이 아니라 **이미 만든 것을 켜고, 잇고, 확장하는 일**이다.

## 3. 아키텍처 (와꾸)

```
[As-Is]  앱 5개가 각자 Realtime DB 를 직접 조작
         ├ index.html (레거시)  ← 실제 운영이 여기서 돌아간다. 전체 덮어쓰기 · 검증 없음
         ├ desktop-crm (Electron)
         ├ company-site /field (PWA)
         ├ shop · signage
         └ field-v2 백엔드 (제품급, 격리 · 멱등성 완비)  ← 꺼져 있음

[To-Be]  앱 → Cloud Functions(field-v2) → Realtime DB
         모든 쓰기가 검증 · 멱등 · 격리를 통과한다
```

품질이 두 계층으로 갈려 있다.

| 구분 | 평가 |
| --- | --- |
| 신규 백엔드 + 릴리스 파이프라인 (SHA 핀 · WIF · 멱등성 · 원자 트랜잭션) | 상용급 |
| 데이터 검증 계층 `spark-canonical.js` (필드 allowlist, 비밀번호·도어락 키 차단) | 양호 |
| 실운영 계층 (`index.html` 케이스·입금 + Apps Script) | 위험 |
| 통합성 (앱마다 제각각 직접 쓰기) | 표준화 안 됨 |

**큰 틀의 3대 약점**

1. 단일 Firebase 프로젝트·단일 조직 전제 — `companyId`/`tenantId` 같은 회사 구분 키가 없다.
2. 데이터 접근 계층이 없어 앱마다 검증·병합 규칙이 다르다.
3. 거대 단일 파일 두 개(`index.html` 6,440줄, `desktop-crm/src/app.js` 5,729줄)가 병목.

## 4. 업무 흐름 점검

앞단(접수·영업)은 이어지고, 뒷단(현장·정산·보고)에서 끊긴다.

| 흐름 | 상태 | 끊기는 지점 |
| --- | --- | --- |
| 문의 접수 → 케이스 생성 | 이어짐 | 동시 접수 시 상태 되돌아감(트랜잭션 없음) |
| 케이스 → 견적 → 건물주 승인 | 대체로 | ~~더미 계좌 노출 위험~~ → **Phase 0 에서 해결** |
| 승인 → 입금 대사(팝빌) | 반자동 | 화면을 열어둔 30분 폴링, 이름·금액 휴리스틱 오탐 |
| **현장 작업 → 전·후 사진·검수** | **끊김** | 현장 앱에 촬영·검수 진입점이 없음(완성된 v1 이 연결 안 됨) |
| 현장 결과 → 월간 보고서 | 수동 | 데스크톱에서 담당자가 취합 |
| 데이터 보존 | ~~없음~~ | → **Phase 0 에서 야간 자동 백업 도입** |

## 5. 판매가능성

### A. 소프트웨어를 다른 회사에 판다 (SaaS) — 아직 불가

없는 것: 멀티테넌트/데이터 격리, 셀프 온보딩, 과금·구독, 백업·복구 SLA, 안정 프레임워크
(공개 사이트가 `vinext@0.0.50` 위에 있다). 사실상 재설계급 공사.

### B. 브링의 건물관리 **서비스**를 판다 — 세 가지만 막으면 가능

1. 현장 촬영·검수 연결 — 증거 사진이 서비스 품질의 핵심
2. 자동 백업 — "고객 데이터가 날아갔다"는 서비스 신뢰를 즉사시킨다
3. 잘못된 입금 계좌 차단 — 금전 사고

> 2·3번은 Phase 0 에서 처리했다. 남은 것은 1번.

## 6. 단계별 계획

### Phase 0 — 지혈 *(이 PR)*
- [x] Realtime DB 야간 자동 백업 (GPG 암호화, 30일 보관)
- [x] 건물주 안내 계좌 fail-closed (설정값 기반, 예시값 거부)
- [x] 저장·불러오기 실패 화면 표시
- [ ] PR #46 · #47 머지 (CI 정상화)

**완료 기준** — 데이터가 사라져도 하루치 이내로 복구 가능하고, 잘못된 계좌가 나갈 수 없다.

### Phase 1 — 만들어 둔 것 켜기 *(4~6주, ROI 최고)*
- `functionsDeploymentAllowed: true` + 배포 잡 추가
- 현장앱 v2 ↔ field-v2 백엔드 연결 (촬영·검수 복구)
- 레거시 `/cases` 에 `.validate` 와 `buildingAssignments` 격리 이식
- Storage 규칙도 배포 파이프라인에 포함

**완료 기준** — 현장 직원이 폰으로 전·후 사진을 남기고 검수까지 끝낸다. 담당자는 배정 건물만 본다.

### Phase 2 — 제품 다지기 *(6~10주)*
- 앱의 직접 DB 쓰기 제거 → Functions 경유로 단일화 (동시편집 유실의 근본 해결)
- `index.html` 모듈 분리, 드래그·로딩 성능 개선
- 데스크톱 코드서명, 자동업데이트의 "첨부 정확히 3개" 취약점 완화
- 월간 보고서 자동 생성

### Phase 3 — SaaS화 *(선택, 4~6개월)*
`organizations/{orgId}` 데이터 프리픽스 + 클레임에 `orgId` → 셀프 온보딩 → 과금 → 지원·SLA.

> **권고: Phase 0~2 를 먼저 끝내고, 실제 수요를 본 뒤 Phase 3 을 결정한다.**

## 7. 남은 위험과 확인 필요 사항

| 항목 | 내용 |
| --- | --- |
| 비용 | Functions 배포와 백업 보관에는 Blaze 요금제가 필요하다 |
| **확인 필요** | **Functions 배포를 왜 껐는지** — 미완성이 이유라면 Phase 1 범위가 커진다 |
| 주의 | `crm-release.yml` 의 트리거를 바꾸면 다음 push 에서 프로덕션 릴리스가 자동으로 나갈 수 있다 |
| 정확도 | 팝빌 대사는 이름·금액 휴리스틱이라 오탐이 나며 상시 자동이 아니다 |

## 8. 남은 개선 목록 (Phase 2 이후)

- 업데이트 팝업이 소규모 수정에도 전 팀원에게 뜬다
- 모바일에서 원 조작 핸들(11px)이 손가락에 작다
- 마케팅 모듈은 대시보드 껍데기(자동화 파일이 저장소에 없다)
- 사이니지가 건물마다 폴더 복사 구조
- Cloudflare 크론이 매 1분 Apps Script 를 깨워 쿼터를 소모한다
- 공개 주문(`signage/orders`)에 값 검증·속도제한이 없다
