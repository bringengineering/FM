# 개발 순서와 검증·출시 계획

2026-10-26 · 실행 전 설계 · 시간·비용·심사 통과를 확약하지 않는 단계별 계획

## 목표 완료 기준

직원이 실제 Android와 iPhone에서 기존 회사 계정으로 허용 현장을 선택하고 전·후 작업사진을 찍는다. 사진이 회사 활동사진 폴더에 정확히 들어가고, 확인한 보고서 PDF가 Drive·CRM에 보관된다. 관리자가 PC를 켜지 않고 앱에서 승인 템플릿으로 한 건을 보내며, CRM과 앱에서 동일한 최종 전달 결과를 확인한다. 통신 중단·앱 종료·두 기기 동시 요청에도 자료 유실이나 중복 발송이 없어야 한다.

## M0 연결 경계와 실행 환경 확인

산출물은 운영 연결표·모듈 재사용 목록·실행 가능성 확인 기록이다. 제품 기능 구현의 첫 착수 단계이며, 확인 전 운영 데이터를 변경하지 않는다.

1. 현재 운영 CRM의 Firebase Auth issuer·프로젝트·DB와 함수 배포 대상을 읽기 전용으로 확인한다. 소스 `.firebaserc`/웹 설정과 제공된 SECURITY 가이드의 프로젝트 설명 차이를 해소한다. signage/shop 규칙을 CRM에 복사하지 않는다.
2. 직원 UID·role·enabled·배정 업무의 실제 관계를 확인한다. 기존 member보다 넓은 권한을 만들지 않는다.
3. 회사 Drive 활동사진 루트와 건물 문서함 루트의 실제 폴더 매핑을 확인한다. 서버 실행에 쓸 기존 connector·scope·소유권·쿼터를 검토한다. 데스크톱 개인별 토큰을 공용으로 재사용하지 않는다.
4. 격리된 환경에서 서버 PDF를 생성해 기존 고객용 PDF와 비교한다. 폰트·페이지 분할·사진·12 MiB 제한·network 제한을 검증한다. 서버 장시간 작업 런타임·큐·비공개 staging의 기존 자원 사용 가능성과 추가 비용을 확인한다.
5. Google Play Console/Apple Developer 회사 계정 보유 여부·관리자·서명 소유를 확인한다. 계정 비밀번호·OTP·서명키를 채팅이나 저장소로 받지 않는다.
6. 앱 표시 이름과 제안 package/bundle ID `kr.co.bringengineering.fieldnotes`의 소유·중복 여부를 확인한다. 데스크톱 CRM app ID·업데이트 채널·버전 예약 공간과 분리한다.

M0 통과 전 금지: 신규 운영 권한·위임·OAuth scope 부여, 운영 규칙 배포, 유료 런타임 생성, 고객 발송. 새 권한이나 비용 승인이 필요한 경우 실제 필요한 대상·범위·회수 방법을 구체화한 뒤 확인받는다.

## M1 앱 골격·로그인·현장

- `mobile-field/` 신규 앱을 제안한다. Expo Development Build + TypeScript로 구성하고 검토한 버전·lockfile을 고정한다.
- iOS/Android application ID, 개발·검증·운영 환경을 분리한다. production에서 mock·debug App Check·공용 패스워드가 활성화될 수 없게 한다.
- 기존 CRM 로그인·현재 사용자 권한 확인, 최소 현장 projection, 배정 작업 선택, 기기 소유 UID 분리를 구현한다.
- 미등록·disabled·unverified·wrong-provider·must-change-password·viewer·마케팅 전용 사용자 차단을 실제 인증 조건으로 검증한다.

**완료:** 두 OS 실기기에서 허용 직원만 자신의 현장을 볼 수 있고, 관리자·일반 직원 화면 권한이 서버 결과와 일치한다. 공개 self-signup은 없다.

## M2 카메라·기기 보관·업로드

- 구역별 전·중·후 연속 촬영, 선택 사진첩 추가, 분류·포함 여부·메모 수정을 구현한다.
- 임시 카메라 파일을 영구 앱 파일로 확정하고 SQLite 큐에 기록한다. 파일 암호화·키 보관·자동 백업 제외와 UID 분리를 구현한다.
- opaque upload ID, 1 MiB chunk·재개, 실제 파일 검증, private staging→Drive 보관→CRM 연결을 구현한다.
- offline·저장소 부족·사진 권한 거부·인증 만료·Drive 오류를 구별하고 큐를 보존한다. OS가 허용하는 background 실행과 다음 앱 실행 복구를 별도로 검증한다.

**완료:** 네트워크를 끊고 앱을 종료한 뒤 다시 실행해도 미완료 사진을 식별·복구한다. 같은 사진 재시도에서 Drive 파일·CRM 사진이 중복되지 않는다. 다른 UID는 이전 직원의 큐를 열거나 전송하지 못한다.

## M3 보고서·PDF·CRM

- 기존 결과보고서 core의 플랫폼 독립 부분을 추출하되 데스크톱 회귀 검증을 유지한다.
- 선택된 ready 사진과 공개 메모로 AI 초안을 만들고 직접 수정·항목 상태 확인을 제공한다. AI 장애 시 직접 작성할 수 있어야 한다.
- ReportRevision, 예상 revision 충돌, 서버 PDF 생성, Drive 무결성 확인, canonical workReport·savedCustomerDocument 연결을 구현한다.
- 실제 보관 PDF 미리보기, 사진 누락·저장 단계 실패·복구를 제공한다.

**완료:** PC가 꺼진 상태에서 앱으로 만든 보고서가 기존 CRM에서 같은 건물·고객·작업·사진·PDF로 보인다. 부분 실패 후 복구에서 보고서·PDF가 무분별하게 늘어나지 않는다. PDF의 문구·사진은 확인한 revision과 일치한다.

## M4 관리자 검토·알림톡·전달 상태

- 일반 직원의 관리자 검토 요청과 관리자의 외부 고객 발송을 구별한다.
- CRM 수신자·저장 artifact·템플릿에 묶인 짧은 미리보기, 관리자 최종 확인, 서버 공통 claim을 구현한다.
- 기존 PC와 모바일의 공통 중복 방지 및 필요한 최소 PC 버전 전환을 검증한다.
- 실제 승인된 결과보고서 V3·문의 1551-3873·WL 버튼 링크 명세를 서버에서 확인한다. 검수/사용 가능 상태가 불명하면 발송하지 않는다.
- provider 접수·처리 중·전달·실패·불명, timeout 이후 조회만 하는 흐름을 구현한다.

**완료:** 사용자에게 별도로 승인받은 테스트 수신자·합성 보고서로 최소 한 건을 보내고 최종 전달을 확인한다. 기존 채팅에 등장한 테스트 번호를 새 승인 없이 자동 재사용하지 않는다. PC·모바일 동시 버튼과 공급자 응답 유실 시험에서 중복 외부 요청이 생기지 않는다.

## M5 실기기·내부 배포·스토어 제출 준비

- Android 회사 내부 테스트와 iOS TestFlight 검증을 진행한다. 카메라·사진 선택·백그라운드·프로세스 재시작·업그레이드를 실제 기기에서 확인한다.
- 회사 소유 스토어 계정·서명, 아이콘·스크린샷·설명·지원 정보, 개인정보처리방침·수집/공유 선언·native privacy manifest를 실제 SDK 동작에 맞춰 준비한다.
- 로그인 앱의 심사자가 기능을 확인할 수 있는 격리된 심사 계정/허용된 시연 환경을 준비한다. 실제 고객 데이터·실제 고객 발송·운영 인증 bypass를 심사 편의 기능으로 넣지 않는다.
- 일반 스토어 공개 다운로드 + 회사 초대 계정 로그인 방식을 기본 출시안으로 둔다. 회사가 비공개/관리형 배포를 원하면 등록 전에 배포 유형을 별도로 확정한다.
- 개인 Google 개발자 계정에는 계정 생성 시점에 따라 12명·14일 연속 비공개 테스트 조건이 적용될 수 있으므로 실제 계정 유형·콘솔 조건을 확인한다. 회사 계정의 심사 면제나 즉시 출시를 보장하지 않는다.

**완료:** 양쪽의 실제 제출용 artifact와 store metadata가 준비되고 내부 수용 시험이 통과한다. 운영 backend·CRM 변경과 스토어 정식 제출/배포는 사용자의 명시적 범위에 따라 진행하며 자동으로 시작하지 않는다.

## 후속: 모바일 월간보고서

첫 버전의 방문·사진·작업 기록이 기존 월간 집계의 source에 연결되는 것을 먼저 확인한다. 후속 화면은 보고월·집계·사진 선택·관리자 검토·보관 PDF·알림톡으로 구성한다. 템플릿은 `BRINGMONTHLYREPORTV2`, 문의 1551-3873이며 **기존 실제 월간 수신 요청 검증**을 동일하게 적용한다. 앱 설치·작업보고서 요청을 월간 정기 요청이나 광고 동의로 간주하지 않는다.

## 운영 배포·롤백

운영 배포가 승인되면 저장소 규칙의 순서를 지킨다: 다른 배포 확인 → 원격 최신 반영 → 태그·예약 버전 중복 확인 → 다음 버전 원자 예약 → 해당 구성의 전체 시험·artifact 검증 → 정식 게시 → 실제 업데이트/배포 채널 확인. 모바일 버전과 iOS buildNumber·Android versionCode는 각각 독립적으로 중복을 검사·예약한다.

backend는 먼저 호환 가능한 읽기·저장 경로를 준비하고, 필요한 PC 변경을 검증한 뒤 모바일 업로드·보고서·발송 capability 순으로 활성화한다. 롤백 시 신규 업로드/발송을 막아도 이미 접수한 delivery 조회와 보관 PDF 접근은 유지한다. 이미 발송한 메시지나 보관 자료를 되돌리기 위해 삭제하지 않는다. DB/권한 변경은 별도 승인·현재 백업·복구 시험·롤백 계획을 갖춘다.
