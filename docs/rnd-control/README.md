# BRING R&D 통합 관리 — CRM 통합 개발본

## 구현 위치

기존 BRING CRM src/index.html·app.js에 R&D 통합 관리 메뉴와 전용 화면을 연결했다. 신규 기능은 desktop-crm/src/rnd-control 폴더에 있다. preload.js는 R&D 읽기·저장 IPC만 노출하며, 인증 토큰은 main.js와 repository.js 안에서 처리한다.

R&D 원장은 별도 rndControl/projects·rndControl/visits이다. 기존 CRM 원장을 변경하지 않는다. 프로젝트별 CRM 고정 자료는 허용된 읽기 전용 메타데이터와 선택 원장 ID만 R&D 경로에 보관한다. 승인 사용자는 기존 crmCompany/access와 별도 rndAccess의 활성·이메일·역할 일치를 확인한다. 공유 복원 Firebase Functions 개발 소스를 추가했으며 운영 배포 금지 정책을 유지한다. 실제 운영 배포는 하지 않았다.

## 현재 기능

7개 영역·23개 산출물, 목표·담당·기한·기준·결과·한계·버전 근거, TRL 개발 계획·판정 초안·수정 이력, 운영 기준선 입력과 시간·비용 검증, 프로젝트 생성·전환·공유 목록 조회, 개별/전체 프로젝트 파일 보관·복원.

읽기·저장은 기존 CRM 세션을 사용한다. 원격 저장은 변경 경로를 묶은 원자적 PATCH와 서버의 revision 증가 조건으로 충돌을 차단한다. 서버에서 버전 충돌로 거부한 경우 최신 revision을 다시 읽어 충돌을 안내하고 덮어쓰기 재시도를 하지 않는다. 공유 연결 실패 시 성공 표시를 하지 않는다. 서버 Rules는 익명·미승인·이메일 불일치·viewer 쓰기·수정자 위조·오래된 revision·삭제를 거부한다. Rules는 개발 파일에만 반영했고 운영 배포는 하지 않았다.

실험계획 작성·지정 검토자 승인·계획 동결·실험 시작/종료·고정 데이터 버전·근거 검토·승인 근거에 연결된 관리자 사업 결정을 추가했다. 자기검토 여부·사유와 서버 세션의 수정자를 기록한다. 일반 공유 저장은 연구 기록 변경을 거부하며 Firebase의 빈 배열 생략과 숫자 키 배열 표현을 동일하게 비교한다. 직접 DB 요청도 지정 검토자 승인·동결 계획 변경 금지·승인 근거 수정 금지·결정/감사이력 삭제 금지 규칙으로 검사한다. 이 규칙은 Emulator 시험을 통과했으며 운영에는 아직 배포하지 않았다.

## 실행·시험

desktop-crm에서 npm ci, node node_modules/electron/install.js, npm start. 운영 로그인 실행 전 시험 설정과 변경 범위를 확인한다.

자동 시험: desktop-crm에서 npm test — 최신 실행 482개 PASS.
앱 시험: desktop-crm에서 node test-rnd-electron.mjs — CRM 첫 실행 안내 닫기, 메뉴·모듈 초기화·시험 저장·신뢰한 수정자·목록·메뉴 전환 보존, 전용 IPC의 실험 승인·동결·실행·종료·근거 승인·사업 결정, 앱 내부 프로젝트 입력창·프로젝트 전환 시 미공유 상태와 연구 화면 분리 PASS. 실제 원격 저장을 시험한 결과가 아니다.
서버 시험: 저장소 루트에서 firebase emulators:exec --only database --project demo-bring-rnd --config rnd-emulator.json "node desktop-crm/test-rnd-rules.mjs" — 허용·거부 요청 시험 PASS. permission_denied 경고는 기대한 거부 시험 로그다.

## 남은 작업

Drive 회사계정 인증·폴더 소유/쓰기 확인·프로젝트/자료/버전 경로·해시·동일 버전 재시도 서비스를 추가했다. company-site/public/rnd-drive-auth와 firebase-public/rnd-drive-auth는 새 인증 페이지이며 아직 회사 호스팅에 배포하지 않았다. 회사 Drive 연결 버튼을 누르면 이 공식 호스팅 페이지를 통해 사용자가 인증한다. 토큰은 메인 프로세스 메모리에만 보관하며 CRM 인증 계정에 묶고 50분 뒤 재연결을 요구한다.

남은 작업: 새 인증 페이지와 R&D 서버 Rules의 회사 환경 반영, 실제 Drive 인증·보관권한·원본 업로드 및 두 승인 계정 실공유 시험, 동시 업로드 시 파일/폴더 중복 처리 강화, 데이터셋 manifest·자료 관계·복구·61개 검수의 미완료 항목, 회사 배포 소스와 병합·릴리스 검수. 원본 파일 업로드 후 연구 DB 등록은 별도 단계이며 실패 시 원본 파일의 ID로 재연결한다.

현재 TRL·산출물 승인·이력은 연구 초안이며 공식 외부 평가나 승인 인증 기록을 의미하지 않는다. 실제 운영 준비 완료가 아니다. 기존 Drive FIELD 코드에서 회사 OAuth·루트 폴더 설정이 존재함을 확인했으며 이를 근거로 재사용 구조를 개발한다. 개인 토큰이나 운영 계정을 임의 생성하지 않는다.

버전·업데이트 채널·회사 설치 앱은 변경하지 않았다. 배포·운영 Rules 반영 전에 변경 패키지와 미완료 항목을 검토한다. 롤백은 신규 메뉴·IPC·모듈·rndControl 규칙 변경을 되돌리는 방식이며 기존 CRM 원장 마이그레이션은 없다.

## 원래 기획서 검수 대조

acceptance-audit.md와 acceptance-status.json에 61개 항목을 유지한다. 부분 구현 또는 좁은 단위 시험만으로 전체 항목에 PASS를 부여하지 않는다. 운영 출시는 이 검수와 실제 두 계정 Drive 시험을 별도로 통과해야 한다.

## 가설 관리 추가

명시적으로 가설 체계 버전과 지정 검토자를 입력하면 기획서 H0~H7을 NOT_TESTED 템플릿으로 만든다. 가설 ID는 프로젝트·체계 버전·코드를 포함한다. 실험은 선택한 체계에 연결되며, 다른 체계의 동일 코드 근거로 판정하지 않는다. 지정 검토자/관리자만 해당 가설의 승인 근거를 연결해 판정할 수 있다. 판정은 원래 템플릿을 교체하지 않고 별도 불변 기록으로 쌓으며 근거 버전·이유·검토자·시각을 보존한다. 실험 종료나 사업 결정은 가설의 자동 확정을 일으키지 않는다.

## 승인 계획 변경 버전

승인·실행·종료한 계획에서 변경 초안을 만들면 새 실험 ID와 계획 버전이 생성된다. parentExperimentId/rootExperimentId/parentPlanVersion으로 원계획을 연결하고 changeReason/appliesTo를 필수 기록한다. 가설 코드·체계는 유지하며 기준·기간·대상·측정 방식은 새 초안에서 변경한다. 이전 계획의 승인·동결본·실행 상태·데이터·근거는 교체하지 않는다. 새 버전은 승인이나 실행 시각을 물려받지 않으며 지정 검토자의 재승인 후 실행한다. 이 흐름과 원계획 변경 거부는 모델·CRM 앱·Emulator에서 검증했다. 실제 운영 데이터셋 manifest 동결과 바이너리 보관 검증은 아직 남아 있다.

## 데이터셋 동결 개발

산출물 보관 파일의 프로젝트·자료·versionId·providerFileId·SHA256 연결을 보존한다. 동결 시 Main은 회사 Drive 파일 소유권·공용 root 경로·appProperties 버전과 실제 바이트 해시/크기를 다시 확인한다. 최대 20MiB 바이트 스트림에 제한을 적용한다. 모델은 대상·포함/제외 기준·수집 기간·독립 대상 ID·행수·파일 버전을 필수 검증하고 동결 계획 해시/버전 및 manifestHash를 생성한다. 파일 수·행수·독립 대상 수는 구별한다. 동결 데이터셋을 선택해 종료하면 근거 source에 해당 snapshot ID와 manifestHash가 유지된다. 서버 Rules는 동결 레코드 변경/삭제와 잘못된 계획 참조를 거부한다.

351개 단위 시험·Emulator의 동결/종료/근거 연계 및 변경/삭제 거부·CRM의 모의 업로드 문맥 시험이 통과했다. 실제 Drive 회사 계정의 바이트 시험은 미실행이다. Rules는 공급자 바이트를 읽거나 해시를 계산할 수 없으며 이 검증은 Main에서 수행한다. 기존 링크 기록은 미동결 표시하고 과거 버전 시험을 유지했다. 대외용 자료 확정 시 동결 근거 강제·가변 링크 제외, 중앙 ArtifactVersion 원장과 재검증 상태·자료 복구는 아직 남아 있다.

## Markdown 기록 내보내기

CRM의 내부 기록/검토용 선별 Markdown ZIP 버튼은 공유 저장된 프로젝트 ID와 revision만 Main에 전달한다. Main은 CRM 세션으로 다시 공유 원장을 읽고 파일 선택 후 revision/세션을 재확인해 ZIP을 보관한다. 기기 미공유 초안은 먼저 저장해야 한다. ZIP은 신규 별도 파일이며 기존 Vault 문서를 변경하지 않는다. 프로젝트·가설·실험·데이터셋·근거·결정 노트의 고유 ID·원장 revision·상대 링크와 manifest의 각 파일 SHA256/크기를 포함한다. 자유 입력은 코드 블록으로 표시하고 위험/인증값 포함 URL 및 알려지지 않은 속성은 내보내지 않는다.

내부 기록은 미승인·미동결 자료를 상태와 함께 보존한다. 검토용은 미승인·공개 범위 미확인·동결 manifest 불일치 근거를 제외하며, 포함할 보관본은 Drive에서 재확인한다. 관리자가 공개 범위를 승인한 유효한 동결 근거만 검토용에 포함하며, 승인 취소나 내용 변경 시 제외한다. 원본 바이너리를 포함하지 않으며 전체 파일 백업이 아니다. 실제 공유 원장의 실Drive 검토용 출력은 아직 검증하지 않았다. 기존 기능 포함 351개 테스트, native 출력 IPC/선택 파일 보관, 생성 ZIP의 CRC·한글·manifest 해시·상대 링크를 확인했다.

## 관리자 검토용 자료 포함 승인

전용 공개 범위 form은 관리자만 allow/revoke를 확정할 수 있다. allow에는 근거 및 연결 실험·데이터셋 전체의 공개 권한/민감 정보 검수 확인과 이유가 필요하다. 해당 근거가 승인되어 있고 동결 manifest와 계획 버전이 유효해야 한다. bundleHash는 근거·실험·데이터셋의 전체 기록에 묶인다. 포함 승인·취소는 sourceRevision/sequence/승인자/시각/이유를 가진 별도 불변 기록으로 쌓이고, 취소는 원래 승인 ID를 참조한다. 서버는 관리자 여부·원장 revision·버전 참조와 이력 수정/삭제를 검사한다.

검토용 export는 최신 승인이 allow이고 현재 bundleHash가 일치하는 근거만 포함한다. 연결 자료는 같은 승인 범위에 포함되며 프로젝트 제목·TRL 판정·사업 결정은 별도 공개 범위 승인 없이 검토용에 내보내지 않는다. Drive 원본 확인은 출력 직전에 다시 수행한다. 공개 포함 승인은 Drive ACL 변경·외부 전송이 아니며 이미 내보낸 파일을 회수하지 않는다. 실제 회사 Drive 공개 범위 검수·출력은 아직 미실행이고 가정/문헌/실측 분류와 자료 복구는 계속 구현해야 한다. 351개 테스트 및 Emulator의 저장 원장 재조회/해시 일치/allow·revoke 선별, native 미동결 근거 거부를 확인했다.

## 근거 출처 유형과 개선율 계산

기존 기록은 미분류로 유지한다. 실험 근거에서 실측·문헌·시뮬레이션·가정을 명시하고 출처/측정/계산 범위를 기록한다. 실측 유형은 유효한 동결 데이터셋과 BRING 직접 측정 확인이 필요하다. 실험과 독립적인 문헌/시뮬레이션/가정 참고 근거는 원출처 URL·버전·한계·검토자를 기록한다. 참고 자료의 독립 실측 표본 수는 0이며 실측으로 자동 변환하지 않는다. 유형·설명·직접 측정 확인은 원장에 불변 기록하며 Markdown에서 표시한다. 서버의 문헌 근거 검토/유형 변경 거부 시험이 통과했다.

시간·원가 개선율 초안 계산은 미측정, 비유한 수치, 0 기준값, 계산 범위 초과를 사유와 함께 —로 표시한다. 실제 0 결과는 유효한 측정값이며 10→0은 100% 감소, 10→12는 -20% 감소로 표시한다. 계산 결과를 metricResults 원장에 기준·결과 데이터셋 ID/해시, 단위, 원본 위치, 계산 버전과 함께 보존한다. 실측 개선 주장은 해당 실험의 유효한 수치 결과 연결이 필요하다. 참고 자료는 현재 내부 기록에 포함되며 검토용의 참고 자료 스냅샷 공개 범위 승인 확장은 남아 있다. 기존 기능 포함 351개 테스트 및 native 계산 화면 검증을 확인했다.

## 수치 결과 원장 추가

기준·결과 동결 데이터셋을 선택하고 수치·단위·원본 위치·측정 방법·한계를 기록한다. Main이 개선율을 계산하고 서버 Rules도 원본 해시와 계산식을 검사한다. 수치 결과는 수정/삭제 대신 별도 기록으로 보존하며 근거에 연결한 ID 목록의 불변 복사본을 대조한다. 공개 포함 승인 해시에 수치 결과와 기준 자료도 묶고, 검토용 출력 전에 기준·결과 원본 모두 Drive에서 재확인한다. Markdown에는 수치 노트와 양쪽 자료 링크를 포함한다.

현재 수치는 사람이 원본에서 전사하는 방식이며 CSV 자동 추출이나 실제 측정 정확도를 검증한 것은 아니다. 실제 회사 Drive/두 계정 시험, 원래 61개 검수는 계속 필요하다. 기존 CRM 기능 포함 351개 자동 시험과 Emulator의 수치 원장 저장·해시/계산식 오류 거부를 확인했다.

수치 연결 목록은 최대 100개이며 서버가 기존 항목의 삭제·교체·추가를 거부한다. 두 수치 결과를 연결한 근거에서 한 항목만 삭제하거나 새 항목을 추가하는 직접 DB 요청 거부를 Emulator에서 확인했다. 삭제 시 하위 validate가 생략되는 Firebase 동작을 고려해 상위 쓰기 조건에서도 기존 연결 보존을 검사한다.

## 첫 프로젝트 시작

최초 R&D 화면은 프로젝트를 자동 생성하지 않는다. 새 프로젝트 입력을 취소하면 원장·세션 프로젝트가 남지 않는다. 이름을 입력해 생성하거나 공유 목록을 조회해 선택한 뒤 산출물·TRL·연구 화면을 사용한다. CRM 앱에서 빈 상태→취소→생성→23개 산출물→공유 저장과 기존 연구 흐름을 확인했다. 실제 빈 운영 workspace 시험은 아직 미실행이다.

## 저장 응답과 초안 보존

프로젝트 저장은 요청 시점의 프로젝트 복사본을 사용한다. 응답 대기 중 프로젝트를 전환해도 현재 선택을 바꾸지 않는다. 요청 이후 추가 수정이 있으면 응답으로 덮어쓰거나 미공유 표시를 지우지 않는다. 프로젝트별 중복 저장 요청을 차단한다. 최신 공유본 비교/재적용 화면은 계속 필요하다. 개발 소스와 재패키징된 Windows 실행 파일에서 지연 응답·전환·추가 수정 시험을 통과했다.

## 공유본 비교와 선택 재적용

최신 공유본과 제목·산출물/TRL의 목표·담당·기한·기준·결과·검토자 차이를 표시한다. 기본 선택은 없으며 이유를 입력해 선택 수정만 최신 revision의 초안에 적용한다. 상태·근거·판정·연구·승인 이력은 최신 공유본을 유지한다. 기존 공유 감사 이력 뒤에 비교 revision/사유/로그인 사용자와 재적용 항목을 추가한다. 재적용 전 초안은 현재 세션에서 파일로 보관할 수 있다. 반영은 공유 저장이 아니며 저장 시 기존 서버 충돌 검사도 유지된다. 351개 자동 시험 및 CRM 비교 화면 시험을 확인했다. 실제 두 계정 동시 편집 검수는 남아 있다.

## 선택 기록 직접 조회

전용 rndGet IPC는 projects/visits와 유효 ID만 받는다. Main이 로그인·역할·비밀번호 변경 상태를 검사하고 선택 기록 경로만 읽는다. 저장소는 토큰 준비 후와 응답 수신 후 세션을 다시 확인하며 반환 ID도 대조한다. 연구 조회·공유본 비교와 기존 Main의 연구 작업/출력은 단건 조회를 사용한다. 전체 목록은 목록 조회에만 사용한다. 이 변경은 전체 검색·10,000건 페이지 처리 검수 완료를 의미하지 않는다.

## 복원 사전 검증과 충돌 유지

개별/묶음 JSON 복원은 파일 구조·프로젝트 ID/revision·9개 고유 TRL 단계·중복 프로젝트를 검증한다. 신규/동일 ID 수를 먼저 표시하며 확인 후 신규 프로젝트만 세션 초안에 추가한다. 기존 동일 ID 프로젝트를 덮어쓰거나 공유 DB에 바로 기록하지 않는다. 기존 수정은 유지하며 새 초안은 미공유 표시한다. 모델과 CRM 앱에서 동일 ID 충돌 유지 시험을 확인했다. 전체 연구 관계 검증·이력 병합·바이너리 복구와 영속 롤백 manifest는 아직 별도 개발이 필요하다.

## 복원 연구 관계 검사

JSON 복원 사전 검증은 연구 레코드 고유 ID·프로젝트 ID, 변경 실험의 부모/계획 버전, 데이터셋 실험/계획 참조, 수치 결과의 기준·결과 자료 해시, 근거의 실험/자료/수치 참조, 판정·결정의 근거 참조, 공개 승인의 자료/선행 승인 참조를 검사한다. 파일 안에서 연결이 끊어진 경우 적용하지 않는다. 이는 Drive 실제 바이트 검증이나 원래 승인자 신원 재인증을 대신하지 않으며, 운영 원장 복구 승인과 바이너리 복원 시험은 남아 있다.

## 필수 산출물 준비율

산출물 편집에서 필수/선택을 명시하고 변경 이유와 함께 기록한다. 종합 현황의 준비율은 필수 산출물 승인/필수 수로 계산하며 선택은 분자·분모에서 제외한다. 필수가 0개면 —이다. 기존 구분 없는 산출물과 신규 23개 기본 템플릿은 필수로 취급하며 사용자가 기준에 따라 선택으로 변경한다. 이 준비율은 기술 성숙도나 외부 평가 점수가 아니다. 필수 4개 중 1개 승인 및 선택만 승인한 경우의 모델 시험, CRM 구분 저장·22개 분모 표시를 확인했다.

## 미완성 실험 초안 모델/서버

전용 createDraft 작업은 실험 ID·가설 코드와 체계 관계를 검사하고 미완성 계획을 draft로 보관한다. editDraft는 작성자/관리자의 명시적 이유와 허용 필드만 받아 보완하며 계획 버전은 유지한다. 이전·이후 계획과 이유를 연구 감사 이력에 추가한다. 승인에는 전체 필수 계획 항목이 필요하며 승인된 계획의 변경은 기존 변경 버전 흐름을 사용한다. 서버는 draft 유지 변경을 작성자/관리자에게만 허용하고 승인 시 필수 항목·지정 검토자·동결본 일치를 검사한다. 모델/Emulator 시험을 통과했다. 미완성 초안 저장·보완 전용 화면을 연결했고 기존 전체 계획 등록도 유지한다.

CRM의 미완성 실험계획 저장·보완 화면에서 ID·가설만으로 초안을 저장하고 기록의 초안 보완 버튼으로 입력을 불러온다. 기존 초안의 ID·가설은 편집 중 잠근다. 실제 CRM 시험에서 질문 보완 저장과 필수 항목 누락 승인 거부를 확인했다. 이 앱 시험은 로컬 시험 원장이며 회사 공유 DB 시험을 대신하지 않는다.

## 릴리스 상태 확인

`npm run rnd:release:check`는 원래 61개 ID를 고정 대조하고 PASS/근거 목록을 검사해 release-readiness.json을 생성한다. 미완료·근거 누락 시 종료 코드 1이다. 현재 4/61 근거 포함 PASS이며 운영 릴리스 준비가 아니다. 기록된 근거의 존재와 실제 내용·실계정·배포 검수는 사람이 별도로 대조해야 한다. `npm run build:rnd:review`는 게시 없이 Windows 검토용 실행 파일만 만든다. 기존 회사 릴리스 명령/업데이트 채널은 변경하지 않았다.

다음 우선순위는 별도 rndAccess 승인, 로그인/로그아웃 시 초안 정리, 동시 업로드 복구, 자료 원본을 포함하는 복구 시험이다. 실제 회사 계정 시험과 61개 종합 검수가 완료되기 전 운영 준비 완료로 표시하지 않는다.

## 별도 R&D 서버 접근 승인

R&D DB 읽기·쓰기는 CRM 승인과 rndAccess 승인을 모두 요구한다. 활성 상태·로그인 이메일·CRM 역할이 일치해야 한다. 기존 CRM 관리자가 별도 승인을 부여/취소하며 approvedBy/approvedAt/reason을 기록한다. 실무자의 자기승인과 역할 위조·승인 삭제는 거부한다. Emulator에서 CRM만 승인된 계정, 별도 승인 비활성·역할 불일치 거부와 관리자 승인/취소를 확인했다. Rules는 아직 회사 서버에 배포하지 않았다. Main/Drive 사전 승인 확인과 관리자 편집 화면·운영 승인자 초기 설정은 계속 필요하다. 기존 사용자에게 R&D 권한을 자동 부여하지 않는다.

## CRM/Drive 작업 전 승인 확인

Main의 목록·단건 조회·저장·연구 작업·내보내기와 Drive 인증/업로드는 별도 R&D 승인을 조회한다. 조회 전후 세션 UID/이메일/역할을 확인하며 활성·CRM 역할 일치를 요구한다. 인증 대기와 파일 선택 이후 다시 승인/계정을 확인한다. 확인 실패 시 Drive 메모리 연결을 지운다. 로컬 앱 시험은 외부 승인 DB를 호출하지 않는 명시적 시험 모드이므로 승인 서비스 단위/서버 Emulator 시험과 구분한다. 실제 회사 승인 DB/Drive 시험과 관리자 UI·로그아웃 정리는 아직 필요하다.

## 관리자 승인 화면

CRM 관리자에게 사용자 UID 기반 R&D 승인 조회·활성/취소·사유 입력 화면을 표시한다. 전용 Main IPC는 관리자와 대상 ID를 검사하고 서비스가 공유 CRM 이메일/역할을 다시 조회한다. 입력한 역할값을 승인 역할로 사용하지 않는다. 승인 전후 세션을 검사하며 서버 Rules도 CRM 역할 일치를 검사한다. 로컬 앱 시험은 현재 시험 관리자만 대상으로 허용하고 실제 회사 승인을 변경하지 않는다. 서비스의 역할 위조 무시/비관리자 거부와 CRM 승인 저장 화면 시험을 확인했다. 운영 승인 이력 별도 원장·동시 관리자 변경 대조·실회사 계정 시험은 남아 있다.

## 관리자 승인 충돌 처리

승인 조회는 Firebase ETag를 받으며 저장은 조회한 ETag의 If-Match 조건으로만 요청한다. 대상 UID를 변경하거나 저장 후에는 다시 조회해야 한다. 412 충돌은 재조회 안내로 처리하고 덮어쓰기 재시도를 하지 않는다. 기존 관리 화면은 현재 승인 조회 후 저장하는 순서다. 조건부 쓰기 헤더·충돌 거부/단일 요청 서비스 시험과 CRM 조회→저장 화면 시험을 확인했다. 두 실관리자 동시 요청의 회사 서버 시험과 승인 불변 감사 원장은 남아 있다.

## 좁은 화면과 긴 식별자

390×844 및 1440×1000 화면에서 R&D 콘텐츠를 확인했다. 긴 해시/ID는 줄바꿈하며 입력·버튼·그리드의 최소 너비가 콘텐츠를 밀어내지 않도록 한다. 비교 대화상자는 화면 높이 안에서 스크롤하고 체크박스를 별도 정렬한다. CRM 앱/Windows 실행 파일에서 300자 식별자와 비교 제목을 넣어 콘텐츠/대화상자 가로 넘침과 높이를 검사했다. 좁은 콘텐츠·비교 대화상자 이미지를 패키지에 보관한다. 전체 모바일 업무 완료/실사용자 시간 검수는 이 검사와 별도로 남아 있다.

## 승인 감사 기록 모델

access-audit.js는 승인 변경 요청의 이전/요청 상태·대상 UID·실제 관리자·사유·ETag·시각·eventHash를 생성한다. 기록은 approval-attempt이며 committed=false로 시작한다. 비관리자·수정자 불일치·대상/원본 버전 누락을 거부한다. 이 모델은 아직 원격 저장 서비스에 연결하지 않았다. 요청/성공 기록 분리·불변 서버 원장·현재 승인 auditId 연결·실패 복구/조회 화면을 다음에 구현해야 하며 모델 시험만으로 승인 감사 원장 완료를 의미하지 않는다.

## 승인 요청 감사 서버 원장

신규 rndAccessAudit/대상UID/요청ID 원장은 CRM 관리자만 생성·조회한다. 서버는 관리자 UID·대상·요청 유형·committed=false·현재 승인과 동일한 이전 상태·CRM 이메일/역할과 일치하는 요청 상태를 검사한다. 생성 후 수정·삭제는 관리자에게도 거부한다. Emulator에서 요청 생성·관리자 수정/삭제·실무자 위조 생성 거부를 확인했다. 서비스의 실제 승인 저장/성공 확인·복구 UI 연결은 아직 남아 있다. eventHash 형식은 Rules가 검사하지만 해시 계산은 Node 모델에서 수행한다.

strengthen-rnd-rules.py의 접근 조건을 기존 생성 결과에서 추출하지 않고 원래 CRM 승인 조건으로 생성하도록 수정했다. 반복 실행 결과의 SHA256 일치를 확인했다. 이 수정으로 nullable 프로젝트 필드 저장 거부 회귀를 해결했고 전체 서버 시나리오를 다시 통과했다. 운영 배포는 하지 않았다.

## 승인 저장과 감사 요청 연결

관리자 서비스는 저장 직전 현재 승인 ETag를 재조회·비교하고 관리자 세션에서 요청 ID를 생성한다. 변경 전/요청 상태를 불변 감사 원장에 먼저 저장하며 실패하면 승인 PUT을 하지 않는다. 성공한 감사 요청 ID를 승인 auditId로 연결하고 기존 If-Match 조건부 PUT을 수행한다. 승인 충돌 시 감사 요청은 남지만 committed=false 요청 기록이며 승인 성공 증거가 아니다. 서버는 auditId가 있을 때 관리자·요청 상태 연결을 확인한다. 모델 서비스의 감사 실패/변경 중단과 충돌 단일 요청 시험 및 전체 서버 시험을 확인했다.

이후 서버 감사 강제 검증을 추가했다. 별도 성공 확인 기록·불확실한 저장 복구·감사 조회 UI·실회사 요청 시험은 계속 구현해야 한다. 로컬 관리자 화면 시험은 별도 메모리 원장이고 원격 감사 저장 증거가 아니다.

## 승인 감사 연결 강제

서버는 새 auditId와 현재 승인 이전 값·요청 이후 값 전체가 감사 레코드와 일치하는 승인 저장만 허용한다. 현재 감사 ID 재사용, 감사 ID 누락, 이전 상태 위조 요청을 거부한다. 과거 초기 레코드는 읽을 수 있지만 이후 변경에는 감사 요청을 생성해야 한다. Emulator에서 감사 요청→승인·취소, 감사 없는 직접 쓰기 거부, 감사 ID 재사용 거부와 이전 값 불일치 거부 및 전체 연구 시나리오를 확인했다. 반복 규칙 생성의 결과 SHA256 일치도 재확인했다. 운영 Rules는 아직 변경하지 않았다.

## 현재 승인 감사 연결 조회

관리자 승인 조회는 현재 승인 auditId의 불변 요청 기록을 추가로 읽고 대상 UID·ID·승인 이후 값 전체를 대조한다. 일치하면 조회한 승인과 연결 확인, 불일치면 확인 필요, 감사 ID가 없으면 과거 기록으로 표시한다. 이는 조회 시점의 현재 승인 포인터에 대한 확인이며 변경 요청만으로 성공을 판정하지 않는다. 과거 성공 상태 별도 확정 원장·응답 유실 복구·미연결 요청 목록·실회사 두 관리자 시험은 남아 있다. 서비스 단위 시험과 기존 관리자 화면/Windows 앱 흐름을 확인했다. 로컬 화면 시험은 실제 감사 DB를 조회한 증거가 아니다.

## 승인 응답 유실 재확인

승인 조건부 PUT의 연결/응답 해석 오류가 발생하면 쓰기를 재시도하지 않고 현재 승인만 다시 읽는다. 같은 auditId와 승인 값 전체가 일치하면 재조회로 확인했다고 반환·표시한다. 값 불일치나 조회 실패면 미확정이며 감사 요청 ID와 재조회 안내를 남긴다. 서비스 시험에서 실제 저장 후 응답 유실의 일치 확인과 미저장 응답 유실의 미확정 거부, 각각 승인 PUT 1회를 확인했다. 이것은 프로세스 종료 후 영속 복구·과거 성공 원장·실회사 네트워크 장애 시험 완료를 뜻하지 않는다.

## 감사 요청 ID 결과 조회

관리자 서비스의 inspect와 전용 IPC는 대상 UID/감사 요청 ID를 받아 불변 요청과 현재 승인만 조회한다. 대상/ID 불일치를 거부하며 현재 승인 auditId와 요청 이후 값 전체가 같을 때 연결 확인으로 표시한다. 그 외는 미확정 요청이며 과거 적용 여부를 단정하지 않는다. 관리자 화면에서 감사 요청 ID를 입력해 조회할 수 있고 정상 원격 저장 후 생성된 ID를 입력칸에 보관한다. 로컬 모드는 실제 감사 조회를 거부하며 운영 감사 DB를 모의 성공으로 표시하지 않는다. 프로세스 종료 후에도 서버 요청 ID 조회는 가능하지만 자동 요청 복구·과거 성공 확정 원장과 실회사 장애 시험은 남아 있다.

## 세션 변경 시 R&D 메모리 정리

CRM 인증 상태의 UID·이메일·역할·비밀번호 변경 상태가 바뀌면 R&D 세션 초기화를 발행한다. 프로젝트 목록/초안·재적용 백업·자료 선택·산출물/TRL/연구 입력·기준선 기록·연구 카드와 관리자 표시를 정리한다. 캐시된 R&D 호스트를 명시적으로 참조해 다른 CRM 메뉴에 있을 때도 정리한다. 세션 이후 이전 업로드 응답은 UI 자료 반영을 중단하며 CRM 로그아웃 완료 과정에서 Drive 연결을 지운다. 앱 시험에서 다른 메뉴로 이동→초기화→R&D 재진입 시 프로젝트/연구 기록 0개를 확인했다. 실제 로그아웃 미공유 확인·승인 취소 즉시 UI 정리·진행 중 전체 작업 취소·두 UID 실계정 시험은 아직 남아 있다.

## 로그아웃 전 R&D 입력 확인

CRM 로그아웃 버튼은 미공유 프로젝트·입력 중인 폼·업로드 대기·기준선 입력을 먼저 확인한다. 기존 CRM 확인창에서 돌아가서 보관을 선택하면 로그아웃 API를 호출하지 않고 초안을 유지한다. 적용/저장에 성공한 폼은 입력 대기 표시를 해제한다. 로그아웃 API 성공 뒤 명시적으로 R&D 세션 초기화를 발행하고 페이지를 다시 연다. Main의 기존 FIELD 로그아웃 순서는 유지하며 완료 과정에서 Drive 연결을 지운다. 앱 시험에서 미공유 초안 생성→로그아웃 취소→동일 ID/미공유 유지 확인을 통과했다. 개발자도구의 직접 로그아웃 호출 경고·실계정 성공/취소·진행 중 모든 작업 취소 검수는 남아 있다.

### 저장 대기 중 입력 보호
연구 기록과 접근 승인 폼은 저장 요청 시 입력 세대를 기록하며, 응답 전에 추가 입력한 경우 미공유 표시를 유지합니다. 세션 초기화 이전 요청도 새로운 입력 표시를 지우지 않습니다. 입력 상태 회귀 테스트를 포함한 Node 테스트 352개와 Electron 화면 흐름을 검증했습니다. 실제 두 계정 동시 운영 검증은 별도 진행해야 합니다.

### CRM 계정 전환 보호
실시간 CRM 로그인 알림을 초기 조회 응답보다 우선하며 계정·역할 변경 시 승인 관리 폼을 새로 생성합니다. 이전 세션의 방문 기록 조회·저장·자료 업로드 응답은 새 화면에 반영하지 않습니다. 방문 기록 저장 중 추가 입력의 미저장 표시도 유지합니다. Electron의 Main→preload 로그인 이벤트 경로에서 회원→관리자 전환과 폼 초기화를 검증했습니다. 시험용 이벤트이며 실제 두 회사 계정의 서버 권한 검증을 대신하지 않습니다.

### Drive 업로드 겹침·세션 변경 보호
동일 CRM 프로세스에서 업로드가 진행 중이면 다음 업로드는 명시적으로 거절하고 완료 후 재시도하도록 안내합니다. 폴더 조회·생성, 기존 버전 조회, 업로드·원본 조회마다 요청 시작 시의 Drive 연결을 확인합니다. 연결 해제·계정 변경 후 후속 생성 요청을 중단합니다. 재사용 버전은 해시뿐 아니라 프로젝트·자료 ID·크기·부모 폴더도 비교합니다. 동시 요청과 조회 대기 중 연결 해제 회귀 테스트를 포함해 Node 테스트 353개가 통과했습니다. 여러 PC의 전역 중복 방지·응답 유실 복구와 실제 Drive 통합 시험은 아직 남아 있습니다.

### 연구 메타데이터 검색
프로젝트·산출물·실험·데이터셋·근거·측정 결과·의사결정·가설을 세션 조회본과 초안에서 검색합니다. 이름·담당자·검토자·가설·자료 ID·결과 등을 NFKC 정규화한 복수 검색어 AND 조건으로 조회하고 종류별 필터 및 50개 페이지 이동을 제공합니다. 검색 결과에서 해당 프로젝트를 열고 산출물은 직접 선택합니다. 검색 화면에 조회 범위와 최신 공유본 확인 필요를 표시하며 세션 전환 시 검색어·인덱스를 정리합니다. 10,000개 메타데이터의 검색·페이지 분리·조건·빈 결과 테스트와 Electron 검색 이동을 검증했습니다. 실제 10,000개 원격 자료 성능과 3인 사용성 시험은 아직 남아 있습니다.

### GitHub 코드 근거 버전 표시
참고 근거에 GitHub HTTPS blob/commit 링크를 등록하면 저장소·파일 경로·40자리 commit SHA 및 고정 여부를 미리 표시합니다. branch·태그·축약 SHA와 저장소 일반 링크는 미고정 경고를 표시합니다. 40자리 링크 SHA와 40자리 출처 버전이 다르면 Main 연구 모델이 저장을 거부합니다. 인증 정보·검색 인자가 있는 GitHub 링크도 거부합니다. ### 범위 명시 메타데이터 백업

### CSV 감사 원격 조회 transport 한도
