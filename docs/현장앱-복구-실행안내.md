# 현장앱 복구 실행 안내

현장앱은 지금 동작하지 않습니다. 원인은 화면이 아니라 **서버 쪽 준비가 안 된
것**입니다. 이 문서는 무엇을 누가 하면 되는지만 적습니다.

길은 두 가지입니다. **A안(권장)** 은 요금제를 바꿔 지금 앱을 그대로 살리는
길이고, **B안** 은 요금제를 그대로 두고 예전 버전을 쓰는 길입니다.

## 왜 지금 안 되는가

막힌 곳이 두 군데입니다.

1. **허용 목록이 비어 있습니다.** 현장앱 로그인은 `fieldPlatformAllowedEmails`
   에 등록된 이메일만 통과합니다. 그런데 이 목록에 값을 넣는 코드가 어디에도
   없습니다 — 규칙상 앱에서도 못 씁니다. 설계 단계부터 "사람이 한 번 등록"
   하기로 되어 있었는데, 그 등록이 안 된 상태입니다.
2. **서버 함수가 배포되어 있지 않습니다.** 지금 `/field` 가 보여 주는 v2 화면은
   작업 배정·전환·방문 변경을 전부 Cloud Functions 로 처리하고, 데이터가 놓이는
   `fieldPlatform/v2` 는 읽기·쓰기가 모두 `false` 라 서버 함수만 접근합니다.

**1번은 요금제와 무관합니다.** 함수를 배포하더라도 허용 목록을 등록하지 않으면
로그인이 `field_access_denied` 로 막힙니다. 그래서 아래 절차에 등록 단계를
따로 두었습니다.

> 이전 판에서 "v1도 v2도 똑같이 함수를 부른다"고 적었는데 **틀렸습니다.**
> v1(`FieldApp.tsx`)은 데이터베이스와 드라이브에 직접 붙는 방식이 기본값이고,
> 함수는 계정 등록 하나만 씁니다. B안이 성립하는 이유입니다.

## 코드는 준비되어 있습니다

| 항목 | 결과 |
| --- | --- |
| 빌드 (`pnpm --dir functions build`) | 성공 |
| 테스트 (`pnpm --dir functions test`) | 1,152건 전부 통과 |
| 배포 대상 함수 | 31개 |

**새로 만들 것은 없습니다.**

# A안 — 요금제를 바꿔 지금 앱을 살린다 (권장)

## 1단계 — 요금제 전환 (사장님)

Firebase 콘솔에서 `bring-fm` 프로젝트를 **Blaze(종량제)** 로 바꿉니다.
카드 등록이 필요합니다.

**Blaze로 바꿔도 무료 사용량은 그대로 유지됩니다.** 매달 다음까지는 요금이
붙지 않습니다.

| 항목 | 무료 범위 |
| --- | --- |
| 함수 호출 | 월 200만 회 |
| 함수 실행 시간 | 월 40만 GB-초 / 20만 CPU-초 |
| 함수 외부 통신 | 월 5GB |
| 실시간 데이터베이스 | 저장 1GB, 내려받기 하루 360MB |

직원 몇 명이 쓰는 현장앱은 이 범위 안에 들어올 가능성이 높습니다. 다만
**예상 밖 청구를 막으려면 예산 알림을 반드시 걸어 두세요.**

- Google Cloud 콘솔 → 결제 → 예산 및 알림 → 예산 만들기
- 금액을 정하고(예: 월 1만 원) 50% / 90% / 100% 알림을 켭니다

> 예산은 **알림**이지 자동 차단이 아닙니다. 완전히 막고 싶으면 결제 계정
> 분리나 상한 자동화를 따로 설정해야 합니다.

## 2단계 — 함수 배포 (사장님 PC에서)

**자동 배포로는 되지 않습니다.** CI 신원에는 함수 배포 권한이 일부러 빠져
있습니다(`release/bootstrap-bring-fm-wif.ps1` 가 Functions 권한을 명시적으로
금지합니다). 보안상 의도된 설계라 그대로 두는 것이 맞습니다.

사장님 계정으로 직접 배포합니다.

```bash
# 1. 이 저장소를 받은 폴더에서
git checkout codex/bring-field-platform
git pull

# 2. 로그인 (브라우저가 열립니다)
npx firebase-tools login

# 3. 빌드
pnpm --dir functions install --frozen-lockfile
pnpm --dir functions build

# 4. 무엇이 배포될지 먼저 확인
npx firebase-tools deploy --only functions --project bring-fm --dry-run

# 5. 실제 배포
npx firebase-tools deploy --only functions --project bring-fm
```

처음 배포는 10~20분 걸릴 수 있습니다. 필요한 API(Cloud Build, Artifact
Registry 등)를 켜라는 안내가 나오면 그대로 진행하면 됩니다.

## 3단계 — 허용 목록 등록 (빠뜨리면 로그인이 막힙니다)

이 단계가 없으면 배포를 마쳐도 로그인이 되지 않습니다.

먼저 구글 자격증명을 준비합니다. 서비스 계정 키 파일을 내려받지 않아도 됩니다.

```bash
gcloud auth application-default login
```

그다음 등록합니다. **먼저 확인만 하고**, 내용이 맞으면 `--yes` 를 붙여 다시
실행합니다.

```bash
# 확인만 (아무것도 쓰지 않습니다)
node functions/scripts/bootstrap-field-account.mjs \
  --email=회사구글계정@gmail.com --role=admin

# 실제 등록
node functions/scripts/bootstrap-field-account.mjs \
  --email=회사구글계정@gmail.com --role=admin --yes
```

역할은 `admin`, `staff`, `reviewer` 중 하나입니다. 직원을 추가할 때마다 같은
명령을 이메일만 바꿔 실행하면 됩니다.

권한을 회수할 때는 `--mode=revoke` 를 씁니다.

```bash
node functions/scripts/bootstrap-field-account.mjs \
  --email=그만둔직원@gmail.com --mode=revoke --yes
```

> 이미 발급된 로그인 토큰은 최대 1시간 남아 있습니다. 즉시 끊어야 하면
> Firebase 콘솔 → Authentication 에서 해당 계정을 사용 중지하세요.

## 4단계 — 확인

```bash
npx firebase-tools functions:list --project bring-fm
```

31개가 보이면 배포는 성공입니다. 그다음 현장앱에서:

1. 3단계에서 등록한 구글 계정으로 로그인합니다
2. 건물 하나를 열어 사진 한 장 올려 봅니다
3. 데스크톱 CRM의 `현장 업무` 메뉴에서 그 기록이 보이는지 확인합니다

## 되돌리기

문제가 생기면 함수만 내리면 됩니다. 데이터는 그대로입니다.

```bash
npx firebase-tools functions:delete <함수이름> --project bring-fm
```

요금제 자체를 Spark로 되돌릴 수도 있습니다. 그러면 함수가 멈추고 현장앱은
지금 상태로 돌아갑니다. **CRM 본체와 업무흐름 빌더는 영향을 받지 않습니다** —
그쪽은 Apps Script와 데이터베이스만 씁니다.

# B안 — 요금제를 그대로 두고 예전 버전을 쓴다

요금제를 바꾸고 싶지 않다면 이 길이 있습니다. **다만 기능이 줄어듭니다.**

## 되는 것과 안 되는 것

v1 현장앱은 데이터베이스와 구글 드라이브에 **직접** 붙습니다. 규칙을 확인해
보면 건물·호실·매물·방문·촬영세션·사진·소유자 메모·광고 패키지·체크리스트가
모두 클라이언트에게 열려 있습니다. 함수가 없어도 됩니다.

| | v1 (B안) | v2 (A안) |
| --- | --- | --- |
| 건물·호실·매물 등록 | 됨 | 됨 |
| 사진 촬영·드라이브 업로드 | 됨 | 됨 |
| 소유자 메모, 광고 패키지 | 됨 | 됨 |
| **작업 배정·전환·방문 변경** | **없음** | 됨 |
| 데스크톱↔현장 인계 | 없음 | 됨 |

작업 배정 기능이 v2에서 새로 만든 것이라 B안에서는 쓸 수 없습니다.

> **역할은 `admin` 또는 `reviewer` 로 등록하세요.** `staff` 로 등록하면 사진
> 열람·제외 기능만 함수를 부르는 경로로 되돌아가서, 함수가 없는 B안에서는
> 그 부분이 실패합니다(`FieldApp.tsx` 의 `directAdApi` 가 `admin`/`reviewer`
> 일 때만 만들어집니다). 나머지 등록·촬영·업로드는 역할과 무관하게 됩니다.

## 필요한 일

1. **허용 목록 + 권한을 직접 등록합니다.** 함수가 없으니 `--mode=provision`
   으로 권한까지 한 번에 붙입니다. 대상 계정이 현장앱에서 **구글 로그인을 한 번
   시도한 뒤**에 실행해야 합니다(계정이 있어야 권한을 붙일 수 있습니다).

   ```bash
   gcloud auth application-default login

   node functions/scripts/bootstrap-field-account.mjs \
     --email=회사구글계정@gmail.com --role=admin --mode=provision --yes
   ```

2. **`/field` 가 v1을 보여 주도록 바꿉니다.** 지금은 v2를 서빙합니다.
   `company-site/app/field/page.tsx` 한 줄짜리 변경이지만, 현장 직원이 보는
   화면이 통째로 바뀌는 일이라 **사장님이 결정하실 일**이라 보고 손대지
   않았습니다. 진행하시겠다면 말씀해 주세요.

권한을 회수할 때는 A안과 같습니다(`--mode=revoke`).

## 건드리지 말아야 할 것

`release/firebase-targets.json` 의 `functionsDeploymentAllowed: false` 는
**자동 릴리스가 함수를 배포하지 못하게** 막는 장치입니다. 코드로 검증까지
하고 있습니다(`readAutomaticFirebaseTarget`). 함수 배포는 위처럼 사람이
확인하고 하는 별도 작업이므로, 이 값은 `false` 로 두는 것이 맞습니다.

CI 신원의 함수 배포 권한도 마찬가지입니다. 넓히지 않는 것이 맞습니다.
