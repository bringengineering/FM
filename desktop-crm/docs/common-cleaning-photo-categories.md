# 공용부청소 사진 분류와 보고서 페이지 검증

공용부 사진은 작업 구역과 전·중·후 단계를 따로 판단한다. 구역이 확실해도 깨끗한 표면이나 촬영 순서만으로 작업 전·후나 완료를 확정하지 않는다. 사람이 수정한 구역·단계는 재분류와 Drive 재선택 때 보존한다.

## 구역과 필요한 근거

기존 `windows` 키는 유지한다. 새 보고서에서는 창틀·레일을 뜻하며, 저장된 예전 보고서의 항목명과 수행범위는 그대로 읽힌다. 추가 항목은 선택 목록에 표시하고 사진이 선택된 보고서에만 포함한다.

| 키 | 구역 | 필요한 시각 근거 |
| --- | --- | --- |
| entrance | 출입구·현관 | 출입문 구조 |
| corridor | 복도·공용 바닥 | 이어지는 복도 또는 경계가 보이는 외부 통로와 바닥면 |
| stairs | 계단·계단참 | 계단 단차 또는 계단에 연결된 계단참 |
| handrail | 난간·손잡이 | 중심 대상인 난간 구조 |
| windows | 창틀·레일 | 창틀 구조 또는 창틀 홈·레일 |
| glass | 공용 유리 | 중심 대상인 유리 면 |
| yard | 마당·외부 바닥 | 마당의 경계·주변 공간과 바닥면 |
| parking | 주차장 | 주차선·주차 구획과 바닥면 |
| drain | 배수구·트렌치 | 중심 대상인 배수 홈·그레이팅 |
| rooftop | 옥상·테라스 | 해당 공간을 확인할 경계 구조와 바닥면 |
| elevator | 승강기 | 승강기 문·내부·버튼 구조 |
| walls | 벽면·문 | 벽면 또는 문 표면 |
| lighting | 조명·천장 | 천장 설비 또는 위쪽 천장면 |
| recycle | 분리수거장 | 분리수거 용기 |
| final | 마감·안전 확인 | 사람이 지정하는 기록; 깨끗한 사진만으로 자동 선택하지 않음 |

구역 점수가 75 미만이거나 필요한 근거가 없으면 `review`로 보류한다. 배경에 차량·난간·창틀이 보인다는 이유로 중심 작업 대상을 바꾸지 않는다. 작업 중 판단은 기존의 접촉·동작 근거와 별도 점수 기준을 유지한다.

분류 값은 Worker 응답 스키마, 근거 정규화, 데스크톱 클라이언트, 사진 계획, 보고서 항목에서 함께 지원한다. 관련 회귀 검사는 양쪽의 `test/common-photo-categories.test.js`에 있다.

## PDF 푸터

본문 마지막의 푸터가 다음 쪽으로 넘어가고 사진 묶음이 강제로 새 쪽에서 시작하면 푸터만 있는 중간 페이지가 생겼다. 건물주용 보고서는 푸터를 본문에서 제거하고 `@page`의 `@bottom-left`와 `@bottom-right`에 브랜드와 페이지 번호를 표시한다. 작성 업체와 수신인은 본문에 보존한다. 사진·요약·캡션을 잘라서 페이지 수를 줄이지 않는다.

이 페이지 여백 기능은 [Chromium 131부터 지원된다](https://developer.chrome.com/blog/print-margins). 현재 CRM의 Electron 39 계열에서 사용할 수 있다.

로컬 Chromium PDF 출력 검증에서는 수정 전 재현 보고서가 3쪽, 수정 후 같은 내용과 사진 2장이 2쪽으로 출력됐다. 추가로 6장 사진, 불균형한 전·중·후 사진 100장, 긴 요약, 긴 후속 안내, 긴 캡션, 전체 구역, 긴 구역명을 검사했다. 수정 후 8개 사례에 푸터만 있는 페이지나 사진 누락이 없었다. 긴 내용은 필요한 만큼 여러 쪽으로 이어진다.

모델 응답·전송·저장 검사는 합성 응답을 사용했다. 실제 현장 사진을 Gemini에 다시 보내 정확도 수치를 측정한 검사는 아니다.
