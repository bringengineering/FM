# BRING CARE CRM·카카오 상담 연결 설계

## 목적

네이버 광고 랜딩페이지의 간편 견적 신청을 회사 Firebase CRM의 실제 신규 고객 기록으로 저장하고, 접수 직후 사용자가 BRING CARE 카카오톡 채널 상담으로 이어지게 한다.

## 확정 사용자 흐름

1. 사용자가 이름, 휴대폰 번호, 지역, 상담 니즈를 입력한다.
2. 브라우저는 Firebase App Check 토큰을 확보하고 Realtime Database에 익명 인증 없이 접속한다.
3. Firebase Database Rules가 010 휴대폰 번호, 동의 여부, 허용 서비스·경로, 필드 길이와 서버 시각을 검증한다.
4. 브라우저는 외부에서 읽을 수 없는 `crmCompany/marketingLeadInbox/{requestId}`에 새 접수 한 건만 생성한다.
5. CRM 직원 계정은 기존 권한 체계로 접수함을 읽고 대시보드에서 신규 문의를 즉시 확인한다.
6. 동일한 요청 ID는 한 번만 생성할 수 있어 더블클릭·재시도 중복을 막는다.
7. 접수 후 개인정보가 아닌 접수번호만 완료 화면 이동에 사용한다.
8. 완료 페이지에서 `https://pf.kakao.com/_xnaRfX/chat`을 새 창으로 여는 카카오톡 상담 버튼과 전화 상담 대안을 제공한다.

## 데이터 설계

- `crmCompany/marketingLeadInbox/{requestId}`: 이름, 전화번호, 지역, 상담 니즈, 문의 유형, 서비스, 랜딩 경로, UTM, 접수 시각과 처리 상태
- 공개 사용자는 새 레코드 생성만 가능하며 조회·수정·삭제할 수 없다.
- CRM의 admin/member/viewer는 접수함을 읽을 수 있고, admin/member만 처리 상태를 바꿀 수 있다.
- 접수함은 CRM 저장 데이터와 분리된 읽기 전용 오버레이로 불러와 기존 고객·계약 동기화 과정에서 삭제되지 않게 한다.

## 보안 및 개인정보

- 유료 서버 함수 대신 브라우저가 제한된 접수함 한 곳에만 직접 쓴다.
- 이름·전화번호를 URL, 접수 완료 주소, 브라우저 저장소에 넣지 않는다.
- 010 형식 휴대폰 번호를 정규화하고 길이를 제한한다.
- 허용된 서비스·랜딩 경로만 받는다.
- honeypot과 Firebase App Check를 적용한다.
- 요청 ID로 재시도 중복 저장을 방지한다.
- 동의 문구는 이메일 전달이 아니라 CRM 저장과 상담 연락에 대한 동의로 바꾼다.
- 무료 구조에는 신뢰할 수 있는 서버 기반 IP 속도 제한과 전화번호 중복 고객 병합이 없으므로 CRM에는 원본 접수함으로 저장한다.

## 실패 처리

- 접수함 저장에 실패하면 완료 페이지로 이동하지 않는다.
- 화면에 전화 상담과 신청 내용 복사 대안을 유지한다.
- 신청 내용 복사 기능은 장애 시 수동 전달을 돕는 보조 경로로 둔다.
- 카카오톡 버튼은 폼 데이터를 자동 전송하지 않는다. CRM에는 이미 신청 내용이 저장되며, 사용자가 직접 채팅을 시작한다.

## 완료 기준

- 세 랜딩 모두 니즈 필드와 실제 휴대폰 형식 검증을 제공한다.
- 정상 제출은 CRM 신규문의 접수함 레코드를 생성하고 접수번호와 함께 완료 페이지로 이동한다.
- 중복 요청 ID가 접수함 레코드를 두 번 만들지 않는다.
- 완료 페이지의 주 행동이 BRING CARE 카카오톡 상담이다.
- Database Rules 에뮬레이터 테스트, CRM 오버레이 테스트, 랜딩 테스트, 타입 검사와 빌드가 통과한다.
