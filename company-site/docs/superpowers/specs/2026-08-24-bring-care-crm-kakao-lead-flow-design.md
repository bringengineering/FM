# BRING CARE CRM·카카오 상담 연결 설계

## 목적

네이버 광고 랜딩페이지의 간편 견적 신청을 회사 Firebase CRM의 실제 신규 고객 기록으로 저장하고, 접수 직후 사용자가 BRING CARE 카카오톡 채널 상담으로 이어지게 한다.

## 확정 사용자 흐름

1. 사용자가 이름, 휴대폰 번호, 지역, 상담 니즈를 입력한다.
2. 브라우저는 같은 출처의 `/api/marketing-leads`로 JSON을 전송한다.
3. Firebase HTTPS 함수가 입력값, 010 휴대폰 번호, 동의 여부, 봇 필드, 요청 빈도를 검증한다.
4. 함수가 `crmCompany/data` 아래에 신규 고객과 상담 기록을 원자적으로 저장한다.
5. 계단·공용부 청소 또는 건물관리 문의는 건물주 영업 파이프라인에도 후보·연락처·서비스 기회를 함께 만든다.
6. 같은 번호가 다시 신청하면 고객을 중복 생성하지 않고 기존 고객에 새 상담 기록을 추가한다.
7. 성공 응답에는 개인정보가 아닌 접수번호만 포함한다.
8. 완료 페이지에서 `https://pf.kakao.com/_xnaRfX/chat`을 새 창으로 여는 카카오톡 상담 버튼과 전화 상담 대안을 제공한다.

## 데이터 설계

### 모든 신청

- `customers/{customerId}`: 이름, 전화번호, 주소·지역, 관심 서비스, 현재 니즈, 홈페이지 유입, 신규 고객 단계
- `activities/{activityId}`: 접수 시각, 유입 랜딩, UTM, 상담 니즈, 후속 행동
- `marketingLeadReceipts/{requestId}`: 중복 전송을 막는 비개인 접수 영수증
- `marketingLeadPhoneIndex/{phoneHash}`: 같은 전화번호를 기존 고객에 연결하기 위한 해시 인덱스

### 건물주 성격의 신청

- `salesProspects/{prospectId}`: 건물 후보, 주소, `candidate` 단계
- `salesContacts/{contactId}`: 제출 연락처, 단 실제 번호 소유가 인증된 것은 아니므로 `verifiedAt`은 비워 둔다.
- `salesOpportunities/{opportunityId}`: 공용부 청소는 `common_cleaning`, 입주청소는 `move_in_cleaning`, 건물관리는 `other`로 기록한다.
- `salesEvents/{eventId}`: 홈페이지 상담 신청으로 후보가 생성됐다는 증거 기록

## 보안 및 개인정보

- 브라우저가 Realtime Database에 직접 쓰지 않는다.
- 이름·전화번호를 URL, 접수 완료 주소, 브라우저 저장소에 넣지 않는다.
- 010 형식 휴대폰 번호를 정규화하고 길이를 제한한다.
- 허용된 서비스·랜딩 경로만 받는다.
- honeypot과 IP 해시 기반 시간당 요청 제한을 적용한다.
- 요청 ID로 재시도 중복 저장을 방지한다.
- 동의 문구는 이메일 전달이 아니라 CRM 저장과 상담 연락에 대한 동의로 바꾼다.

## 실패 처리

- CRM 저장에 실패하면 완료 페이지로 이동하지 않는다.
- 화면에 전화 상담과 신청 내용 복사 대안을 유지한다.
- 이메일 폼 전송 코드는 제거하지 않고 장애 시 수동 전달을 돕는 보조 경로로 둔다.
- 카카오톡 버튼은 폼 데이터를 자동 전송하지 않는다. CRM에는 이미 신청 내용이 저장되며, 사용자가 직접 채팅을 시작한다.

## 완료 기준

- 세 랜딩 모두 니즈 필드와 실제 휴대폰 형식 검증을 제공한다.
- 정상 제출은 CRM 고객·상담 기록을 생성하고 접수번호와 함께 완료 페이지로 이동한다.
- 중복 요청 ID와 같은 전화번호 재신청이 중복 고객을 만들지 않는다.
- 완료 페이지의 주 행동이 BRING CARE 카카오톡 상담이다.
- 서버 테스트, 랜딩 테스트, 타입 검사, 빌드가 통과한다.
